Module 1 — Kubernetes Through an AI Lens

You already run Kubernetes. This module does not re-teach it. It re-reads the objects you know, one at a time, and shows where an AI workload breaks the instinct you built around each of them.

Then you reproduce three of those breaks yourself, on a cluster on your own laptop, before you read much more. That is the order on purpose: build first, explain after.

Seven Kubernetes assumptions that AI workloads break​

Think of Kubernetes as a city bus service. Buses are identical. Passengers are interchangeable. If one bus is full, the next one will do. Nobody minds if a bus runs a little late, and if one breaks down the passenger simply takes another.

An AI workload is not a bus passenger. It is a chartered train: you need a whole coach, every seat in it, all booked together, and the cargo takes minutes to load before the train can even leave. The kube-scheduler, the Service and the HorizontalPodAutoscaler controller were all tuned for buses. Here are the seven spots where that shows.

Assumption you holdWhat an AI workload does to itFixed in
Requests and limits are soft. A Pod can burst and the node will squeeze it.An accelerator, that is a GPU or a similar card, can neither be squeezed nor burst. You get the device or you do not.M4
The kube-scheduler handles one Pod at a time.A training job needs eight workers together or none. Seven placed Pods hold seven devices and make no progress.M5
A PVC and a StorageClass are plumbing.The storage path decides whether an expensive accelerator is busy or waiting for data.M6
A Deployment starts a Pod and it is ready soon after.A model server loads weights for minutes and then holds a cache in memory that you cannot just restart away.M8
A Service spreads requests round-robin and that is fair.Across LLM replicas, round-robin is a performance bug, because the replica that already holds the right cache should get the request.M9
The HorizontalPodAutoscaler controller sizes the replica count from CPU.The request queue grows and users wait, but the autoscaler reads CPU, which does not follow the queue. It may add no replica at all, or add one that cannot serve until the load has passed.M8
A Job is a Pod that runs to completion, and a ResourceQuota counts what you have.A job is a gang, and a quota for a device nobody has installed is a trap.M5 and M7

You do not need to memorise this table. The lab makes the first, fourth and sixth rows happen in front of you, with real command output, and the rest of the course fixes them in the order shown.

Run the lab now

Go to the lab and do it before you continue. It takes you to a completed result: a running cluster, three failures you caused on purpose, and a file in your own repository that records them with real output. The rest of this page will make more sense after.

The four workload classes and the AI Platform Engineer role​

Every AI workload your platform will carry falls into one of four classes. Module 2 takes each in detail, so this is only the map.

ClassWhat it is, in one line
Data preparationBatch work that reads and writes large datasets. Cheap CPUs mostly, heavy on storage
Training and fine-tuningA gang of workers that run together for hours or days and must survive a failure by resuming
InferenceA long-running service answering requests, where latency and cache are the product
AgentsSoftware that calls models and tools in a loop, and needs a boundary around what it may touch

Now the job title. An AI Platform Engineer is the person who runs these four classes for many teams at once. Think of a railway operator, not a train driver. The ML team decides which model to run and whether it is good. The application team decides what to build on top. You decide whether the devices exist, who gets them, whether the job starts, whether the service stays up, and what it costs.

BoundaryOwns
AI Platform EngineerDevices, quota, scheduling, serving infrastructure, the data path, observability, cost
ML teamModel choice, quality, training code, evaluation
Application teamThe product built on the model, prompts, retrieval, the user experience

Where ownership sits​

The three failures in the lab each have a different owner. If you cannot say who drives a mechanism, you cannot debug it, so this table is worth reading before the lab output makes sense.

MechanismOwner
Places a Pod on a node, or leaves it Pendingscheduler (kube-scheduler, the control-plane process that picks a node)
Creates and replaces Pods through a rolloutDeployment controller
Routes requests to Pod endpointsService (EndpointSlice objects and kube-proxy do the actual routing)
Changes the replica count from a metricHPA controller
Supplies the CPU metric the HPA readsmetrics-server

Read it left to right. The first row is the scheduler saying nothing useful. The second is a Service sending traffic to a Pod that has not opened its port yet. The third is an HPA watching a number that does not measure the problem. The lab ran three times with the same load, and each time the queue reached 15 or 16 waiting requests. In the first run CPU read 24 percent of the request and the HPA never scaled. In the second it read 66 percent, and the HPA added a replica that could not answer until the load was over. In the third it read 36 percent, and the HPA never scaled.

The lab environment and the Lab Truth Contract​

Every lab in this course carries one of four tags, and the tag is on the lab page, in the page header and in the checks file. The tag tells you what you are about to run, so you never have to guess whether a number came from real hardware.

TagMeaning
REALReal software doing the real thing, on your own machine
SIMULATEDA simulator, a synthetic device or a fake node stands in for hardware
RENTED HARDWARERun on a rented accelerator instance, inside a declared environment and a stated cost
BRIEFConcepts, objects and manifests only. Nothing was executed

Two rules follow from it. A claim never goes beyond its tag. And a synthetic device is never called a GPU: it is a synthetic device, a simulated device, every single time.

The environment. Everything on the core path runs on one laptop, with no GPU, no cloud account and no registry login.

  • Rancher Desktop with the Moby (dockerd) engine as the container runtime.
  • kind v0.33.0, creating a real Kubernetes cluster in containers, pinned to a 1.37.x node image. A real kubelet matters, because probes and Pod execution only behave truthfully on a real one.
  • kubectl at the matching version, and helm.
  • KWOK, which fakes nodes for scale and topology work in later modules. It has no kubelet, so it is never used where a device must be prepared.

If you have not set this up yet, the lab setup page walks through it.

The profiles. A profile is a cluster you can create, verify and tear down with three scripts. You run one profile at a time, on a machine with 8 GB or 16 GB of memory, and the lab tells you which size each step needs. This module uses the base profile, grid-core, with one control-plane node and one worker.

The platform repository. In the lab you point your clone at a repository you own and start grid-platform inside it. Every module adds to it. By the end it is the platform you built, in Git, as proof.

The rented-GPU track. Four optional labs use one rented GPU instance, because some behaviour only exists on hardware: sharing a device between Pods, partitioning it, collective communication across a link, and a real model server under load. Each declares its instance type and software, finishes inside an hour, and states its cost, which is a few dollars. To avoid being billed for something you forgot: run the teardown at the end of the lab, check the provider console for running instances, and set a spending alert before you start. Two things you should know. These four are written and reviewed, but they have not been machine-validated, because no GPU was available while the course was built, and each page says so. And each one has a read-along path, so you lose nothing by skipping the rental.

Your laptop simulates the devices. The four rented labs validate the hardware-specific behaviour. And every lab tells you which one it is.
