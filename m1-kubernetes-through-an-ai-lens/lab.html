Lab — Reproduce Three AI Workload Failures on Kubernetes

Lab Truth Contract — REAL

The cluster, the scheduler, the Service, the HPA and every object you read are real Kubernetes behaviour on a real kind cluster. The one thing instrumented is the simulator's startup window, which is a timed wait that prints labelled states, not a model loading.

Your laptop simulates the devices; four optional labs on one rented GPU validate the hardware-specific behaviour, and every lab tells you which it is.

In this lab you will build a small cluster on your laptop and make three failures happen on purpose, so you can read each one in real command output. A Pod asks for a device no node has. A slow-starting server sits behind a Service with no readiness gate. An autoscaler watches CPU while the queue grows. You will record all three in your own grid-platform repository.

Run every command from the root of your clone of the labs repository, as the setup page shows. If you open a second terminal, export KUBECONFIG there again.

Where the platform stands​

Before this lab you have a laptop and a clone. After it you have a cluster profile that you create, verify and tear down with one command each, and a file in your own repository, grid-platform/docs/baseline-failures.md, holding three failures with real output.

Three things are still broken when you finish, and that is the point. The device request stays Pending until the device modules in M4 give the scheduler something to allocate. The startup window and the autoscaler signal stay broken until M8, which adds readiness gating and a queue-aware metric. You are recording the problem so the later modules have something to fix.

When you finish, check that each of the three failures has its own section in that file, with the command you ran and the output it printed under it. A failure without its output is a claim, and this course does not accept claims.

What this lab installs​

This lab names everything it puts on your cluster. Three images are pulled, and each is pinned by its index digest, which is a hash that resolves to the same image on Apple Silicon and on x86. The digests and platform lists are in m1/PINS.md.

ComponentVersionWhat it is for
metrics-serverv0.9.0Supplies CPU and memory numbers to the HPA. A CPU autoscaler cannot work without it
llm-d-inference-simv0.11.2An instrumented simulator. It answers requests on the OpenAI-style path and publishes queue metrics. It is not a model server, and it loads no model
busybox1.37.0The shell that starts the simulator after a timed wait, and the client that sends test traffic

The simulator image has no shell, so busybox starts it. The simulator binary is mounted into the busybox container from the simulator's own image, through an image volume. Nothing here is built on your machine.

A slow pull is not a failure

The simulator image is about 40 MB, and how long its first pull takes depends on your link. Two cold pulls of the same image on the authoring host gave two very different figures, each read from the kubelet's Pulled event.

MeasuredPull timeConditions
2026-10-248 m 2 sone cold pull, registry link of about 160 KB/s, no mirror, Apple M1 Pro through a Rancher Desktop VM
2026-10-3012.39 s, or 17.758 s including waitingone cold pull on a freshly created cluster, link speed not measured, no mirror, same host

The lab pre-pulls the image before the first timed observation, so what you watch later is the simulator's startup window and not your download.

metrics-server varies too. On the course's first run it was still not Available when a five-minute wait ran out, and the cause was not established. On the cold run this page shows, its Pod was Ready 45 seconds after it was created. So the lab starts it early and waits for it with a bound that tells you what to inspect if it runs out.

Symptom one: a device request no node can satisfy​

A Pod asks for one nvidia.com/gpu, the resource name a real GPU node would advertise. This cluster has no GPU and no node here advertises one, so the request cannot be met.

file: m1/device-request.yaml

apiVersion: v1
kind: Pod
metadata:
  name: device-request
  namespace: m1-baseline
spec:
  containers:
    - name: app
      image: docker.io/library/busybox@sha256:bdf57e528e45e4433820e045b29b4597825a1c9e38353532d90a01445013f82e
      command: ["sleep", "3600"]
      resources:
        limits:
          nvidia.com/gpu: 1

Apply it, then confirm the Pod exists.

kubectl --context kind-grid-core apply -f m1/device-request.yaml
kubectl --context kind-grid-core -n m1-baseline get pod device-request

[ Expected output ]

Symptom two: a slow-starting server behind a Service with no readiness gate​

Now the simulator. Its startup window is a timed wait of 60 seconds, printed as labelled startup-state= lines, then the simulator opens its port. That window stands in for a model server loading weights. It is instrumentation, not a model load.

The Deployment has no readiness probe. That is deliberate, because that is the symptom. Here are the parts that matter.

file: m1/simulator.yaml (excerpt)

      containers:
        - name: sim
          image: docker.io/library/busybox@sha256:bdf57e528e45e4433820e045b29b4597825a1c9e38353532d90a01445013f82e
          env:
            - name: STARTUP_SECONDS
              value: "60"
          command:
            - sh
            - -c
            - |
              echo "startup-state=loading (instrumentation: a timed wait of ${STARTUP_SECONDS}s, not a model load)"
              [...]
              echo "startup-state=serving (exec llm-d-inference-sim; port 8000 opens once it has started)"
              exec /sim/app/llm-d-inference-sim --config=/config/latency-profile.yaml --model=m1-sim --force-dummy-tokenizer=true --port=8000
          [...]
      volumes:
        - name: simulator
          image:
            reference: ghcr.io/llm-d/llm-d-inference-sim@sha256:32144df791330a0006b747edfdf2b114a0fe728e023a9d1b3463eeb48d32abb9

where,

  • STARTUP_SECONDS is the declared length of the window.
  • the wrapper prints the states, waits, then execs the simulator, so the running process is the simulator.
  • the simulator volume is the simulator image, mounted read-only at /sim.
  • there is no readinessProbe, so Kubernetes counts the container ready the moment it starts.

The latency numbers come from an upstream profile in the ConfigMap, copied unchanged. Nothing the simulator prints about latency is a measurement.

Apply the simulator and a client Pod, and confirm the objects exist. Each object is named in the kind/name form, because plain words after get deployment would all be read as Deployment names.

Observe it. Only the new Pod is listed, and it reads ready=true serving=true about 20 seconds into a 60-second window, while its port is still closed. This is symptom two. The Deployment has no readiness probe, so the kubelet marked the new container ready the moment it started. The Deployment then counted the new Pod available and removed the old one, and the EndpointSlice now sends every request to a Pod that cannot answer yet. A readiness gate is exactly what would have kept this Pod out of the list. Wait for the loop to finish, then count what the client saw.

wait

If your HPA did scale, look at what the new replica did. It has no readiness probe either, so the kubelet marked it ready the moment its container started, and the Service began sending it requests. But it still had its 60-second startup window to sit through, with its port closed, and the load was over before that window could end. So the replica the HPA added could not answer a single request while users were waiting. What it did do was refuse its share of them: those are the Connection refused lines among the load output. In the run that scaled, there was one Pod before the scale-up and it was already answering, so the refusals came from the new one. That is symptom two again, inside symptom three.

That is symptom three. The HPA was given CPU, and CPU is not the queue. This simulator models its latency by waiting rather than computing, so the CPU it burns says little about how many users are waiting. Whether your HPA scales, and when, depends on a number that does not measure the problem. M8 changes the signal to the queue itself, and gates a new replica on readiness before it gets traffic.

kind get clusters still lists grid-core after the deep dive. Seen in a learner walk that read the pages in sidebar order (QA M1 walk F6). The deep dive's rebuild brings the cluster back after this page's Teardown. Run both blocks of this page's Teardown again; Module 2 needs no cluster.

Where you will use this​

The next time a team tells you their training Pod has been Pending since the morning, you will read the PodScheduled condition before you read anything else, and you will know what the message leaves out. The next time a model server rollout drops requests while every dashboard says healthy, you will look at the readiness gate and the EndpointSlice before you blame the network. And the next time an inference service is slow but its autoscaler is idle, you will ask which number the autoscaler was given.

Teardown​

Delete the lab's objects, confirm they are gone, then delete the cluster. Your Git commit is already done.

Delete metrics-server first. It registers the metrics.k8s.io API with the API server. The namespace controller lists every registered API group to find what is left in a namespace, so if a registered API cannot answer, the namespace can stay Terminating. Removing metrics-server first removes that registration, so the namespace deletion that follows cannot wait on it. The --timeout bounds the wait, so a stuck deletion shows up as an error instead of a terminal that never returns.

kubectl --context kind-grid-core delete -f m1/metrics-server.yaml
kubectl --context kind-grid-core delete namespace m1-baseline --timeout=5m
kubectl --context kind-grid-core get namespace m1-baseline --ignore-not-found
