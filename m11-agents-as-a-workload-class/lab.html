Lab — Agent Sandboxes Under gVisor, a Read-Only Tool Identity and the Audit Trail

Lab Truth Contract — REAL

Everything here runs for real on a real kind cluster: nested gVisor under a real kubelet, the Agent Sandbox controller, RBAC, NetworkPolicy and the API server's own audit log. The warm-pool part reads a manifest only and applies nothing. No part of this page shows that the sandbox isolates anything; it shows which kernel a workload talks to, and who was allowed to do what.

In this lab you build a cluster whose nodes can start Pods under gVisor, then you put a workload inside it and ask four questions with evidence. Which kernel is it really talking to? How long does a sandbox take to be ready? What does it see that a plain Pod does not, and what does it see the same? And when something with an identity tries to change the cluster, who stops it, and who can prove it afterwards?

Think of it as moving a guest into a building with a front desk that answers every request itself. First you check the guest really is behind the desk and not wandering the corridors. Then you time check-in. Then you walk both a guest and a resident through the same short list of doors and write down which ones open. Last, you give one guest a key that only reads the notice board, and watch the building's own visitor log record every door they tried.

Run every command from the root of your clone of the labs repository, as in the earlier modules. If you open a second terminal, export KUBECONFIG there again. You need jq on your machine; the setup page installed it.

Where the platform stands​

On the path through this course so far you have built Modules 1 to 4: the base cluster and its wrappers, the primer's capacity and cost models, the platform design and its audit, and the node layer with synthetic devices. Modules 5 to 10 come before this one in the course, but this lab assumes nothing from them, so it runs the same whether or not you have done them.

What the platform cannot do yet is host code nobody reviewed. No workload on it runs under any runtime but the default one, no identity exists for an agent or a tool server, nothing limits where a Pod's packets may go, and the API server records nobody's requests. When you finish, the platform can place a workload under gVisor and prove it from inside, give a tool server an identity that can only read, refuse an actor's direct change, and show the refusal and your approval in the audit log. Your repository gains grid-platform/agents/, grid-platform/docs/autonomy-policy.md and the grid-sandbox wrappers.

One thing is still missing, on purpose. Nobody can see what any of this is doing while it runs: there is no dashboard, no alert and no trace. M12 adds them.

Create the sandboxed cluster​

This lab runs on its own cluster profile, grid-sandbox, because its nodes need something the base cluster's nodes do not have: containerd configured with the runsc runtime handler. containerd reads that configuration once, when it starts, so the handler has to be in the node image before the cluster exists. You build that image first, on your own machine. It also carries the API server's audit policy, which this lab reads at the end.

bash sandbox/runsc-node/build.sh

Measure sandbox allocation latency​

How long does a caller wait between asking for a sandbox and being able to use it? The object answers that itself: metadata.creationTimestamp is when the API server accepted it, and the Ready condition's lastTransitionTime is when the controller reported it ready. Agent Sandbox v1.0.5 does have a creation-latency metric, but it records a sample only for a sandbox that arrives through a SandboxClaim, and a Sandbox you create directly, as here, gets none. So the object's own timestamps are the instrument, at one-second resolution.

You create five Sandboxes from the same template as probe-sandbox, one after another, each deleted before the next starts, so no run shares the node with another. Each row is computed from the object by jq and saved as you go.

: > evidence/m11/latency-rows.txt
for i in 1 2 3 4 5; do
  sed "s/name: latency-1$/name: latency-$i/" m11/latency-sandbox.yaml | kubectl --context kind-grid-sandbox apply -f -
  kubectl --context kind-grid-sandbox -n agent-probes get sandbox "latency-$i" -o name
  kubectl --context kind-grid-sandbox -n agent-probes wait --for=condition=Ready "sandbox/latency-$i" --timeout=300s
  kubectl --context kind-grid-sandbox -n agent-probes get sandbox "latency-$i" -o json \
    | jq -r --arg run "$i" '(.status.conditions[] | select(.type == "Ready") | .lastTransitionTime) as $r
        | "| \($run) | \(.metadata.name) | \(.metadata.creationTimestamp) | \($r) | \(($r | fromdate) - (.metadata.creationTimestamp | fromdate)) |"' \
    | tee -a evidence/m11/latency-rows.txt
  kubectl --context kind-grid-sandbox -n agent-probes delete sandbox "latency-$i" --wait=true
  kubectl --context kind-grid-sandbox -n agent-probes wait --for=delete "pod/latency-$i" --timeout=180s
done

The grid-sandbox API server writes an audit event, at Metadata level, for every request in agent-mcp, agent-actor and agent-target, and for every request made by the two lab ServiceAccount groups anywhere. Write the record into your repository. The jq below takes the non-read requests from those three identities, drops repeats, and adds what each row proves:

  echo
  echo "Read from the grid-sandbox API server's audit log (Metadata level), ConfigMaps in agent-target, non-read verbs only."
  echo
  echo "| Who | Verb | Object | Code | What it proves |"
  echo "|---|---|---|---|---|"
  kubectl --context kind-grid-sandbox -n kube-system logs kube-apiserver-grid-sandbox-control-plane \
    | jq -Rnr --arg me "$ME" '[inputs | fromjson? | select(type == "object" and .kind == "Event")
        | select(.objectRef.namespace == "agent-target" and .objectRef.resource == "configmaps")

Known failures and their fixes​

Each entry below is something that actually happened in one of the course's own runs of this page, or in a learner walk of it, with the step it happened in named so you can compare it with your output.

Two results on this page are refusals on purpose and are not failures: the 403 from the create_configmap tool and the actor's direct-change=403. If either one comes back as a success instead, stop: the RBAC you applied is not the RBAC in m11/, and everything after it would prove the wrong thing.

The course ran this page twice from a fresh clone, every block in order from the image build to the teardown, and the lab's checks passed before the teardown both times. The first run hit the failure below, in the probe script itself. The script was fixed, and the second run, whose output this page shows, did not hit it. It is listed because it is what you will see if your clone is older than the fix.

The privileged-op row reads no, and a raw-socket cell starts with PING. Seen in the course's first run, at the two steps that run the probe script and build the matrix. The plain Pod's mount failed with mounting none on /mnt failed: No such file or directory, because the busybox image has no /mnt, while the sandboxed Pod's failed with permission denied. So the row compared a missing folder with a refusal, and showed a difference nobody had tested. The sandboxed Pod's raw-socket cell held ping's PING 127.0.0.1 banner instead of its error. The script now mounts onto a new empty folder it makes with mktemp -d, and skips the banner. If you see either one, your m11/probe-matrix.sh predates the fix: update your clone from the course's labs repository and run both probe steps again.

Three readings in both runs look like failures and are not.

Two steps end with a non-zero exit status. Seen in both of the course's runs, at the step that asks the authorizer about the tool server and at the step that creates the actor's identity. Each ends with a kubectl auth can-i whose answer is no, and can-i exits with status 1 when the answer is no. That no is the result the step is there to show.

The Sandbox's READY column is empty, or False with DependenciesNotReady, right after you create it. Seen in both of the course's runs, at the step that creates the namespaces and the Sandbox: the first run printed an empty READY, the second False and DependenciesNotReady, both in the read made straight after the create. The controller has not created the Pod yet. The next step waits for the Ready condition, and both runs reached it.

A Pod reads 0/1 and ContainerCreating. Seen in both of the course's runs, at the plain Pod, the tool client and the actor. Each of those steps reads the Pod straight after creating it and then waits for it, so the read comes before the container starts. The wait line after it is the one that matters.

If a step fails in a way the page does not describe, read the object that step reads, in the form the page reads it, before you re-run anything. A Sandbox that never becomes Ready says why in its conditions, and a Pod that never starts says why in its events.

Where you will use this​

The first time a team asks to run an agent that executes code it writes itself, you will ask which runtime its Pod gets, and you will check the answer by reading the kernel from inside the Pod rather than trusting a Running phase. When someone shows you a table of blocked capabilities as proof that a sandbox is safe, you will say the sentence from this lab and ask what was not tested. When a tool server is proposed for your cluster, you will read its ServiceAccount's RBAC with kubectl auth can-i before you read its tool list. And when an incident review asks who changed a tenant's setting, you will read the API server's audit log and tell the actor's refused attempt apart from the human's approved change.
