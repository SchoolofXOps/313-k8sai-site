Module 11 — Agents as a Workload Class

An agent is a program that decides its next action while it runs. It reads something, picks a tool, calls it, reads the answer, and picks again. Nobody wrote down the sequence ahead of time, and that is the whole point of it. For a platform engineer that changes one thing: the code inside the Pod is no longer code your team reviewed line by line, so the boundary around the Pod has to do work that code review used to do.

This module is about that boundary. It is not about building agents. You will put a workload under a second kernel, read the evidence that it is really there, give a tool server an identity that can only read, let a scripted actor propose a change it is not allowed to make, and read the whole exchange back from the API server's own audit log. Building and operating agents is the next course, 314.

  • Core path: ~2.0 h
  • Advanced brief: 0.5 h (labelled, optional)

Agents as a new workload class​

Think about the workloads you already run as three kinds of guest in a building. A web service is a tenant with a lease: it does the same few things every day, and you know which doors it uses. A batch job is a contractor: it arrives with a work order, does one job, and leaves. An agent is a guest who was handed a set of keys and told "sort it out". It will open doors you did not expect, in an order nobody planned, because the order is decided while it walks.

Three things follow from that, and they are what makes agents a workload class of their own rather than one more Deployment:

  1. The code path is decided at run time. An agent that runs a shell command, writes and executes a script, or calls a tool with arguments it made up is running code that did not exist when the image was built. The image scan you trust for a web service says nothing about it.
  2. The identity does the governing. Whatever the agent's ServiceAccount may do, the agent may do, at machine speed and without asking. The RBAC rules on that identity are the real policy, not the prompt.
  3. The blast radius is a design input. A web service that misbehaves fails in the ways its code allows. An agent fails in the ways its permissions allow, and that is a much larger set.

So the platform's questions are the old ones, asked harder: which kernel does this code talk to, who is it when it calls the API, where can its packets go, and who can prove afterwards what it did. Each of the next four sections answers one of them, and the lab answers each with evidence you read yourself.

The isolation decision for agent sandboxes​

A normal container shares the node's kernel. Namespaces and cgroups give it its own view of processes, files and memory, but every system call it makes lands in the same kernel every other Pod on the node uses. For code you reviewed, that is a fine trade. For code an agent wrote a minute ago, one kernel bug is the distance between the agent and everything else on the machine.

A sandboxed runtime puts something between the workload and the host kernel. Think of it as a hotel's front desk that takes every request from a guest and decides itself how to handle it, rather than handing the guest the master key to the building. Two common choices, and they put the front desk in different spots:

  • gVisor runs a userspace kernel, the sentry, written in Go. The workload's system calls go to the sentry, which implements them itself and makes only a small, filtered set of calls to the real host kernel. The runsc runtime is what containerd starts for it. No virtual machine is involved, so it runs nested inside a kind node container, which is how this course's lab runs it.
  • Kata Containers starts a lightweight virtual machine per Pod, with its own guest kernel. The boundary is the hypervisor. It needs hardware virtualisation on the node, which a laptop's container runtime VM usually does not pass through, so this course does not run it.

Neither is "the secure one". You choose against a declared threat model and a latency budget: which escapes you are defending against, how much per-sandbox memory you can afford, and how long a caller can wait for a sandbox to be ready. The lab measures the last one for gVisor, on your machine, and writes down the machine.

The Kubernetes half of the decision is small, and it is the same for both. A RuntimeClass is a cluster-scoped name with a handler. A Pod asks for it with spec.runtimeClassName. The kubelet passes the handler to containerd, which looks it up in its own configuration and starts the Pod with that runtime. The choice is per Pod, so one node can run a sandboxed Pod beside a kube-proxy Pod on the default runtime. The lab shows exactly that.

There is one trap here, and it is the most important sentence on this page. The trap is not a missing handler, because that failure is loud. If the RuntimeClass object does not exist, the API server refuses the Pod the moment you create it. If the object exists but its handler is missing from the node's containerd configuration, the Pod is scheduled and then never starts. It waits in ContainerCreating, and its events keep repeating no runtime for "runsc" is configured. Nothing falls back to the default runtime. The quiet failure is the Pod that never asked. A Pod with no runtimeClassName gets the node's default runtime and reports Running, exactly as it would have under gVisor. Think of a hotel guest who forgot to ask for the room with the extra lock. Nobody refuses them. They simply get an ordinary room, and from the corridor every door looks the same. So a template that lost that one field looks, from outside, exactly like success. The only evidence that a workload is sandboxed is read from inside it: the kernel identity in /proc/version. Under gVisor it reads Linux version 4.19.0-gvisor, because that is the kernel the sentry implements, whatever the host runs. The course proved that path on both CPU architectures before writing this module, reading that string from inside a Pod on an Apple Silicon laptop and on an amd64 CI runner. The node image the lab builds pins gVisor release-20260928.0.

The sandbox object. Agent Sandbox, a kubernetes-sigs project, adds one custom resource, Sandbox, and a controller that turns each one into exactly one Pod from the object's spec.podTemplate. Because that template is a real PodSpec, it carries runtimeClassName, and that one field is where the two halves meet: the Sandbox API does not know gVisor exists, and gVisor does not know Agent Sandbox exists. The platform engineer joins them. The object adds what a bare Pod lacks for this job: a stable identity for one long-lived, stateful workload, a Ready condition, and a lifecycle with shutdownTime and shutdownPolicy so an idle sandbox is reaped on schedule.

This course installs the Sandbox CRD at agents.x-k8s.io/v1beta1 from release v1.0.5, using that release's sandbox.yaml asset, which holds the controller and the one CRD and nothing else. v1alpha1 was removed at v1.0.0, together with its conversion webhooks, so a manifest copied from a 2025 example is rejected outright, not converted. The claim, template and warm-pool kinds live in a separate group, extensions.agents.x-k8s.io/v1beta1, and ship as a separate asset. The project moves fast. Five more releases followed the pin, v1.0.6 to v1.0.10, the last on 2026-11-06, as read on 2026-11-10. The course stays on the version every measurement in this module was taken at.

The client libraries and services that sit above the sandbox are a different layer, with a different owner:

The Agent Sandbox SDKs, sandbox-router and sandboxd are the scope of course 314.

Warm pools. A cold sandbox has to be scheduled, have its image pulled, and have its runtime start before it is Ready. A warm pool keeps a number of sandboxes created and ready ahead of demand, the way a taxi rank keeps cars waiting at the station so a passenger does not wait for one to be called. A SandboxWarmPool names a SandboxTemplate and a replica count, and a SandboxClaim takes one ready sandbox out of the pool, which the pool then replaces. All three kinds are in the extensions group. In this course you read a warm-pool manifest and do not apply it. Two reasons: the extensions asset is outside the install fence this module draws, and the memory gVisor adds per sandbox has not been measured here, so the runsc RuntimeClass carries no overhead.podFixed and the scheduler would not account for a pool of five. The pool waits until that number exists.

Tool servers as infrastructure​

An agent does not call the Kubernetes API directly in most designs. It calls tools, and a tool server exposes them. The Model Context Protocol (MCP) is the common contract for that: a JSON-RPC interface where a client asks a server tools/list, gets back names and argument schemas, and then calls tools/call with a name and arguments.

Here is the part that matters to a platform engineer. A tool server is a workload with an identity. When its list_pods tool runs, the request reaches the API server carrying the tool server's ServiceAccount token, and RBAC decides it. Not the tool's description, not the model, not the prompt. A tool named create_configmap on a server whose identity holds only get and list is a tool that will always be refused, and the API server, not the tool, does the refusing.

So treat a tool server the way you treat any shared service with credentials:

  • One identity per server, least privilege on it. The lab's server runs as mcp-reader, a ServiceAccount granted get and list on pods and configmaps in one namespace, through a Role and a RoleBinding in that namespace.
  • Ask the authorizer, not the code. kubectl auth can-i create configmaps -n agent-target --as=system:serviceaccount:agent-mcp:mcp-reader answers from the same RBAC rules the API server applies. Read it before you trust any claim about what a tool can do.
  • The caller holds nothing. The lab's client Pod has no Kubernetes credential mounted at all. Whatever it achieves, it achieves through the server's identity, which is exactly what you want to be able to audit.

Governance for an actor that improvises​

The pattern this section teaches has six steps, and the platform's job is to put a boundary in the middle of them:

Detect, diagnose and propose belong to the actor. Approve and execute belong to a human, or to a process a human signed off. Verify belongs to everyone. The boundary is drawn in RBAC: the actor's ServiceAccount can read the target and can create proposal objects in its own namespace, and it holds no write verb on the target at all. If it tries to change the target directly, the API server refuses it with a 403, and the refusal is recorded. The change reaches the cluster only when a person with that authority reads the proposal and applies it under their own name.

Picture a junior engineer on their first week. They can read every dashboard and write a change request, but they cannot merge to production. Nobody thinks that is an insult; it is how the team stays safe while the junior learns. The actor gets the same deal, for the same reason, and unlike the junior it will not get bored of filing requests.

The lab's actor is a fixed script, not an agent, on purpose. A model's behaviour varies from run to run, and what this module teaches is the boundary, which must hold whatever the actor does. A script that always tries the forbidden change gives you a refusal to read every time.

Who did it. The API server's audit log is the record that settles it. Each audited request produces an event with the authenticated user, the verb, the object and the response code. In the lab you read two refusals, each attributed to a ServiceAccount, and one applied change attributed to your own user, the name kubectl auth whoami prints. That last point is the one to hold on to: approval only means something if the log can tell the approver apart from the actor.

Workload identity beyond the API server. An actor that calls services outside the cluster needs an identity those services can check, and a bearer token is a poor fit for that. This is where certificates come in:

Pod Certificates and ClusterTrustBundle are GA in Kubernetes 1.37.

A PodCertificateRequest lets the kubelet obtain an X.509 certificate for a Pod from a named signer and project it into the Pod, rotating it before it expires, so a workload can prove who it is over mutual TLS without a long-lived secret. A ClusterTrustBundle publishes a set of CA certificates as a cluster-scoped object, so every Pod can be given the roots it should trust. The projected-volume source that writes such a bundle into a Pod is GA in 1.37 as well.

The history is worth knowing, because it is the trap this course keeps teaching. The two bundle gates were beta from 1.33 with defaultValue: false through 1.36: beta, and off in every cluster that did not switch them on. 1.37 is the release where they became usable without a flag. PodCertificateRequest moved faster: alpha in 1.34, beta in 1.35 and 1.36, stable in 1.37.

One more fact decides what the lab can do. A pod certificate is issued by a signer, and Kubernetes 1.37 ships no built-in signer that issues them. The one well-known signer name the API documents, kubernetes.io/kube-apiserver-client-pod, is described there as currently unimplemented. So on a stock cluster a PodCertificateRequest waits with nobody to answer it. The lab shows both APIs served and does not run issuance; the deep dive projects an administrator's ClusterTrustBundle into a Pod, which needs no signer.

The autonomy policy, and where this course stops​

Not every action needs a human. Reading cluster state is harmless and constant; asking a person to approve each read would make the actor useless and the person numb. Deleting a namespace is the opposite. The useful question for each class of action is not "is it allowed?" but two narrower ones: can it be undone, and how far does it reach if it goes wrong.

The lab writes those answers down as the platform's autonomy policy, one row per action class, with one of three decisions:

  • autonomous: the actor may do it under its own identity. Reversible, small reach. Reading state; restarting one Pod of the actor's own workload.
  • approval-gated: the actor proposes, a human applies. Reversible but with reach beyond the actor: changing a tenant's ConfigMap, scaling a tenant's Deployment.
  • never delegated: no actor identity holds the verb at all. Hard to undo or wide in reach: changing RBAC, deleting a namespace, rotating a credential.

The policy is only real where RBAC enforces it. An approval-gated row means the actor's Role lacks the verb; a never delegated row means no agent identity anywhere holds it. A policy document that the RBAC rules contradict is a wish, and the audit log is how you find out.

That is where this course stops. Hosting agents safely is this module: the runtime boundary, the identity, the egress decision, the audit trail and the policy. Building agents, wiring them to models, the SDKs that start sandboxes and send traffic to them, and running them as a product are course 314.

Read the table from top to bottom and you have the module. The controller decides that a sandbox exists, the RuntimeClass and runsc decide which kernel it talks to, RBAC decides what its identity may ask for, NetworkPolicy decides where its packets may go, and the audit log is how you prove any of it afterwards. None of them knows about the others, and that is why each one has to be checked on its own.
