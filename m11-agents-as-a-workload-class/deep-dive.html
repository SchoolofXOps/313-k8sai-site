Deep Dive — How a Sandbox Is Assembled: the runsc Handler, Sentry and Gofer, Ownership, Reaping and Trust Bundles

The lab showed that a Sandbox becomes a Pod, that the Pod talks to gVisor's kernel, and that the cluster serves the trust-bundle API. This page takes the same objects apart one layer down. You read the line in the node's containerd configuration that the runsc RuntimeClass resolves to, and you find the two gVisor processes that stand behind one sandboxed Pod. You read the ownership link that lets the controller clean up after a Sandbox. You watch a Sandbox delete itself at a time you set. And you give a Pod a set of CA certificates through a ClusterTrustBundle, with no signer anywhere. You will use these layers when a sandboxed Pod starts but you are not sure what it started under, when sandboxes pile up and nobody knows who should delete them, and when workloads need to trust a private CA without a Secret copied into every namespace.

Where this picks up

This page runs on grid-sandbox with the Agent Sandbox controller installed and probe-sandbox running in agent-probes. If they are still up from the lab, this block finds them and changes nothing. If you tore them down, or never did the lab, it creates exactly what is needed. It calls the profile scripts directly, so it works without the lab's wrappers. Run it from the root of your clone.

The error: line under ==> waiting for the Sandbox CRD to be Established is not a failure. kubectl wait read the new CRD a moment before the API server wrote its first status condition, and in that case it does not wait: it fails at once. install.sh knows this one error. It says so on the next line, asks again 2 seconds later, and the second wait finds the CRD Established. Any other error, or ten of these in a row, stops the script with a FAIL: line and a command to inspect the CRD. It does not happen on every install, so you may not see those two lines at all; it happened in several of the course's own runs, including the one this output comes from. After the wait, the script waits for the controller and prints its summary. Its last line, next:, names a path as the course's source repository lays it out, under labs/; in your clone that path has no labs/ in front, and this page's next block is your next step.

Everything on this page lives in agent-probes, apart from the trust bundle, which is cluster-scoped by design.

Here is the chain this page walks, from the object you write to the processes that run your code:

The runsc handler and the sentry and gofer, seen from the node​

A RuntimeClass is only a name. The thing it names lives in the node's containerd configuration, which the node image wrote at build time. You can read that file, and the processes it leads to, from a debug Pod on the node. kubectl debug node/... with --profile=general starts a Pod in the node's process, network and IPC namespaces, with the node's root filesystem mounted at /host, so you see what the node sees without logging into it.

First, which node runs the Sandbox's Pod:

NODE=$(kubectl --context kind-grid-sandbox -n agent-probes get sandbox probe-sandbox -o jsonpath='{.status.nodeName}')
echo "node=${NODE}"

[ Expected output ]

node=grid-sandbox-worker

Then the handler stanza in that node's containerd configuration, and every process whose command line names runsc. The debug Pod runs one shell command and exits.

Do not attach to the debug Pod with -i. Attaching races the command. In the course's first run of this page, the shell finished before the attach connected, and the block printed nothing at all, with no error. So start the Pod without attaching, keep the name kubectl debug prints for it, wait until the Pod has finished, and then read its logs. The logs hold everything the command printed, every time. The last line reads the ID of the sandboxed Pod's own container, so you can find it in the process list.

The two grep patterns are written so that neither matches the debug Pod's own shell. Its command line is in the process list too, and a plain runtimes.runsc in it would put it there as a runsc process.

DEBUG_POD=$(kubectl --context kind-grid-sandbox -n agent-probes debug "node/${NODE}" --profile=general \
  --image=docker.io/library/busybox@sha256:bdf57e528e45e4433820e045b29b4597825a1c9e38353532d90a01445013f82e \
  -- sh -c 'grep -n -A2 "runtimes\.[r]unsc" /host/etc/containerd/config.toml; echo ---; ps -o pid,ppid,args | grep "[r]unsc"' \
  | sed -n 's/^Creating debugging pod \([^ ]*\) .*/\1/p')
echo "debug pod: ${DEBUG_POD}"
kubectl --context kind-grid-sandbox -n agent-probes wait --for=jsonpath='{.status.phase}'=Succeeded pod/"${DEBUG_POD}" --timeout=120s
kubectl --context kind-grid-sandbox -n agent-probes logs "${DEBUG_POD}"
kubectl --context kind-grid-sandbox -n agent-probes get pod probe-sandbox -o jsonpath='{.status.containerStatuses[0].containerID}{"\n"}'

Read the first half. The stanza name after runtimes. is the handler, runsc, and it is the string the RuntimeClass object's handler field must match, character for character. Its runtime_type names the containerd shim, io.containerd.runsc.v1. If those two names did not match, containerd would have no runtime to start for that handler, and the Pod would not run under runsc at all. This file shows what the node is set up to do, not what a given Pod got, and a Running phase does not name the runtime either. That is why the lab read the kernel from inside the Pod rather than trusting either this file or the phase.

Read the second half, and match each process to its parent in the second column. One sandboxed Pod is several runsc processes, not one. There are two containerd-shim-runsc-v1 processes, each with its own -id. The ID the last line printed after containerd:// is the second shim's: that shim belongs to the Pod's agent container. Under the first shim are the sentry, the line that starts {gvisor_sentry} runsc-sandbox and has boot in its arguments, and a gofer, runsc-gofer with gofer in its arguments. The sentry's arguments also name the Pod's own log directory, agent-probes_probe-sandbox_ and the Pod's UID. Under the second shim there is a second gofer and no second sentry: one sentry serves the whole Pod. The sentry is the userspace kernel. It handles the workload's system calls itself and makes only a limited set of calls to the host kernel, under a filter. The gofer is a separate process that serves what the sentry cannot serve from inside that filter, file access among it. The other runsc lines, runsc-fd-parking and runsc … wait, are helpers this page does not take apart. So the "front desk" from the lesson is not one process: the part that answers the workload and the part that touches the host's files are separate.

The controller's owned objects​

The controller did not just create probe-sandbox's Pod; it recorded that it owns it. The Pod's ownerReferences names the Sandbox, with controller: true. That one field is what Kubernetes garbage collection follows: when the owner goes, the owned object goes with it.

kubectl --context kind-grid-sandbox -n agent-probes get pod probe-sandbox \
  -o jsonpath='{range .metadata.ownerReferences[*]}{.apiVersion} {.kind} {.name} controller={.controller}{"\n"}{end}uid={.metadata.uid}{"\n"}'

[ Expected output ]

agents.x-k8s.io/v1beta1 Sandbox probe-sandbox controller=true
uid=9afc804b-fdb0-47ca-bc8e-7ef5ea3b5221

Idle reaping, observed live​

An agent session that is abandoned leaves a sandbox running, holding memory and a runtime. The Sandbox API has two fields for that, read from the v1.0.5 CRD schema: spec.shutdownTime, an instant, and spec.shutdownPolicy, Retain (the default) or Delete. With Delete the controller deletes the Sandbox object when that time passes, and its Pod goes with it through the owner reference you read above. Retain, the default, keeps the object; the v1.0.5 schema carries no field descriptions, so read what Retain does to the Pod on your own cluster before you build on it. This page runs Delete.

Create reap-demo with a shutdown time about two minutes ahead and shutdownPolicy: Delete. jq computes the time, so the command works the same on macOS and Linux:

T=$(jq -nr 'now + 120 | todate')
echo "shutdownTime=${T}"
sed "s/2000-01-01T00:00:00Z/${T}/" m11/dd-reap-demo.yaml | kubectl --context kind-grid-sandbox apply -f -
kubectl --context kind-grid-sandbox -n agent-probes get sandbox reap-demo -o jsonpath='{.metadata.name} shutdownTime={.spec.shutdownTime} shutdownPolicy={.spec.shutdownPolicy}{"\n"}'
kubectl --context kind-grid-sandbox -n agent-probes wait --for=condition=Ready sandbox/reap-demo --timeout=300s

The Pod can lag behind it by a moment: if the Pod get prints reap-demo as Terminating, its container is still being stopped. The second wait returns once the Pod is gone too, and if the Pod was already gone it returns at once and prints nothing. The events are what is left of the Pod's short life. Reaping by a time set at creation is the simplest policy; it does not know whether the session was busy. A platform that wants "reap after ten idle minutes" has to move shutdownTime forward while the session is active, and that is a job for the layer above the sandbox.

A ClusterTrustBundle projected with no signer​

Pod Certificates need a signer, and none ships with Kubernetes 1.37. The other half of the feature does not. A ClusterTrustBundle with no signerName is a set of CA certificates an administrator publishes, and the clusterTrustBundle projected-volume source writes it into any Pod that asks, kept in step with the object by the kubelet. Both are GA in 1.37. This is how a workload learns which private CA to trust without a Secret copied into its namespace.

m11/dd-cluster-trust-bundle.yaml holds the bundle, carrying one throwaway CA certificate generated for this lab whose private key was deleted when it was made, and the Pod ctb-reader that mounts it. Apply it and assert both objects exist:

kubectl --context kind-grid-sandbox apply -f m11/dd-cluster-trust-bundle.yaml
kubectl --context kind-grid-sandbox get clustertrustbundle m11-demo-bundle -o jsonpath='{.metadata.name} signerName={.spec.signerName}{"\n"}'
kubectl --context kind-grid-sandbox -n agent-probes get pod ctb-reader
kubectl --context kind-grid-sandbox -n agent-probes wait --for=condition=Ready pod/ctb-reader --timeout=300s

[ Expected output ]

pod/ctb-reader created
m11-demo-bundle signerName=
NAME         READY   STATUS              RESTARTS   AGE
ctb-reader   0/1     ContainerCreating   0          0s

signerName= is empty on purpose. Read the bundle back from inside the Pod, and compare it with the object:

kubectl --context kind-grid-sandbox -n agent-probes exec ctb-reader -- sh -c 'ls -l /var/run/ctb/; grep -c "BEGIN CERTIFICATE" /var/run/ctb/bundle.pem; head -n 1 /var/run/ctb/bundle.pem'
kubectl --context kind-grid-sandbox get clustertrustbundle m11-demo-bundle -o jsonpath='{.spec.trustBundle}' | grep -c "BEGIN CERTIFICATE"

[ Expected output ]

lrwxrwxrwx    1 root     root            17 Nov 13 04:59 bundle.pem -> ..data/bundle.pem
1
-----BEGIN CERTIFICATE-----
1

One certificate in the object, one in the file. Nobody signed anything, nothing was issued, and the Pod still received exactly what the administrator published. When a signer does exist on your cluster, it publishes its own roots the same way, with its signerName set, and Pods select bundles by that name instead of by object name.

Where you will use this​

Where you will use this
  • A RuntimeClass resolves to a handler stanza in the node's containerd configuration, and nothing checks the match for you. Use it when: a team reports that their sandboxed Pods "work" on a new node pool. Read the handler stanza on one node, then read the kernel from inside one Pod, before you believe it.
  • One sandboxed Pod runs one sentry, with a shim and a gofer per container ID: two of each for probe-sandbox, which declares one container. Use it when: you size nodes for sandboxed workloads, or a sandboxed Pod is slow on file-heavy work. The extra processes are the memory you account for, and file access crossing to the gofer is where the cost shows up.
  • The controller owns the Pod through ownerReferences, so deleting the Sandbox cleans up, and a recreated Sandbox gets a new Pod UID. Use it when: you build anything that tracks sandbox sessions, or you clean up after an agent platform. Delete the owner, not the Pod, and key sessions by Sandbox name.
  • shutdownTime and shutdownPolicy reap a sandbox at a set time. Use it when: abandoned agent sessions are holding node memory. Set a shutdown time at creation with Delete when nothing needs the object afterwards, and test Retain on your own cluster before you rely on what it keeps.
  • A ClusterTrustBundle with no signer gives every Pod the same CA set without a Secret per namespace. Use it when: workloads must trust a private CA, for example an internal model registry or tool server, and you are tired of copying a CA Secret into every new namespace.
