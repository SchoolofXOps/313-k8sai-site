Deep Dive — Checkpoint Storms on a Shared Claim and the Evidence Order for a Slowdown

The lab timed four storage paths one at a time, which is the right way to compare paths and the wrong way to see what a training gang does to shared storage. A gang does not write one checkpoint; every worker writes its own at the same moment, into the same shared volume. This page puts several writers on the lab's one shared NFS claim at once, beside a single writer on its own, records the result with its configuration, and puts the lesson's restart-cost formula to work on your own record. Then it hands you a synthetic evidence bundle from a slow eight-accelerator job and asks you to read it in the order the lesson taught, rule each layer in or out, and name the root cause. You will use these the day a checkpoint directory slows every tenant on the cluster, and the day an incident channel fills up with theories about why eight accelerators are slower than four.

Where this picks up

This page runs on grid-core with the storage layer applied and nothing else. The block below gets you there from any state. If the lab's NIC and device layers are still up, it removes them first, through your lab wrappers, NIC layer first. If there is no cluster, it creates one, and if the storage layer is not applied, it applies it. Every step converges, so re-running the block is safe. Run it from the root of your clone.

The layer's verify ends with two SCOPE LIMIT lines, exactly as in the lab. They state what the course's own storage runs found, and they say nothing about your cluster. The block keeps the verify's whole output in a shell variable, prints the verify's own exit code, and then prints everything except those two lines.

The page never relies on a lab object surviving. It needs the cluster and the storage layer's namespace, spike-02, with its shared claim and its probe, and it writes only under grid-platform/dataplane-storage/measurements/checkpoint-storm-* and grid-platform/dataplane-storage/diagnosis/.

The checkpoint storm​

Several writers on one shared claim​

Imagine one photocopier in an office. One person copying a long report gets the machine's full speed. Now the whole team of eight arrives at five o'clock, each with their own report, because the deadline is the same for everyone. Nobody's report takes longer to print in theory, but everyone waits for the machine, and the person who only wanted one page waits too. A checkpoint storm is that five o'clock queue: every worker of a gang writes at the same moment, into the same shared storage, and the shared server is the photocopier.

Here is what the script does, and where each write goes:

Three writers mount the same ReadWriteMany claim, spike02-nfs-rwx, and the kubelet on the worker mounts it through the kernel's NFS client. The script then runs the harness's own probe in three rounds. First each writer writes once on its own, one after another: the warm-up. Then all three write at the same moment. Then one of them writes once more alone. Every byte goes through one NFS server Pod into one claim on one disk. The probe is the same program that produced the lab's table, read from the harness's own ConfigMap, so the storm is timed exactly the way the four paths were. The script sizes each writer the way the harness sizes its clients and records that formula next to the figures.

Why the warm-up? Think of the office coffee machine first thing in the morning. The first cup after it is switched on takes far longer than the second, and that has nothing to do with how many people are queueing. The lab showed you the same thing on this path: a freshly started NFS server holds back every new open for its first 90 seconds, its grace period, so the first write after it starts waits far longer than any write after it. The block above applied the storage layer moments ago, which started that server, so without a warm-up the three writers at once would also be starting inside that window, and you could not tell how much of their slowness came from sharing the server and how much from arriving early. So every writer writes once alone before the storm. The script records those warm-up rows rather than hiding them, and keeps them out of the comparison: the concurrent rows and the single row both run on a volume every writer has already written to, so they differ in one thing only, how many writers write at once.

The record must also say what else was running on this machine, because other containers share the VM's memory and disk with the storm. A description typed in before the run can be wrong by the end of it: on the course's first run of this page, a container from another project stopped while the storm was running. So the block sets OTHER_CONTAINERS=count, and the script counts the containers on your machine that are not this cluster's own nodes, once when the storm starts and once when it ends, and writes both numbers into the record. It records no names. If you would rather describe them in words, set OTHER_CONTAINERS to that description, or to none, and the script records it as you gave it.

OTHER_CONTAINERS=count bash m6/checkpoint-storm.sh

What you can read is a comparison inside one record: what each writer got while three wrote at once, against what one writer got on its own, on the same claim, minutes apart, both after the warm-up. Here is what the same record said on the course's run of this page. The volume's first write, storm-writer-0's warm-up, took 90.77 s (conditions: an Apple M1 Pro host running a Rancher Desktop VM, kernel 6.18.36-0-virt, 5 CPUs; Kubernetes v1.37.0 on kind v0.33.0 at the 8 GB size; six containers from other projects sharing the VM, counted by the script when the storm started and when it ended; one writer, 128 mebibytes written and flushed by the four-path harness's probe onto the shared claim spike02-nfs-rwx; storm run 20261118T131428Z, the first warm-up row, whose rate column divides the payload by that time). That time is almost all waiting: the write started moments after block 1 had started the NFS server, inside its grace period, and the probe the lab describes showed a first write in that window takes about the same time whether it carries 16 mebibytes or 256. The other two writers' warm-ups, each their first write through their own mount, ran at 128.5 and 85.9 MiB/s (conditions: the same run, the same claim, one writer at a time, right after the first). So on that run the wait was paid once, by the first write after the server started, and not again by each writer's mount, because by the time the other two wrote the window had closed. After the warm-up, the three writers at once got 67.7, 68.6 and 68.8 MiB/s (conditions: the same run, three writers on the one claim at the same moment, 128 mebibytes each, one figure per writer), and storm-writer-0 alone got 535 MiB/s (conditions: the same run, one writer, right after the burst), about 7.8 times what each concurrent writer got. Three writers together moved less than one writer alone, so on that run sharing the server did more than split it three ways. The configuration those figures were taken under is the record itself, its knobs table and the probe beside it, in grid-platform/dataplane-storage/measurements/checkpoint-storm-20261118T131428Z/, the same place your own run put yours. None of the figures is disk performance; all of them belong to that machine, that VM and that run.

The restart-cost formula, applied to your record​

The lesson derived the checkpoint interval that wastes the least time:

τ* = √(2 δ M)

Here δ is the time one checkpoint stalls the job, and M is the mean time between failures. The formula's δ is the time for the whole gang's checkpoint, not for one worker writing alone. That is the point the storm makes concrete. Suppose your record shows each concurrent writer getting about a k-th of what the single writer got. Then a gang's checkpoint, all workers writing at once, takes roughly k times as long as one worker's test suggested, so δ is k times larger than a single-writer benchmark would tell you. Put that into the formula, and the right interval τ* grows by the square root of k: checkpoint less often, because each one costs more. The overhead per hour, δ / τ*, grows by the square root of k as well.

Try it on the course's record above. There k was about 7.8, with three writers, so the gang's δ was about 7.8 times what the single-writer row suggested, and τ* grows by the square root of 7.8, about 2.8 times: checkpoint less than half as often as the single-writer test would have told you. Your own record will give your own k, and that is the one to use.

So the platform team has two levers, and the record helps choose between them. Make δ smaller for the gang: asynchronous checkpoints that copy to host memory and write in the background, sharded checkpoints where each worker writes only its slice, or a storage tier that holds up under many writers at once. Or accept a longer interval and the larger loss per failure that comes with it. Whichever you choose, compute it from your own k, recorded on your own platform with its configuration beside it, not from a figure on someone else's slide.

The evidence order for a distributed slowdown​

The bundle​

A synthetic evidence bundle

Every file in m6/slowdown-evidence/ was written by the course, and its first line says so. No device, NIC or fabric produced any line of it. The node names, device names, addresses and figures are invented, in the formats the real tools print, so that you can practise reading evidence in order. Nothing here is a measurement.

The scenario: a training job runs on four accelerators on one node at a good pace. The team scales it to eight accelerators across two nodes, with the same global batch, and every step gets slower, not faster. You have six files, one per step of the lesson's evidence order. Read them in that order and do not skip ahead, because the point is to rule each layer in or out before you look at the next one.

If you found the cause, you will notice it connects straight back to the lab's network half. A claim that names a NIC beside the accelerators, with a matchAttribute on their PCIe root, is exactly the platform object that stops this class of incident before the job starts. On real hardware it is the request that would have put the fast NIC into the container in the first place; in this course it is the object-level selection the lab showed and nothing more.

Where you will use this​

Where you will use this
  • A gang's checkpoint is many writers at once, and shared storage serves them all through one path. Use it when: a team asks for "faster checkpoint storage". Warm the volume with one write from each writer first, then run several writers at once against one writer on the volume they will actually use, record both beside the configuration, and size the request from the concurrent figure, not the single one.
  • The restart-cost formula takes the gang's write time, not one writer's. Use it when: someone sets the checkpoint interval from a single-node test. Ask for the concurrent write time, put it into √(2 δ M), and show the interval and the overhead per hour that follow.
  • A slowdown is read from the device outward, one layer at a time. Use it when: eight accelerators are slower than four and the incident channel has five theories. Read device telemetry, then data-loader timing, then the collective library's transport line, then the interface and RDMA counters, then the topology, and rule each one in or out before you move on.
  • An idle accelerator with no errors is waiting for something. Use it when: a dashboard shows low utilisation and someone wants to replace the hardware. Read the step-time breakdown before anything else.
  • A claim that names the NIC beside the accelerator is the platform's fix for the wrong-interface incident. Use it when: a distributed job's collective library falls back to sockets on the ordinary interface. Look at what the job's claim asked for, and whether anything tied a fast NIC to the accelerators' PCIe root.
