Lab — Four Storage Paths, One Invocation, and a Device-and-NIC Claim

Lab Truth Contract — SIMULATED

The storage half runs on a real kind cluster with real protocols: S3 over HTTP, NFS, a local-path claim and a hostPath bind mount, all timed by one probe. It is scope-limited by three fences recorded on the course's own runs: no pvc-versus-hostpath claim, no ranking of nfs against s3 on write, and no figure presented as disk performance. The device and the NIC in the network half are synthetic, published by two releases of the upstream example driver. There is no accelerator and no network card anywhere in this lab, and the claim shows object-level selection only.

In this lab you take the grid-core cluster and give it two things a training job depends on and nobody sees: a data path and a network path. First you put four storage paths side by side and time all four with one probe in one go, and then you write down, in your own words, what that run can and cannot tell apart. Then you clear the storage away, add a synthetic NIC beside Module 4's synthetic device, and ask the scheduler for one of each, under one PCIe root, in a single claim. Every part ends with something you read from the cluster's own objects or from a record the run wrote: a claim's allocation, a slice's attribute, an event, a namespace that is gone, a file with its configuration beside it. You never read a result from a Pod's phase alone.

Think of this lab as a delivery company's test day. In the morning you send the same parcel by four different routes and write down how long each took, along with the weather and the traffic, because a delivery time with no conditions beside it is useless. In the afternoon you book a lorry and a driver who live in the same town, in one booking, so they can start together, and then you try a booking where they live in different towns and watch it fail. The morning is the storage half; the afternoon is the network half.

Run every command from the root of your clone of the labs repository, as in the earlier modules. If you open a second terminal, export KUBECONFIG there again, and set OUT again as the part that measures describes.

Where the platform stands​

Think of where the platform is as a building with a fair booking desk, and nobody yet checking the corridors.

After Module 5 the platform can hold three tenants to a fair share of quota, admit a group of Pods whole or not at all, and keep a group inside one topology block. The cluster is torn down, and your repository holds the capacity layer under grid-platform/capacity/ and the synthetic-device wrappers under grid-platform/clusters/addon-dra/ from Module 4.

What is still broken: nothing says whether the data reaching an accelerator, or the network between two of them, starves the fair pool you built. When you finish, the platform has a timed record of four storage paths with its configuration beside it, a written conclusion that stays inside what the run can tell apart, and a claim template that asks for a device and a NIC together. Your repository fills grid-platform/dataplane-storage/. Module 7 runs the first coordinated training job on top of it, and its checkpoints land on the shared path you time here.

Measure four paths in one invocation​

Now the timing, and one detail decides whether it is worth anything. A freshly started NFS server makes the first file anyone opens on it wait. For its first 90 seconds (the Grace_Period = 90 in the server's own configuration) it is in what NFS calls its grace period: a window in which clients that held files before a restart may reclaim them, and every new open is held back. Think of a shop that unlocks its doors but, for the first minute and a half, serves only people collecting orders they placed before it closed. That wait is part of what this run should see, because a training job meets it too. If you let the layer sit and then time it, the window has already closed, out of sight. So the next block removes the layer's namespace and, in the same breath, lets the harness provision all four paths from nothing and time them in one process. Run it as one block, with no pause in between.

Two names appear in it, and they are not the same thing:

  • MEASURE_ID is the name you choose for the directory, a timestamp, so each run lands in its own folder under grid-platform/dataplane-storage/measurements/.
  • The harness's own RUN_ID is generated inside the harness and cannot be set from outside. It names the files it writes into that folder, table-<RUN_ID>.md and results-<RUN_ID>.jsonl, and it is the Run id: line in harness-config.md.

Both redirections on the last line matter. Without CONFIG_OUT, the harness rewrites its own committed storage/four-path/harness-config.md and dirties your clone. Without RESULTS_DIR, the results land in /tmp, outside your repository. With both, the figures and the configuration that produced them land in one directory.

You type no docker command here. The harness itself runs docker inspect, docker exec and, where it is present, rdctl to describe the node, the disk and the NFS module in harness-config.md. The whole block takes several minutes: four paths, two repetitions each, one at a time.

MEASURE_ID="$(date -u +%Y%m%dT%H%M%SZ)"
OUT="${PWD}/grid-platform/dataplane-storage/measurements/${MEASURE_ID}"
mkdir -p "${OUT}"
bash storage/four-path/run.sh teardown
CONFIG_OUT="${OUT}/harness-config.md" RESULTS_DIR="${OUT}" bash storage/four-path/run.sh

Now read it the way this course reads every storage figure, against three fences. Each one came out of the course's own runs on the course's build machine, and each one binds what you may write about your own table.

  1. The two local paths, pvc and hostpath, are not compared. On kind, the local-path provisioner's directory is a bind mount on the node, so both paths reach the same kind of storage by two routes. Their figures can land close together or far apart, and which one is ahead can change between write and read or from one repetition to the next. That is not a difference to explain; it is the result. This harness cannot tell these two apart on this machine.
  2. nfs and s3 are not ranked against each other on write. Their difference on the course's runs sat inside the spread the runs set for themselves.
  3. No figure here is disk performance. Your cluster runs inside a VM, and the host's page cache sits under the VM's disk where nothing in the guest can evict it. Every figure is for this machine, this VM and this run, and it means nothing without harness-config.md beside it.

One claim, a device and a NIC under one PCIe root​

Here is the claim template. Two requests, one to each driver's class, and one constraint: whatever the scheduler picks for the two requests must have the same value for resource.kubernetes.io/pcieRoot.

apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: accel-and-nic-one-root
spec:
  spec:
    devices:
      requests:
      - name: accelerator
        exactly:
          deviceClassName: sim-accelerator.example.com
      - name: nic
        exactly:
          deviceClassName: sim-nic.example.com
      constraints:
      - matchAttribute: "resource.kubernetes.io/pcieRoot"

The template has no namespace on purpose, so the same file can be committed to your platform and applied by any tenant into its own namespace. The Pod, accel-and-nic, takes one claim from it, prints its environment and sleeps.

This claim does not go through a Kueue queue, and that is deliberate. At the Kueue version this course pins, Kueue does not account a claim's constraints, so routing this Pod through a LocalQueue would hand Kueue a claim it cannot read correctly.

Known failures and their fixes​

Every entry here is something a real run of this page printed. Each one names the step, what you will see, and what to do.

  • The storage layer's apply waits for minutes on 0 of 1 updated replicas are available. Step: applying the storage layer. What you see: Waiting for deployment "s3-server" rollout to finish: 0 of 1 updated replicas are available..., and the same line for nfs-provisioner and client-nfs, with nothing else for several minutes. On the course's second run the block took about nine and a half minutes. If you look from a second terminal meanwhile, client-nfs is Pending with the event pod has unbound immediate PersistentVolumeClaims, the claim spike02-nfs-rwx is Pending with Waiting for a volume to be created … by the external provisioner 'spike02.lab/nfs', and s3-server may show Readiness probe failed: … connection refused once. Why: the first apply pulls three images, and the shared claim cannot be provisioned until the NFS server Pod, whose image is the slowest to pull, is running; its client waits for the claim. What to do: nothing. Let the block finish. It ends with the OK: addon-dataplane applied line on its own once the pulls complete. Re-running it in the middle only restarts the wait.
  • warning: refs/tags/v0.5.0 … is not a commit! when a device layer goes on. Step: applying the device layer and the NIC layer. What you see: that line right after ==> cloning https://github.com/kubernetes-sigs/dra-example-driver.git at v0.5.0. Why: it is git's own message for an annotated tag, which points at a tag object rather than straight at a commit. What to do: nothing. The layer goes on to print its OK: line, as the output in those steps shows.
  • The split-roots event also says 1 node(s) had untolerated taint(s). Step: the constraint no pair can satisfy. What you see: 0/2 nodes are available: 1 cannot allocate all claims, 1 node(s) had untolerated taint(s). Why: the second node is the control plane, which carries a taint ordinary Pods do not tolerate. The node that matters is the worker, the one that has the devices, and it is the one that cannot allocate all claims. What to do: nothing; this is the failure the step sets out to show.

If a step fails in a way this list does not describe, read the object that step reads, in the form the page reads it, before you re-run anything: on the storage half that is the harness's own unmeasured reason in the table or a namespace stuck in Terminating, and on the network half it is the claim's allocation and the Pod's FailedScheduling event.

Where you will use this​

The next time a training job's accelerators sit idle at work, you will time the data path with one probe across every storage path you offer, in one run, with the configuration beside the figures, before anyone buys faster storage. When someone sends you a storage benchmark, you will ask what it cannot tell apart, and whether its numbers are a disk or a page cache. When a shared namespace hangs in Terminating, you will look for an NFS client whose server was deleted first. And when a team asks for an accelerator and a network card that sit together, you will write one claim with a matchAttribute constraint rather than node labels, and you will know exactly what that claim does and does not prove.
