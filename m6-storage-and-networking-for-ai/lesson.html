Module 6 — Storage & Networking for AI

The accelerator is 8 percent busy, the job says it is running, and nobody can say why it is slow. Nothing is broken in Kubernetes. The kube-scheduler placed the Pods, Kueue honoured the quota from Module 5, and the scheduler's DRA plugin allocated the device. The bottleneck sits four layers below all of that: in the path the data takes to reach the device, or in the network between two devices that have to talk to each other on every training step. This module is about those two paths. It teaches you to measure the first one with a method you can take to any fleet, and to read the second one in the right order when a distributed job slows down.

  • Core path: ~3.0 h
  • Advanced brief: 1.0 h (labelled, optional)

The rest of this page will make more sense after.

Five storage workloads and their access patterns​

Imagine a busy restaurant kitchen. The vegetables arrive in large crates once a day and are read through, crate by crate, all morning. The chef's recipe book sits on one shelf and everyone reads it, nobody writes in it. Every hour, a cook writes down exactly where each dish is, so that if the power goes out, the kitchen can start again from that note and not from the morning. Plates go out and come back all day. And a small notepad by the stove holds the orders that are cooking right now. Five kinds of storage, in one room, and no single cupboard would serve all five.

An AI platform has the same five, and each one asks for something different:

  • Datasets. Large, read many times, mostly sequential, read in parallel by many workers at once. What matters is read throughput, and how fast the first byte of each file arrives when there are millions of small files. A dataset is usually rebuilt from its source if it is lost.
  • Checkpoints. A training job's saved state, written in large bursts by every worker at the same moment, read back only after a failure. What matters is write throughput at the burst and the time to read it back on restart. When a worker dies, the workload controller, a Job or a JobSet, restarts its Pods and the training code reads the checkpoint back, so a lost checkpoint is lost training time and durability matters.
  • Model artifacts. The weights a server loads at start. Written once, read many times, often by many replicas starting together. What matters is how fast a new replica can read the whole file, which is the model-loading bottleneck Module 8 measures.
  • Container images. Pulled by the node's runtime before a Pod can start. Large AI images make the pull a real part of cold start.
  • Vector indexes and KV caches. Small, random reads and writes, where latency matters more than throughput. Module 10 runs a vector database; the KV cache lives in accelerator memory and Module 9 routes by it.

Three words get mixed up in every storage discussion, so here they are plainly. Throughput is how many bytes per second you can move in a long, steady stream. IOPS is how many separate small operations per second the storage can answer. Latency is how long one operation takes from start to finish. A dataset of large files wants throughput. A dataset of millions of tiny images wants IOPS and low metadata latency, because the file system spends more time finding each file than reading it. That second problem has a name, metadata pressure, and it is often what makes a "fast" shared file system feel slow to a training job.

So one StorageClass cannot serve all five. A platform offers a small set of storage classes, each with a stated access pattern, and puts each workload on the one that fits.

The storage ladder from object store to accelerator​

Back to the kitchen. The crates of vegetables come from a warehouse across town: huge, cheap, slow to reach. A walk-in cold room in the kitchen holds what the day needs. A shelf beside the stove holds what the next hour needs. And the chef's own chopping board holds what is being cut right now. Each step closer is smaller, faster and more expensive per kilogram. Nobody keeps the whole warehouse on the chopping board, and nobody walks across town for each onion.

Data for an accelerator climbs the same ladder, from the cheapest tier to the fastest:

Read it left to right. Each arrow is a copy, and each copy is where time goes. Object storage is the cheapest per gigabyte and the slowest to start reading; node-local disk is the fastest and is lost with the node. A cache tier exists so that the second read of a dataset or a model does not go back to object storage.

The Kubernetes mechanics underneath every step of that ladder are the ones you already know, used with an AI workload in mind:

  • A PersistentVolumeClaim asks for storage. A StorageClass says which kind it gets, and the CSI driver behind that class provisions and attaches the volume. On this course's kind cluster the default class, standard, is served by the local-path provisioner, which makes one directory on the node per claim.
  • Access modes decide how many nodes may mount a volume. ReadWriteOnce is one node. ReadWriteMany (RWX) is many nodes at once, and it is what a distributed training job's shared checkpoint directory needs. Most block storage cannot do RWX at all, which is why RWX usually means a network file system.
  • VolumeSnapshots copy a volume at a point in time, which is one way to keep a checkpoint without stopping the job.

Two cheaper steps sit under all of this and need no brief: object storage reached over the S3 protocol, and a plain NFS server. The lab runs both. The object store in the lab is SeaweedFS behind the S3 protocol, and the path is called s3 everywhere, because it is the protocol being taught, not the product.

What a storage measurement can and cannot tell apart​

The lab times four storage paths with one harness. Here is the method, because the method is the part that transfers to any real fleet:

  • One probe, every path. The same small program writes and reads the same payload on every path, with the same clock and the same chunk size. The only thing that changes between the four numbers is the path under the write.
  • Every write includes the flush to disk, so the number is a durable write and not a write into memory.
  • Every read first asks the kernel to drop that file from its page cache, and every repetition writes a new file name, so no read can be served from bytes a previous step left in memory.
  • The paths run one at a time, never together, because all four end on the same disk and would otherwise be timing their fight with each other.
  • The configuration is written by the same run that produces the figures, into a file beside them. A storage figure without its configuration is not evidence of anything.

The four paths are s3 (an object store over HTTP), nfs (a shared RWX claim from an in-cluster NFS server), pvc (a claim on the cluster's default class) and hostpath (a Pod volume onto a directory the node had bind-mounted when it was created).

Now the part most storage write-ups skip: what this harness cannot tell you. Three fences bind everything the harness, run.sh, reports in this module, and each came out of the course's own runs:

  1. No claim that pvc and hostpath differ. On kind, the local-path provisioner's directory is itself a bind mount on the node, so the two local paths end up on the same kind of storage by two routes, and the gap the course's runs saw sat inside the spread the runs set for themselves. That null result is the lesson: the harness cannot tell these two apart on this machine, and saying so is the honest report.
  2. No ranking of nfs against s3 on write. Their separation also sat inside the runs' own threshold.
  3. No absolute figure is disk performance. The cluster runs inside a VM on your laptop, and the host's own page cache sits under the VM's disk where nothing inside the guest can evict it. A figure in your table is a figure for that laptop, that VM, that run, with the configuration printed beside it.

What is claimable is a property, not a number: the tier split. Both local-file-system paths came out above both network-protocol paths, on write and on read, in 16 of 16 rows in the course's first study and in 8 of 8 in a later run of the storage layer, both on the course's build machine, an Apple M1 Pro running a Rancher Desktop VM. The course's three runs of this module's lab, on the same machine, did not repeat it. The first held it on write in both repetitions but not on read. The second held it in the first repetition on both sides and broke it in the second on both. The third held it on write in both repetitions and on read in the first, and broke it on read in the second. Wherever it broke, s3, whose server keeps a cache the client cannot evict, came out above at least one local path, and on one read in the first run and one in the third nfs did too. So the split is a property you check on each side and in each repetition, not one you can expect. Your run is your own: the lab asks you to read your table and write down what it shows, in your own words, beside the configuration that produced it.

One reading did repeat, and it is the one Module 7 inherits: the shared path's first write. On the course's second run of the lab, the nfs path's first write, onto a volume provisioned in the same invocation, took 82.94 s (conditions: an Apple M1 Pro host running a Rancher Desktop VM, kernel 6.18.36-0-virt, 5 CPUs; Kubernetes v1.37.0 on kind v0.33.0 at the 8 GB size; six containers from other projects sharing the VM; one writer, a payload of 256 mebibytes written and flushed by the harness's probe; harness run 20261118T122454Z, repetition 1), and its second write onto the same volume took 3.09 s (conditions: the same run, the same volume, the same payload, repetition 2). The configuration that run was taken under is published beside those figures with the grid-v1.2 reference point, and the course's third run, the one the lab shows with its own figures and conditions, saw the same pattern. Neither is disk performance, and the first one is barely writing at all. It is waiting. A freshly started NFS server spends its first 90 seconds in a grace period: a window in which clients from before a restart may reclaim the files they held, and every new open is held back until it closes. Picture a shop that unlocks its doors but, for the first minute and a half, serves only people collecting orders they placed before it closed. That first write had arrived during that minute and a half. A separate probe on the same layer showed it plainly: a 16-mebibyte and a 256-mebibyte first write, started together on two fresh volumes just after a fresh server came up, took 88.09 s (conditions: the same host, VM, versions and layer; the 16-mebibyte write, flushed, onto its own fresh volume, started eight seconds after the server; probe of 2026-11-18) and 91.36 s (conditions: the same probe at the same moment; the 256-mebibyte write onto a second fresh volume), nearly all of it inside open, while a 256-mebibyte first write started after the window had closed took 2.12 s (conditions: the same probe and server; started 110 seconds after the server). What carries over is the order of events: a training job's checkpoints land on that shared path, and a checkpoint that starts within 90 seconds of the NFS server starting, or restarting, waits for that window to close, however small it is.

Checkpoints and model caches as infrastructure​

A training job that runs for days will fail somewhere along the way. A node dies, a spot instance is taken back, a driver hangs. The workload controller (JobSet in Module 7) restarts the Pods and the kube-scheduler places them again, but the work since the last save is gone. The job's protection is the checkpoint, which is nothing but a saved copy of the job's state that it can restart from. Two questions follow, and both are platform questions: how often should the job checkpoint, and what does each checkpoint cost the shared storage?

The restart-cost formula, derived​

Start from Module 2's cost model. A fleet costs the same per hour whether the accelerators do useful work or not, so every hour a job holds N accelerators costs N into the price per accelerator-hour, busy or idle. Anything that wastes job-hours wastes that money. Checkpointing wastes job-hours in two ways, and they pull in opposite directions.

Name the four quantities first:

τ  (tau)    the checkpoint interval: time between two checkpoints
δ  (delta)  the time one checkpoint takes to write, during which training stalls
R           the restart time after a failure: reschedule, reload the checkpoint, warm up
M           the mean time between failures for the whole job

Cost one: the stall. Every interval τ, the job stops for δ to write. So the fraction of time lost to writing is:

overhead from writing  =  δ / τ

Checkpoint more often, and this goes up.

Cost two: the lost work. A failure lands at a random moment inside an interval, so on average it lands halfway through. The work since the last checkpoint, τ / 2 on average, is lost, and the restart costs R on top: the time for the workload controller (JobSet in Module 7) to restart the Pods and for the kube-scheduler to place them. Failures arrive once every M hours on average, so the fraction of time lost to failures is:

overhead from failures  =  (τ / 2 + R) / M

Checkpoint less often, and this goes up.

Add them and find the bottom. The total fraction of wasted time is:

W(τ)  =  δ / τ  +  (τ / 2 + R) / M

Take the derivative with respect to τ and set it to zero:

dW/dτ  =  − δ / τ²  +  1 / (2M)  =  0
τ²     =  2 δ M
τ*     =  √(2 δ M)

That is Young's approximation for the checkpoint interval. It is derived, not guessed, and it says something useful: the right interval grows with the square root of both the write time and the time between failures. Note that R drops out of the interval. It still costs you money on every failure, but it does not change how often you should save.

A worked example, with numbers you can replace with your own. Say a checkpoint takes 6 minutes to write and the job fails on average once every 50 hours, each time costing whatever restart time R your JobSet and storage give you. Then 2 into 0.1 hours into 50 hours is 10, and its square root is about 3.2, so checkpoint about every three hours. Then multiply back through Module 2's model: a 64-accelerator job at your quoted price loses, on every failure, about half an interval plus the restart time, into 64 accelerators, into that price. That number is what a platform team shows when someone asks why checkpoint storage is worth paying for.

Checkpoint storms and the rest of the checkpoint problem​

Now the platform half. Every worker in a gang writes its checkpoint at the same moment, so a 64-worker job does not write one checkpoint every three hours; it writes 64 of them at once, into the same shared file system. That burst is a checkpoint storm, and on shared storage it slows down every other tenant using that storage, not just the job doing the writing. The deep dive puts three concurrent writers on the lab's one RWX claim beside a single writer, so you can see the effect for yourself on your own machine.

The ways teams live with it:

  • Asynchronous checkpointing. The job copies its state to host memory, which is fast, and goes back to training while a background thread writes it out. The stall δ shrinks to the copy, and the formula above gives a shorter interval for free.
  • Sharded checkpointing. Each worker writes only its own slice of the state, in parallel, so no single writer carries the whole thing.
  • Retention. Keep the last few checkpoints and delete the rest, because checkpoints are large and the storage bill grows with every one you keep.
  • Restore time. A checkpoint you cannot read back quickly makes R large. Test the restore, not just the save.

Model caches are the same problem pointed the other way. Many replicas of a model server start at once after a deploy and all read the same weights. A cache on each node, or a shared cache tier, turns the second and later reads into local reads. The hard parts are the usual cache problems: eviction, deciding which model to throw out when the cache is full, and invalidation, noticing that a model was updated so that no replica keeps serving the old one. Module 8 measures model cold start; this module gives you the storage underneath it.

Collective traffic beyond the pod network​

Imagine eight colleagues each holding a page of the same calculation. After every step, each one must tell all the others their result before anyone can take the next step. If they sit around one table, it takes seconds. If half of them are in another building and the only link is the office's general phone line, which everyone else in the company is also using, the calculation spends most of its time on hold. That is a distributed training job on an ordinary network.

Training traffic is mostly east-west: from one node to another inside the cluster, not in and out of it. The collective operations Module 2 introduced, like all-reduce, make every worker exchange data with the others on every step. The ordinary Pod network is built for many small, independent connections, so it is the wrong road for that. AI clusters add a second, faster network beside it:

  • RDMA, which is nothing but a network card writing straight into another machine's memory without the operating system copying each packet. It comes in two flavours: InfiniBand, a separate fabric with its own switches, and RoCE, RDMA over ordinary Ethernet, which needs the network configured to avoid dropping packets.
  • GPUDirect RDMA lets the network card read and write accelerator memory directly, skipping the copy through host memory, on hardware that supports it.
  • The NVIDIA Network Operator installs the drivers and the device plugins for that hardware on a Kubernetes cluster.

All of these need real hardware. This course has none, so they are taught here and in the recorded briefs, and nothing in the lab claims to show them.

A second network for a Pod​

A Pod has one network interface by default. To give it a second one, on the fast network, the cluster needs a meta-plugin that calls more than one network plugin. Multus is that plugin: it reads a custom resource, the NetworkAttachmentDefinition (NAD), in group k8s.cni.cncf.io at v1, and attaches the extra interface the NAD describes to any Pod that names it in an annotation. The course read Multus at v4.3.2. SR-IOV is the usual thing a NAD points at on real hardware: one physical network card split into many virtual ones, each handed to a Pod.

This course teaches Multus by reading its manifests, not by installing it, and here is one detail from that reading worth knowing at work: the release's own thick-plugin DaemonSet manifest, at the release tag, names its image by a floating snapshot-thick tag, not by the release. A manifest that pulls whatever was pushed last is not something to install unchanged, and a platform team pins the release-tagged image or a digest instead. No NAD is committed to your platform repository either, because no lab in this course can verify one.

Topology Manager and NUMA alignment​

A server with two CPU sockets has two NUMA nodes: each socket has its own memory, and its own PCIe slots. An accelerator and a network card plugged under the same socket can talk to each other without crossing between sockets. Plugged under different sockets, every transfer crosses the link between them and gets slower.

The kubelet's Topology Manager tries to give a Pod a device, a network card, CPUs and memory from one NUMA node. With the policy single-numa-node, it refuses to start a Pod it cannot align that way. It works with the CPU Manager and the Memory Manager, which pin CPUs and memory. The policy is configuration you can read: on any node, the kubelet's live configuration is served at the node's configz endpoint, and topologyManagerPolicy is one field in it. Whether alignment actually happened is a property of real hardware with real NUMA nodes, and a kind node inside one VM has none to align. So this course shows you where the setting is and stops there.

A device and a NIC in one claim​

Dynamic Resource Allocation, GA in Kubernetes 1.34 at resource.k8s.io/v1, already lets a claim ask for a device by its attributes. It can also ask for two devices from two different drivers in one claim, with a constraint that they share an attribute. The attribute that matters here is resource.kubernetes.io/pcieRoot, a standard name for which PCIe root a device sits under. One claim, two requests, one constraint:

devices:
  requests:
  - name: accelerator
    exactly: { deviceClassName: sim-accelerator.example.com }
  - name: nic
    exactly: { deviceClassName: sim-nic.example.com }
  constraints:
  - matchAttribute: "resource.kubernetes.io/pcieRoot"

The scheduler's DRA plugin then allocates only a pair that sits under one root, or nothing. That replaces the old way of doing this, node labels and hope, with a decision the scheduler makes and records on the claim.

The lab runs this with two instances of the upstream example driver: one publishes synthetic devices, and a second release, on the driver's network profile, publishes synthetic NICs named nic-0 to nic-3, with a model string LATEST-NET-MODEL and a 100G bandwidth capacity that no device has. Both drivers publish pcieRoot from the same helper, so a pair under one root exists. Every one of those names and figures is a constant in the driver's source, and the lab puts a caption beside every capture that prints them, exactly as Module 4 did for the device driver's own labels.

The real implementation of this idea for network cards is DRANet. DRANet, a SIG Network subproject at kubernetes-sigs/dranet, v1.5.0 (2026-10-03), publishes resource.kubernetes.io/pcieRoot and uses this same constraint in its own examples. This course did not run it.

Be exact about what the lab can and cannot show:

object-level selection only — NUMA alignment, device injection and RDMA performance are hardware- and driver-dependent

The lab shows the scheduler choosing a pair that shares an attribute, and the two drivers preparing what it chose. It shows nothing about a NUMA node, a real network card, or a packet.

The evidence order for a distributed slowdown​

Eight accelerators train slower than four. Everyone in the incident channel has a theory: the storage, the network, the code, the new driver. The way out is to read the evidence in a fixed order, from the device outward, and rule each layer in or out before moving to the next. Like a doctor who checks pulse and temperature before ordering a scan, you start with the cheapest signal closest to the patient.

  1. Device telemetry. Is the accelerator busy, idle, or reporting errors? An idle device with no errors is waiting for something. A device with errors is the problem.
  2. Dataloader timing. Does each step wait on data? If the time spent loading the next batch is a large part of the step, the storage path from the ladder above is the suspect.
  3. NCCL logs. NCCL, the collective-communication library most training frameworks use, logs which network transport and which interface it picked at start. A job that should use RDMA and logs a socket transport on the ordinary interface has already told you the answer.
  4. Interface counters. The bytes and drops on each network interface. Is the ordinary interface saturated while the fast one is idle?
  5. RDMA counters. The RDMA device's own counters: data sent and received, retransmits, congestion signals.
  6. Topology. Which PCIe root and NUMA node each accelerator and each network card sits under, and whether they line up.

Alongside the sequence, four hardware-level causes come up again and again:

  • NCCL interface selection. NCCL picks its interface by environment variables such as NCCL_SOCKET_IFNAME and its own detection; a wrong guess sends collectives over the slow road. Its topology files describe the machine to it, and a wrong one misleads it.
  • PFC and ECN, the two congestion controls a RoCE network relies on so that it does not drop packets. Misconfigured, they cause pauses and retransmits that look like a slow job.
  • MTU, the largest packet size. A mismatch along the path fragments or drops packets.
  • Link failures, a flapping cable or port, which show up as error counters and retransmits.

The deep dive hands you a synthetic evidence bundle, written by the course and labelled as synthetic in every file, and asks you to classify it in exactly this order and name the root cause. No device, NIC or fabric produced any line of it.

Rented and recorded network evidence​

Advanced brief (+1.0 h, optional). Two kinds of evidence this laptop course cannot produce, and how it handles each.

The first is a two-device NCCL all-reduce bandwidth test, the same job over the fast device-to-device link and then forced over PCIe, for about $3 of rented time. It turns Module 2's interconnect lecture into a number from real hardware, with its instance type and software stated. It arrives with the rented-hardware track, and until then it is not part of this module.

The second is multi-node RDMA and InfiniBand fabric behaviour: congestion, the adaptive routing the fabric's subnet manager and switches decide, what a failing link does to a job across many nodes. That needs a fabric no laptop and no single rented instance has. The course covers it as recorded material from real clusters and says so wherever it appears.

Where ownership sits​

Every mechanism in this module has exactly one owner. When data is slow or a pair will not allocate, the first question is which one.

On this course's cluster, the CSI row is served by the local-path provisioner, and the in-cluster NFS server in the lab provisions its own RWX claims the same way.
