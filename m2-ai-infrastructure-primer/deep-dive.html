Deep Dive — KV Cache, Paged Blocks, the Decode Bound and Ring All-Reduce Cost

The lab gave you a budget for memory, a capacity from demand and a cost. Each rested on a formula that the calculators applied for you. This page opens the four formulas underneath: why the cache is as large as it is, how an engine wastes less of it, how fast one request can possibly be answered, and what the network costs a training step. You will use these when a team asks "why does this model run out of memory at twenty users", "why is it slow even with nobody else on it" and "why did adding servers not speed up training". All four are arithmetic, so every figure here is an estimate from stated inputs.

Where this picks up

This page needs only your clone and the m2 folder from the lab. No cluster is involved. It writes scratch files under /tmp/m2-dd and never changes your inputs, so re-running any block is safe. Run everything from the root of your clone.

mkdir -p /tmp/m2-dd && ls m2/kv-blocks.sh m2/decode-bound.sh m2/allreduce.sh

[ Expected output ]

m2/allreduce.sh
m2/decode-bound.sh
m2/kv-blocks.sh

1 — Why the KV cache is as large as it is​

A model reads a prompt word by word, and every new word is compared with all the words before it. To avoid redoing that work, the server stores two small tables for every earlier word, a key and a value. That store is the KV cache. Now think of a library reading room. Every reader at the table (a query head) wants to consult notes. In the old design each reader had a private notebook. In grouped-query attention several readers share one notebook, and in the extreme case, called multi-query attention, the whole table shares one. The readers still read separately. They just stop copying the same notes.

The formula counts notebooks. Each token stores a key and a value (the 2), in every layer, for every key-value head, each of a fixed width, at the bytes per value you chose.

KV bytes per token = 2 * layers * kv_heads * head_dim * bytes per value

Here is the proof on one model. The first model file has 28 attention heads and 4 key-value heads, as its published config.json states. Make copies of it with the key-value head count changed to 28 (one notebook per reader), 8, 4 and 1, and run the same scenario.

for h in 28 8 4 1; do
  sed "s/^num_key_value_heads=.*/num_key_value_heads=$h/" m2/inputs/models/qwen2.5-7b-instruct.conf > /tmp/m2-dd/kv$h.conf
  echo "kv_heads=$h $(bash m2/vram-budget.sh /tmp/m2-dd/kv$h.conf m2/inputs/vram-scenario.conf | grep -E '^(kv_bytes_per_token|kv_gb_all_requests)=' | tr '\n' ' ')"
done

[ Expected output ]

kv_heads=28 kv_bytes_per_token=401408 kv_gb_all_requests=52.61 
kv_heads=8 kv_bytes_per_token=114688 kv_gb_all_requests=15.03 
kv_heads=4 kv_bytes_per_token=57344 kv_gb_all_requests=7.52 
kv_heads=1 kv_bytes_per_token=14336 kv_gb_all_requests=1.88

The cache per token is linear in the head count. The 28-head copy is seven times the real model, and that ratio is the whole saving of grouped-query attention. The cache for all requests also grows linearly with context and with concurrency, so the three levers multiply. A product team that doubles the context and doubles the concurrent users has asked for four times the cache, and the weights did not change at all.

The cost is not abstract. When the weights already take most of a card, the cache is what is left, and the number of requests one replica can hold is that remainder divided by the cache per request. Part 2 of the lab used this to find the replicas that memory demands. Two models of about the same parameter count can differ by more than a factor of two in cache per token, as the lab's Mistral and Qwen files did, and only the model card tells you.

2 — Paged blocks and internal fragmentation​

Think of a hotel that books by the room. A group of five guests takes three rooms and leaves a spare bed, and the hotel can give every other room to someone else. The alternative is to book the guest group a whole floor because they might bring more people. The floor is empty most of the time and nobody else can use it. An engine that sets aside the maximum context for every request is booking floors. An engine that hands out small fixed blocks of cache, called paged blocks, as a sequence grows is booking rooms.

With blocks, a sequence of L tokens needs L divided by the block size, rounded up to a whole number of blocks. The only waste is the unused tail of its last block, called internal fragmentation. The calculator compares that with reserving the whole context for each request. The sample lengths come from your scenario file, and they are declared assumptions.

bash m2/kv-blocks.sh m2/inputs/models/qwen2.5-7b-instruct.conf m2/inputs/vram-scenario.conf | sed -n '/^RESULTS/,$p'

Read the two waste columns. Paged waste stays small for every length, because a tail is at most one block. Reserved waste depends entirely on how short the real requests are compared with the maximum, so it is large exactly when most requests are short. A larger block wastes a larger tail, and a smaller block means more blocks to track. Engines pick the block size as a trade-off between the two. Two conditions apply to every line above. The five sample lengths are an assumption, not traffic. And the calculator models only the tail. Real engines also share blocks between requests that start with the same prompt, which saves more, and that sharing is the subject of Module 9.

3 — The bandwidth-bound decode upper bound​

Answering a request has two phases. In the first, the server reads the whole prompt in one pass. In the second, called decode, it produces one token at a time. Each new token needs the model to look at every weight. Go back to the kitchen. The cooks are fast, but for every single token they must read the entire recipe book through the pantry door before they cook anything. If the book is fifteen GB and the door passes 3350 GB each second, you can read the book about two hundred and twenty times each second, and you cannot make tokens faster than that however many cooks you add. The 3350 GB each second is the vendor's printed figure for the H100 SXM.

That gives an upper bound for one request on its own:

tokens per second <= memory bandwidth (GB/s) / weight bytes read per token (GB)

The conditions are strict, and they are printed in the calculator's header. The batch size is one. The weights are read once per token, with no cache reads. No kernel overhead and no overlap are counted. So the bound is optimistic by construction, and every line ends with (estimate).

bash m2/decode-bound.sh m2/inputs/models/qwen2.5-7b-instruct.conf | sed -n '/^RESULTS/,$p'

Read the bandwidth column. The memory of each card is printed in the calculator's header, which the sed cuts off here, and it plays no part in the bound. The weights are printed to four decimal places so that you can divide the two printed figures yourself and get the printed bound. Lines marked [weights exceed one card] are shown only so you can see the arithmetic. On those cards the weights alone are larger than the memory the vendor prints for one card, before any cache, so the number describes no real deployment on one card. Two more cautions. For a mixture-of-experts model such as Mixtral, a token reads only the experts it uses, so dividing by the total weights would give a pessimistic figure, not an upper bound. This course does not state the active parameter count for it, because the model card does not. And batching changes the picture: reading the weights once serves every request in the batch, which is why engines batch, and why the per-request bound and the fleet's total throughput are different numbers.

4 — The cost model of ring all-reduce​

Training makes every card hold the same correction at the end of a step. Imagine a ring of cooks, each holding a pot of the same size. Each cook splits the pot into as many portions as there are cooks, and passes one portion to the neighbour while receiving one from the other side. After enough passes everybody has the combined pot. This is the ring all-reduce. Each card sends and receives the data twice over in total, in small chunks, and the passing happens at the same time around the ring.

With N cards and S gigabytes of data per card, each card moves about 2(N-1)/N times S. Divide by the bandwidth B of the link each card sends over, and you have the time of the bandwidth term:

time = 2 * (N - 1) / N * S / B

The factor 2(N-1)/N is below two for any N and approaches two as N grows. That is the useful surprise. Beyond a handful of cards, adding more does not make the ring much slower, and it does not make it faster either. The time is set by S over B, the size of the data and the speed of the slowest link. Run the calculator on your link classes, which are declared round numbers, not vendor specifications.

bash m2/allreduce.sh m2/inputs/interconnect.conf | sed -n '/^RESULTS/,$p'

[ Expected output ]

RESULTS (modelled):
in_node_fast in-node fast link class      B= 450.0 GB/s time_s=0.0583 (estimate)
in_node_pcie in-node PCIe class           B=  50.0 GB/s time_s=0.5250 (estimate)
net_400g     network 400 Gbit/s class     B=  50.0 GB/s time_s=0.5250 (estimate)
net_100g     network 100 Gbit/s class     B=  12.5 GB/s time_s=2.1000 (estimate)

Now vary the number of cards and keep the links. Copy the file with two, eight and sixty-four participants, and print only the slowest and the fastest link.

for n in 2 8 64; do
  sed "s/^participants=.*/participants=$n/" m2/inputs/interconnect.conf > /tmp/m2-dd/ring$n.conf
  echo "participants=$n"
  bash m2/allreduce.sh /tmp/m2-dd/ring$n.conf | grep -E '^(in_node_fast|net_100g) '
done

[ Expected output ]

participants=2
in_node_fast in-node fast link class      B= 450.0 GB/s time_s=0.0333 (estimate)
net_100g     network 100 Gbit/s class     B=  12.5 GB/s time_s=1.2000 (estimate)
participants=8
in_node_fast in-node fast link class      B= 450.0 GB/s time_s=0.0583 (estimate)
net_100g     network 100 Gbit/s class     B=  12.5 GB/s time_s=2.1000 (estimate)
participants=64
in_node_fast in-node fast link class      B= 450.0 GB/s time_s=0.0656 (estimate)
net_100g     network 100 Gbit/s class     B=  12.5 GB/s time_s=2.3625 (estimate)

From two to eight participants the time for each link rises by three quarters, and from eight to sixty-four by only an eighth, because the factor 2(N-1)/N is already close to two. Between the two links it changes by a factor of thirty-six, the ratio of their bandwidths. A ring that spans servers has to cross the network, so its pace is the network row, even when the links inside each server are many times faster. This is the reason placement matters for training, and the reason Module 6 and Module 7 pay so much attention to the network. Conditions: the formula covers the bandwidth term only. Per-hop latency, overlap with compute and the real topology of the fabric are outside it, and a real training step on real hardware would include all three.

rm -rf /tmp/m2-dd

Where you will use this​

Where you will use this
  • The KV cache per token is two, into layers, into key-value heads, into head width, into bytes per value, and it grows with context and with concurrency together. Use it when: a team asks to double the context window or the user count. Read the model card for the number of key-value heads, rerun the budget and the capacity table, and tell them the cache need before they find it out as an out-of-memory error.
  • Paged blocks waste at most the tail of one block per request, while reserving the maximum wastes the gap between the maximum and the real length. Use it when: two engines, or two settings, show very different capacity for the same card. Check the block size and how the engine reserves memory before you blame the hardware.
  • Single-request decode speed is bounded by memory bandwidth divided by the weight bytes read for each token. Use it when: someone asks for a faster accelerator to speed up one slow chat. Compare the bandwidth of the card you have with the bound for your model. If you are already near it, a different card with more bandwidth, a smaller model or batching is the answer, and more cooks are not.
  • Ring all-reduce time depends on data size over the slowest link, and beyond a handful of cards hardly on how many there are. Use it when: a training job is slow only when it spans servers. Find the slowest link on the path and the size of the data it carries, before you add cards or change the job.
