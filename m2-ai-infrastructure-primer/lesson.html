Module 2 — AI Infrastructure Primer

You can run Kubernetes. You may never have run a model. This module gives you every AI idea the rest of the course uses, told from the infrastructure side. You will not learn how a model is trained or how good its answers are. You will learn what it asks of a machine: how much memory, how much network, how many accelerators, and what that costs when they sit idle.

An accelerator is the card that does the heavy arithmetic. Most people say GPU, which is short for graphics processing unit. This course says accelerator when it means the whole family of cards, and GPU when it names a specific product.

Nothing in this module needs a cluster. The lab is arithmetic, done with small scripts on your laptop, and every figure it prints is an estimate from stated assumptions. You finish with two documents in your own repository: a capacity model and a cost model.

The four workload classes in detail​

Imagine a catering company that runs a wedding season. Buying and cleaning vegetables the night before is one kind of work. Cooking the main feast, where every cook must be in the kitchen together for hours, is another. Serving guests at the counter, where nobody will wait, is a third. And a waiter who walks between the tables and the kitchen again and again, deciding the next step each time, is the fourth. It is the same company, but it puts four very different demands on its kitchen.

AI workloads split the same way. Module 1 gave you the map. Here is the same map with the columns an infrastructure engineer actually needs.

Three distinctions change how you build the platform, so learn them early.

Online, batch and offline inference. Online inference answers a person who is waiting, so latency is the target. Batch inference answers a queue of requests that arrive together and can wait minutes, so throughput is the target. Offline inference runs over a stored dataset overnight, so cost per answer is the target. It is one model, but it needs three different platforms.

Training, fine-tuning and continued pretraining as resource patterns. Training from scratch asks for the most accelerators for the longest time, with heavy traffic between them. Fine-tuning starts from finished weights and adjusts them, so it asks for fewer accelerators for less time, but still needs the weights and extra training state in memory. Continued pretraining is a training-sized job that starts from existing weights. You do not need the method. You need the pattern each one makes on your cluster.

Inference engine versus inference platform. The engine is the process that loads a model and answers requests. It batches requests together and manages the memory cache for each one. The platform is everything around many engines: how many copies run, which accelerators they sit on, who may use them and what happens when one fails. The engine is not your job, but the platform is.

Inside the accelerator, and the VRAM arithmetic​

A CPU is a small kitchen with a few very skilled chefs. An accelerator is a hall with thousands of cooks, all chopping at the same time. That works well when the job is the same chop repeated millions of times, which is what a model does when it multiplies large tables of numbers. The cooks are grouped into teams that the hardware calls streaming multiprocessors, and special units inside them, called tensor cores, do the multiply-and-add in one step.

Here is the part that matters to you. The cooks are fast, but they get their ingredients through one pantry door. That door is the accelerator's own memory, called VRAM (video RAM), or HBM (high bandwidth memory) on data-centre cards. How wide the door is, called memory bandwidth, usually decides the speed, not how many cooks you have. Most of the time an accelerator would be waiting for data, not computing.

VRAM is also where you run out first. A model server needs three things in that memory at once.

  • Weights. The learned numbers of the model. Their size is the parameter count into the bytes used for each parameter.
  • KV cache. A KV cache (key-value cache) is the memory the server keeps for every request that is still being answered, so it does not redo work for words it has already read. Its size grows with the number of requests and the length of each one.
  • Overhead. Working space for the framework and for temporary results.
weights          = parameters * bytes per parameter
KV per token     = 2 * layers * kv_heads * head_dim * bytes per value
KV for requests  = KV per token * tokens per request * concurrent requests
total            = (weights + KV for requests) * (1 + overhead fraction)

Four real model cards show how different the numbers get. Each row is read from the model's own config.json at a pinned revision. The parameter count comes from the Hugging Face API for the same revision. Conditions for every figure: 2 bytes per value (16-bit), 8192 tokens of context per request, 16 requests at the same moment, overhead of one tenth, GB meaning 10^9 bytes. They are modelled estimates, not measurements.

ModelParametersLayersKV headsWeights, GBKV bytes per token

Read the first two rows together. The two 7B models have almost the same weights. But the second keeps eight key-value heads and the first keeps four, which doubles its cache for every token, and its 32 layers against 28 push it past double. This trick of sharing key-value heads is called grouped-query attention. It is a design choice of the model, and it is written in the model card. You read it before you size anything.

Read the last row for a different reason. Mixtral is a mixture of experts: it holds eight expert blocks and runs only two for each token. People hear that and assume it needs little memory. It does not. All the parameters must be in memory, because any token may need any expert. Memory follows the total parameter count. Only the compute follows the two that run.

Quantization shows up here only as an input. Storing each weight in 8 bits instead of 16 halves the bytes per parameter in the formula, and 4 bits halves it again. How a model keeps its quality at fewer bits is a model-technique topic and belongs to course 305. Here it is one number you change in the lab.

On the hardware side, the vendors' own specification tables, read on 2026-10-29, put the memory of one accelerator anywhere between 24 GB on an NVIDIA L4 and 192 GB on an AMD Instinct MI300X. Treat the products as examples of a class. What remains the same is the structure of the choice: a single-card node, a server with several cards joined by a fast link, or a whole-rack system where dozens of cards behave like one. The card names will change within the year.

The interconnect and collective communication​

When one accelerator is not enough, several of them must work as one. Imagine a relay of workers moving a heavy pot of water around a circle, each passing a share to the neighbour. The whole circle can only move as fast as its slowest hand-off. That one idea explains most of the network design you will see in an AI cluster.

Inside one server the cards talk over PCIe (the standard slot bus) or over NVLink, NVIDIA's much faster direct link between cards. NVSwitch is the chip that lets many cards use NVLink with each other at once. Between servers the traffic goes over Ethernet, InfiniBand or RoCE (RDMA over Converged Ethernet). RDMA (remote direct memory access) lets one machine write straight into another's memory without involving the CPU. GPUDirect extends the same idea so that data goes between the accelerator and the network card or the disk without a detour through main memory.

Training makes the cards swap results all the time. The patterns of that swapping are called collectives.

  • AllReduce adds up a value from every card and gives everyone the total. Training uses it to combine gradients, which are the small corrections each card computes.
  • AllGather gives every card the pieces held by all the others.
  • ReduceScatter adds up the values and hands each card one slice of the total.

NCCL (the NVIDIA Collective Communications Library) is the library that runs these patterns across the cards. The NCCL library chooses the path through the links and sets the pace, so when a job runs slowly, its log is where you start. The cost has a simple form for the ring pattern: the data each card must move, divided by the bandwidth of its slowest link. The Deep Dive turns that into a calculator.

There is one more input to placement. Inside a big server, memory and cards are attached to particular CPU sockets, and a card is closer to some memory than to the rest. This layout is called NUMA (non-uniform memory access). A job that lands on the wrong side of it runs slower for no visible reason, so the scheduler needs to know about it.

You will learn about five ways of splitting a job across cards. Learn each by what it demands from the network and from placement, not by how to configure it.

SplitWhat is dividedWhat it demands

Capacity planning from demand​

A chai stall sees customers arrive at a steady rate and each one stays a few minutes. To know how many people are standing at the stall at any moment, you take the arrival rate into the time each customer stays. Nothing else is needed. That is Little's law, and it is the first step of sizing a model service: concurrent requests equal requests per second into the seconds each request stays in the system.

Everything else follows from that number. The platform needs to cover it in two different ways, and you plan for the larger of the two answers.

  • Memory. Each request needs KV cache. Divide the memory left after the weights by the cache per request, and you know how many requests one replica can hold at once. Concurrent requests divided by that gives the replicas the memory demands.
  • Throughput. Each request produces tokens, and one replica can produce only so many per second. Total tokens needed per second divided by that gives the replicas the compute demands.

Then you would add what a production setup needs on top. A failure reserve is extra replicas so that losing one does not break the service. Fragmentation is capacity lost because replicas cannot be fitted tightly onto the accelerators you have. Beyond those, a real plan also weighs zone availability, the chance that spot capacity is taken back, the mix of accelerator types, how much you reserve in advance, and how long a request may wait in a queue before you miss your target.

The hard part of capacity planning is that every input is a guess until you have traffic. So you do not report one number. You report the number, the inputs behind it and a sensitivity analysis: change each input by a fixed amount and see which ones move the answer. Then you write an explicit uncertainty section that lists every assumption that would change the answer. Part 2 of the lab does exactly this and commits the result to your repository.

The economics of idle accelerators​

A wedding hall is booked for the whole year at a fixed rent. If a wedding happens on five days, you still pay for the other days. An accelerator fleet works the same way. The meter runs whether the card is busy or not.

Cloud pricing comes in three forms. On-demand is the highest price, available when you ask. Reserved is a lower price for a commitment of a year or more. Spot is the lowest price, for capacity the provider can take back. Beyond the hyperscalers, specialist GPU clouds and owned hardware change the mix again. The price in this course is always a number you type in, labelled "replace with your own quote". We do not state a market rate.

Where does the money go? A survey of Kubernetes clusters by Cast AI, its 2026 State of Kubernetes Optimization report, put average GPU utilisation at around five percent. That is a vendor report, so read it as attributed, not as a figure this course produced. Take the size of the problem seriously, though. Most of the fleet's hours go to idle waiting.

The lab compares a 64-accelerator fleet at five percent utilisation with the same fleet at sixty percent. Sixty percent is a design target this course picked for comparison, not an observed figure. The fleet cost is identical in both cases, so the cost of each useful hour falls by a factor of twelve. Read that again, because it is the whole argument for the platform.

This means utilisation percentage by itself can mislead you. A card can be busy doing wasteful work, or be busy only because one oversized job holds it. The number to track is the one the business sees: useful tokens generated per accelerator-dollar. Utilisation is one input into it, and the other inputs are how well the engine batches and how much of the output anyone wanted.

There are four levers to move that number, and the rest of the course builds each one.

  • Share. Put several small workloads on one accelerator. Module 4 covers how.
  • Queue. Hold work in a queue so the accelerator is never waiting for the next job, and so teams get fair quota. Module 5 builds this with Kueue.
  • Pack. Fit workloads onto fewer accelerators so you can release the ones you do not need.
  • Reclaim. Take back allocations that sit idle, such as a notebook nobody has touched since last week.

The AI infrastructure stack, named​

Every layer you will build in Modules 4 to 12 sits somewhere in one picture. Keep it open as a map.

Read it from the top. An agent calls a model. The call goes through a routing layer to a serving layer, which asks the scheduling layer, the platform, for accelerators. Training jobs ask the same scheduler for the same accelerators. Storage and network sit beside the scheduler because a fast accelerator waiting for data is wasted money. Operations watches all of it and attaches a cost.

The boundary of who owns what is where most organisations argue. The model team picks the model and judges its quality. The application team builds the product. The platform team supplies devices, quota, serving infrastructure and the bill. The arguments start in the grey areas: who sets the replica count, who owns the model server image, who pays for the accelerator that sat idle between two experiments. The answer for this course is written in the section below, and the same table pattern returns in every module.

Where ownership sits​

Four mechanisms in this module have four different owners. If you cannot say who drives a mechanism, you cannot debug it or size it.

MechanismOwner
Batches requests and manages the KV cache inside one model serverthe inference engine
Decides fleet size, quota and how many model servers run across many machinesthe platform
Combines gradients across accelerators in a training job (AllReduce)NCCL
Carries data directly from one accelerator to another inside one serverNVLink

When a request is slow, ask which owner it belongs to before you change anything. If the cache is full, that is the engine, and the answer is a smaller context or more memory. If there are too few replicas, that is the platform. If a training step is slow only when it spans servers, the problem sits with NCCL and the link underneath it, and no setting in the model will fix it.

What you carry into the lab is the habit of reading a model card, a vendor table and an assumption before you trust a number. Every figure you generate there is arithmetic you can change, and the page that shows it says so.
