Deep Dive — Core PodGroup Gangs, Quota-Only Admission and the Pre-Created Claim

The lab ran every group through Kueue, and Kueue carries this course's labs. This page goes one level below that and puts the two paths side by side on the same simulated fleet. You place a gang with the core scheduling.k8s.io/v1beta1 PodGroup, where the kube-scheduler itself holds the members back until enough of them fit. You submit a gang that cannot fit and read how the core path refuses it. You send the identical ten-Pod group through Kueue and watch Kueue admit it on quota while the fleet places only half. And you read the one device request Kueue refuses at the version this course pins: a Pod that names a claim created ahead of time. You will use these layers when someone asks whether to move gang scheduling into the core API, when a queued job is admitted and still half-placed, and when a team's device request is refused with a reason that does not mention quota.

Where this picks up

This page runs on grid-core with the synthetic-device layer and the queueing layer applied. If they are still up from the lab, this block finds them and changes nothing. If you tore them down, or never did the lab, it creates exactly what is needed. All three create scripts converge, so re-running the block is safe. Run it from the root of your clone.

The queueing layer's own verify is not in this block. You met the reason in the lab: applied with TAS_GANGS=none, the layer submits nothing itself, and its verify refuses to report clean while Kueue has decided nothing. Until then, the check is the create script's own summary, the line near the end of the block's output that starts OK: addon-kueue-kwok applied. You run the verify in section 3, right after Kueue admits this page's first group.

The page never relies on a lab object surviving. It needs four things: the cluster, the device layer, the queueing layer with its nine simulated nodes, and the lab's four ResourceFlavors, which it applies itself. Everything else it creates in its own two namespaces, m5-core-gang and m5-claims.

1 — A core gang placed whole​

In the lab, the queue held a group back until there was quota for all of it. The core API does something different, and it does it in the scheduler. Picture a lift that will only leave when a whole tour group is inside: the lift operator counts heads at the door, and if the group does not fit, nobody gets in. A PodGroup is that head count. It says "these Pods belong together, and at least minCount of them must be placed at once". The kube-scheduler then treats the group's members as one decision: it binds them together, or it binds none.

The core objects are served at scheduling.k8s.io/v1beta1 in Kubernetes 1.37, behind the GenericWorkload gate, which is beta and off by default; the grid-core profile turns it on. A Pod joins a group through one field in its own spec, schedulingGroup.podGroupName. Here is the object and the field, from m5/dd-core-gang.yaml:

file: m5/dd-core-gang.yaml (the group and the Pod template's link to it)

apiVersion: scheduling.k8s.io/v1beta1
kind: PodGroup
metadata:
  name: research-gang
  namespace: m5-core-gang
spec:
  schedulingPolicy:
    gang:
      minCount: 4
---
    spec:
      schedulingGroup:
        podGroupName: research-gang

The members come from a Deployment, not a Job. On the simulated fleet, kwok finishes a Job's Pods almost as soon as they are bound, so a Job's gang would be gone before you could read it; a Deployment's Pods stay. There is no queue label on this Deployment: Kueue decides nothing in this section. Each member asks for 4 cpu, so each needs a node of its own.

Apply it and read the result. The apply itself is a check on the field names: kubectl validates fields on the server, so a misspelled field is refused rather than ignored.

kubectl --context kind-grid-core apply -f m5/dd-core-gang.yaml
kubectl --context kind-grid-core -n m5-core-gang get podgroups.scheduling.k8s.io research-gang -o name
kubectl --context kind-grid-core -n m5-core-gang get deployment research-gang
for i in $(seq 1 60); do
  b=$(kubectl --context kind-grid-core -n m5-core-gang get pods -l app=research-gang -o json | jq '[.items[] | select(.spec.nodeName != null)] | length')
  [ "$b" -ge 4 ] && break
  sleep 2
done
kubectl --context kind-grid-core -n m5-core-gang get podgroups.scheduling.k8s.io research-gang -o jsonpath='minCount={.spec.schedulingPolicy.gang.minCount}{"\n"}'
kubectl --context kind-grid-core -n m5-core-gang get pods -l app=research-gang -o json \
  | jq -r '"members=" + (.items | length | tostring) + " bound=" + ([.items[] | select(.spec.nodeName != null)] | length | tostring) + " nodes=" + ([.items[].spec.nodeName // "none"] | unique | join(","))'
kubectl --context kind-grid-core -n m5-core-gang get podgroups.scheduling.k8s.io research-gang -o json \
  | jq -r '.status.conditions[]? | .type + "=" + .status + " reason=" + (.reason // "none")'

2 — A gang that cannot be placed​

Now a group the fleet cannot hold. oversized-gang is ten members of 4 cpu with minCount: 10. Each simulated node has room for one such Pod, research-gang already holds four nodes, and nine nodes could never hold ten anyway. Ask what a Pod-at-a-time scheduler would do here: place five and leave five waiting, the 7-of-8 trap again. The core path should place none.

Let's analyze what happened:

  • Ten members exist and none is bound. The scheduler did not place the five that would have fit, because the group's minimum is ten and the fleet has room for five.
  • The PodGroup's condition is False with reason Unschedulable, and its message does the counting in the group's own terms: minCount (10) cannot be satisfied. The Pods' FailedScheduling events carry the same message. One event also shows the plain per-Pod view: of 11 nodes, the 9 simulated ones have too little cpu left, and the two real nodes are ruled out by a node selector and a taint. Two extension points do this work inside the scheduler: PlacementFeasible, which runs after each member is tried and decides whether the group can still be placed whole, and PodGroupPostFilter, which runs when the group cannot be scheduled. Do not expect to see their names. In this course's run on Kubernetes 1.37, no event in m5-core-gang named either one. The messages speak in the group's own terms instead, minCount against what could be scheduled, and that is the line to read.
  • This is the property the lab's queue gave you, reached from the other side. Kueue refused the lab's queued group before any Pod could be placed; the core path lets every Pod exist and holds all of them back at placement.

3 — The same group through the queue​

Now send the identical group through Kueue: kueue-same-gang, ten members of 4 cpu, in m5-core-gang, through a LocalQueue whose ClusterQueue, compare-cq, has quota for all forty cpu. It is a StatefulSet, the lab's pattern for a group that must keep holding its quota.

Read the arrows. Kueue's decision is about quota: is there room in the ClusterQueue for the whole group? It is not a decision about whether the nodes have room. After Kueue lifts the gates, the kube-scheduler places each Pod on its own, exactly as it did in the lab's 7-of-8 trap.

kubectl --context kind-grid-core -n m5-core-gang get statefulset kueue-same-gang
sleep 20
kubectl --context kind-grid-core -n m5-core-gang get workloads.kueue.x-k8s.io -o json | jq -r '.items[]

Let's analyze what happened:

  • The Kueue Workload is admitted, and the quota for all ten members is charged to compare-cq.
  • Only some members have a node. With research-gang on four nodes, the fleet has room for five 4-cpu Pods, so five are bound and five wait. This page reads that number and does not assert it, because it depends on what else holds the fleet at that moment.
  • So an admitted group can still be half-placed, and that is the surprise this section exists for. Kueue's all-or-nothing is a quota guarantee. It becomes a placement guarantee only when the flavour is a topology flavour, as in the lab's part 4, where Kueue checks the nodes' capacity before admitting, or when Kueue's wait-for-Pods-ready setting evicts a group whose Pods do not all start within a time limit.

Two more facts belong beside this comparison. First, the pinned Kueue release does not read the core PodGroup at all: at that tag, nothing in Kueue's own controller code imports the core scheduling.k8s.io/v1beta1 API or watches its objects. The API shows up only in scheduler libraries Kueue copies in and in one end-to-end test. That is what the pinned source shows, not a promise about the next release. The course's run agrees: Kueue made one Kueue Workload in m5-core-gang, for the StatefulSet, and put no label, annotation, finalizer or owner of its own on either core PodGroup. Second, the two paths can disagree. A group under both a PodGroup and a Kueue queue can be admitted by one and held by the other, and while the core scheduling.k8s.io/v1beta1 API is beta in Kubernetes 1.37 and off by default, the platform should pick one owner for "whether" per workload type, which is why the Grid's answer is the Kueue path.

4 — A pre-created claim, refused​

The lab charged devices through a ResourceClaimTemplate: each Pod gets its own claim, made from the template when the Pod is created, and Kueue counts the device the template names. There is a second way to ask for a device. A team creates one ResourceClaim ahead of time and has its Pod name it, through resourceClaimName. Think of it as bringing your own reserved table to a restaurant that takes bookings only through its front desk: the desk has no record of how your table was booked, so it cannot count it.

Kueue v0.20.6 counts devices only through ResourceClaimTemplates, and refuses a Pod that names a pre-created claim, with QuotaReserved false and reason Misconfigured. The course's own run showed the same refusal on this cluster. Read it here with quota taken out of the question: claims-cq has a device quota of 1 on the real worker, enough for this request.

kubectl --context kind-grid-core apply -f m5/dd-precreated-claim.yaml
kubectl --context kind-grid-core get clusterqueues.kueue.x-k8s.io claims-cq
kubectl --context kind-grid-core -n m5-claims get resourceclaim pre-made-claim
kubectl --context kind-grid-core -n m5-claims get job precreated-claim
kubectl --context kind-grid-core -n m5-claims wait workloads.kueue.x-k8s.io --all --timeout=120s \
  --for=jsonpath='{.status.conditions[?(@.type=="QuotaReserved")].reason}'=Misconfigured
kubectl --context kind-grid-core -n m5-claims get workloads.kueue.x-k8s.io -o json | jq -r '.items[]
  | .status.conditions[]? | select(.type == "QuotaReserved" or .type == "Requeued")
  | .type + "=" + .status + " reason=" + .reason + " message=" + ((.message // "") | .[0:120])'
kubectl --context kind-grid-core -n m5-claims get resourceclaim pre-made-claim -o jsonpath='allocated={.status.allocation.devices.results[0].device}{"\n"}'
echo "pods: $(kubectl --context kind-grid-core -n m5-claims get pods -l batch.kubernetes.io/job-name=precreated-claim -o json | jq '.items | length')"

Where you will use this​

Where you will use this
  • A core PodGroup places a group whole or not at all, at the scheduler, with no quota in the decision. Use it when: someone proposes switching gang scheduling to the core API. Check the GenericWorkload gate on the target clusters first, and ask who will decide "whether" for that workload type: the core path or the queue, not both.
  • Kueue's all-or-nothing admission is a quota guarantee, not a placement guarantee. Use it when: a job is admitted and still half-placed. Read the Kueue Workload's admission, then each Pod's .spec.nodeName, and then decide between a topology flavour, wait-for-Pods-ready, or a smaller group.
  • The two paths read different objects, and the pinned Kueue release does not read the core PodGroup. Use it when: a team puts a PodGroup and a queue label on the same workload and gets behaviour neither predicted.
  • A Pod that names a pre-created claim is refused Misconfigured at this release. Use it when: a team's device workload is refused with a reason that does not mention quota. Look for resourceClaimName in the Pod template, and move the request to a ResourceClaimTemplate.
