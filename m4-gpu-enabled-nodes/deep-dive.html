Deep Dive — Claim Preparation, the CDI Spec, Claim Device Status and NoExecute Device Taints

The lab showed that a claim gets allocated, that a container starts with a device injected, and that a NoSchedule device taint keeps new claims off a device. This page goes one level below each of those. You read both halves of one claim, the scheduler's and the kubelet's; you read the file the driver writes on the node to tell the container runtime what to inject; you switch on the field where a driver writes per-device state back onto the claim; and you watch a NoExecute device taint evict a Pod that was already running. You will use these layers when a claim is allocated but its container will not start, when someone asks what a container was actually given, and when a device has to be taken out of service under a running workload.

Where this picks up

This page runs on grid-core with the synthetic-device layer applied. If they are still up from the lab, this block finds them and changes nothing. If you tore them down, or never did the lab, it creates exactly what is needed. Both create scripts converge, so re-running the block is safe. Run it from the root of your clone.

The page never uses an object from the lab. Everything it reads, it creates in its own namespace, m4-deepdive, and it holds at most two synthetic devices at a time.

1 — Allocation and preparation on one claim​

The lab traced allocation and then read the result inside the container. Between those two there is a step the lab did not show: the kubelet calling the driver. Here you read both halves on one claim, and the evidence that ties them together is the claim's UID.

Create one claim and one Pod that uses it. The Pod prints its environment when it starts.

kubectl --context kind-grid-core apply -f m4/dd-prepare.yaml
kubectl --context kind-grid-core -n m4-deepdive get resourceclaim dd-prepare-claim
kubectl --context kind-grid-core -n m4-deepdive get pod dd-prepared
kubectl --context kind-grid-core -n m4-deepdive wait --for=condition=Ready pod/dd-prepared --timeout=180s

Let's analyze the two halves:

  • The scheduler wrote the allocation before the Pod ran on the node. Nothing on the node was touched to do it.
  • The kubelet asked the driver to prepare the claim after the Pod was bound to the node. The driver's log line carries the same UID as the claim, which is how you tie the two halves together.
  • So when a claim is allocated but the container never starts, look at the driver's log on that node, filtered by the claim's UID. When a claim is never allocated, look at the scheduler's events. Those are two different places, and the claim's status tells you which one to open.

2 — The CDI spec on the node​

How does the container runtime know what to put into the container? The driver writes it down. Think of it as the packing slip taped to a box: the porter who delivers the box does not decide what goes in, he follows the slip. That slip is a Container Device Interface (CDI) spec, a small file in a directory on the node that names a device and lists the edits to apply to any container given it: environment variables, device nodes, mounts. This driver writes its specs into /var/run/cdi on the node.

Read that directory from a debug Pod on the node. The general debug profile mounts the node's root filesystem at /host. One detail matters here: on the node, /var/run is a link to /run, and a link to an absolute path resolves inside the debug container, not on the node. So read /host/run/cdi, which is the same directory seen through the node's real path.

Do not attach to the debug Pod with -i. Attaching races the command: in the course's own runs, one attach came too late and fell back to the Pod's logs, and another returned before the command had printed anything, with no listing at all. So start the Pod without attaching, keep the name kubectl debug prints for it, wait until the Pod has finished, and then read its logs. The logs hold everything the command printed, every time.

DEBUG_POD=$(kubectl --context kind-grid-core -n m4-deepdive debug node/grid-core-worker --profile=general \
  --image=docker.io/library/busybox@sha256:bdf57e528e45e4433820e045b29b4597825a1c9e38353532d90a01445013f82e \
  -- sh -c "ls /host/run/cdi; echo; cat /host/run/cdi/*${CLAIM_UID}*" \
  | sed -n 's/^Creating debugging pod \([^ ]*\) .*/\1/p')
echo "debug pod: ${DEBUG_POD}"
kubectl --context kind-grid-core -n m4-deepdive wait --for=jsonpath='{.status.phase}'=Succeeded pod/"${DEBUG_POD}" --timeout=120s
kubectl --context kind-grid-core -n m4-deepdive logs "${DEBUG_POD}"

Let's analyze the spec:

  • There is one file per prepared claim, and its name carries the claim's UID, the same UID as in section 1. There is also one common file the driver writes once.
  • Each device entry lists container edits. The environment variables you read inside the container in the lab come from here, not from the Pod's manifest.
  • The kubelet passes the runtime only a CDI device name. The runtime looks the name up in this directory and applies the edits. That is why CDI is vendor-neutral: a different vendor's driver writes a different spec, and the runtime does the same thing with it.

3 — Claim device status​

Back to the hotel from the lab. The front desk wrote a room number on the guest's form. With claim device status, the porter also writes down what he found in the room: the state of the device, in the driver's own words, on the claim itself. The field is status.devices[], one entry per allocated device, written by the driver. DRAResourceClaimDeviceStatus is GA in Kubernetes 1.37.

The example driver writes it only when its GPU_DEVICE_STATUS setting is on, and the chart turns it off by default, so a claim's status.devices stays empty unless you change that. Switch it on with kubectl set env, exactly as the lab switched the sharing modes.

kubectl --context kind-grid-core -n dra-example-driver set env ds/dra-example-driver-kubeletplugin GPU_DEVICE_STATUS=true
kubectl --context kind-grid-core -n dra-example-driver rollout status \
  ds/dra-example-driver-kubeletplugin --timeout=120s

4 — A NoExecute device taint evicts a running claim's Pod​

In the lab, a NoSchedule device taint kept new claims off the devices and left the running holder alone. NoExecute is the other effect. It is the hotel closing a room for repairs and asking the guest already in it to leave. Device taints are GA in Kubernetes 1.37, and DeviceTaintRule is served at resource.k8s.io/v1 with a selector of driver, pool and device only.

Start the victim: a Pod holding one device through its own claim. Read which device it holds, because the rule will taint exactly that one.

kubectl --context kind-grid-core apply -f m4/dd-taint-victim.yaml
kubectl --context kind-grid-core -n m4-deepdive get resourceclaim taint-victim-claim
kubectl --context kind-grid-core -n m4-deepdive get pod taint-victim
kubectl --context kind-grid-core -n m4-deepdive wait --for=condition=Ready pod/taint-victim --timeout=120s
VICTIM_DEVICE=$(kubectl --context kind-grid-core -n m4-deepdive get resourceclaim taint-victim-claim -o jsonpath='{.status.allocation.devices.results[0].device}')
echo "victim device: ${VICTIM_DEVICE}"

The rule file carries DEVICE_FROM_CLAIM where the device name goes. Put the victim's device in, apply it, and read it back.

metadata:
  name: sim-evict-demo
spec:
  deviceSelector:
    driver: sim-accelerator.example.com
    pool: grid-core-worker
    device: DEVICE_FROM_CLAIM
  taint:
    key: sim-accelerator.example.com/evict-demo
    value: "true"
    effect: NoExecute

kubectl --context kind-grid-core get devicetaintrule sim-evict-demo -o jsonpath='device={.spec.deviceSelector.device} effect={.spec.taint.effect}{"\n"}'

Synthetic device — the tainted device

The device in the rule is the example driver's name for a synthetic device.

The last command waits for one more thing than the Pod's deletion. The Pod disappears first; the controller that evicted it updates the rule's status a moment later. Read the rule straight after the Pod is gone and it can still say the eviction is in progress, so the block waits, bounded, until the rule itself reports the eviction finished.

The Pod is gone. Read why, from two objects: the rule's own conditions, and the events recorded against the Pod, which outlive the Pod.

kubectl --context kind-grid-core get devicetaintrule sim-evict-demo \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} reason={.reason} message={.message}{"\n"}{end}'
kubectl --context kind-grid-core -n m4-deepdive get events --field-selector involvedObject.name=taint-victim \
  -o custom-columns='REASON:.reason,MESSAGE:.message'

Let's analyze the eviction:

  • The rule's EvictionInProgress condition says whether the taint is still evicting Pods. When it reads False with reason Completed, every Pod that was using the tainted device and did not tolerate the taint has been evicted, and the message counts them: one Pod here.
  • The event against the Pod names the device taint as the reason. The Pod was not killed by the kubelet for a local reason; it was evicted by the control plane because of its device.
  • The victim's claim was a plain ResourceClaim, so it outlives the Pod. Its device is still tainted, so any new Pod that references it would be evicted too. Taking a device out of service is therefore one object, the rule, and putting it back is deleting that object.

Teardown​

First remove what this page created: the eviction rule, then the namespace, which takes the remaining claims and Pods with it. If you want to go on exploring the cluster, stop after this block.

kubectl --context kind-grid-core delete devicetaintrule sim-evict-demo
kubectl --context kind-grid-core delete namespace m4-deepdive --timeout=5m
kubectl --context kind-grid-core get namespace m4-deepdive --ignore-not-found

devicetaintrule.resource.k8s.io "sim-evict-demo" deleted
namespace "m4-deepdive" deleted

Where you will use this​

Where you will use this
  • The scheduler allocates a claim and the kubelet prepares it, and the claim's UID ties the two halves together. Use it when: a team says their Pod has a device on its claim but the container will not start. Read the claim's allocation, then filter the driver's log on that node by the claim's UID, and you know which half failed.
  • The driver writes a CDI spec per prepared claim, and the runtime applies its edits. Use it when: someone asks what a container was actually given, or a device reaches the container without the variable or mount the application expects. Read the spec on the node; it is the record of what was injected.
  • Claim device status is where a driver writes per-device state onto the claim, and the example driver writes it only when its setting is on. Use it when: you evaluate a DRA driver for your fleet and need to know whether you can read device state from the API instead of from each node.
  • A NoExecute device taint evicts running Pods from one device, and deleting the rule puts the device back. Use it when: a device starts failing under a running workload and must be taken out of service without draining the whole node.
