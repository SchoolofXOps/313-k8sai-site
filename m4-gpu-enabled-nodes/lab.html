Lab — Synthetic Devices Through the Device Plugin, Dynamic Resource Allocation and Health

Lab Truth Contract — SIMULATED

The control plane, the kubelet, the driver DaemonSet's rollout and rollback, and the claim lifecycle are real Kubernetes behaviour on a real kind cluster. The devices are synthetic, published by the upstream example driver; there is no accelerator anywhere in this lab and nothing here measures one.

In this lab you take the grid-core cluster from Module 1, add a driver that publishes synthetic devices, and then ask for those devices in six different ways. Every part ends with something going wrong on purpose. You read each failure from the cluster's own objects: a condition, an allocation, an event or a status field. You never read it from a Pod's phase alone.

Think of the driver as a hotel's front desk that hands out room keys. The first part shows the old way, where the desk only counts how many keys are left. The rest show the new way, where every room has a card on file saying which floor it is on and what it has, and you ask for a room by what is on the card. The keys in this hotel are made up, though. The rooms do not exist. That is the one thing to hold on to through every part: the driver's own output calls its devices gpu-0, gpu-1 and so on, and none of them is a GPU.

Run every command from the root of your clone of the labs repository, as in the earlier modules. If you open a second terminal, export KUBECONFIG there again.

Where the platform stands​

After Module 3 your platform record holds the baseline failures, the capacity and cost models and the platform design, and the cluster is torn down. The base cluster serves the Dynamic Resource Allocation API, resource.k8s.io/v1, but no driver publishes a single device into it. That is the gap Module 3's audit named, and this lab closes it on synthetic devices.

When you finish, the platform can address a device by attribute and can show a device's health in Pod status. Your repository gains grid-platform/nodes/: a device class, two claim templates, the driver's values file, a rollback record and an XID classification. It also gains the wrappers for the synthetic-device layer under grid-platform/clusters/addon-dra/.

One thing is still broken, and it is on purpose. Nothing stops one tenant from claiming every device on the node. M5 adds quota and queueing to fix that.

Devices as a counted extended resource​

Start with the old way, the one the device plugin uses. A device plugin tells the kubelet "this node has 4 of resource X", and the kubelet writes the number onto the node. The scheduler then counts. That is all it does. It does not know which of the four is which, or what any of them can do.

You do not need a device plugin to see this. A node's extended resources can be advertised by patching its status directly, which is the documented way to advertise an extended resource by hand. Advertise 4 of a course-named resource, sim-accelerator.example.com/device, on the worker, then wait for the kubelet to copy it into allocatable.

kubectl --context kind-grid-core patch node grid-core-worker --subresource=status --type=json \
  -p '[{"op":"add","path":"/status/capacity/sim-accelerator.example.com~1device","value":"4"}]'
kubectl --context kind-grid-core wait node/grid-core-worker --timeout=60s \
  --for=jsonpath='{.status.allocatable.sim-accelerator\.example\.com/device}'=4
kubectl --context kind-grid-core get node grid-core-worker -o jsonpath='{.status.allocatable}{"\n"}'

[ Expected output ]

Driver rollback without touching the workload​

A device driver on a node is a DaemonSet like any other, and one day you will upgrade it. The question this part answers is the one an on-call engineer asks first: if the new driver revision is broken, what happens to the workloads already holding devices?

Here you break the driver on purpose, with an image that never pulls, so no new code runs. Then you roll it back and compare the workload before and after.

A readiness gate on the devices, not on the node​

A node whose driver has not finished loading is a trap: the node is Ready, so the scheduler sends device work to it. The obvious gate is a NoSchedule taint on the node. On this cluster that is the wrong gate. The driver's DaemonSet carries no tolerations, so a custom node taint would also stop the driver's own new Pod from being scheduled, and the rollback you are about to do would get stuck.

The right gate taints the devices. A DeviceTaintRule selects devices by driver, pool and device, and a NoSchedule effect blocks new allocations from them. It is served at resource.k8s.io/v1 in Kubernetes 1.37. Confirm the type is served before you rely on it.

file: m4/readiness-rule.yaml

apiVersion: resource.k8s.io/v1
kind: DeviceTaintRule
metadata:
  name: sim-driver-not-ready
spec:
  deviceSelector:
    driver: sim-accelerator.example.com
    pool: grid-core-worker
  taint:
    key: sim-accelerator.example.com/driver-not-ready
    value: "true"
    effect: NoSchedule

Device requests by attribute​

Back to the hotel. Counting keys told you nothing about the rooms. With Dynamic Resource Allocation, every room has a card on file, and you ask for a room by what is on the card. The card is the ResourceSlice entry, the request is a ResourceClaim, and the rule that picks rooms is a CEL expression. Dynamic Resource Allocation is GA in Kubernetes 1.34, API resource.k8s.io/v1.

First, a DeviceClass with a course name. The chart's class is named after the driver; yours is named for what it means on your platform.

file: m4/attr-deviceclass.yaml

apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: sim-accelerator-class
spec:
  selectors:
  - cel:
      expression: "device.driver == 'sim-accelerator.example.com'"

Then a claim template that asks for a device by attribute. On this driver only three attributes differ between devices: index, uuid and pcieRoot. The model string and the memory figure are the same on all eight, so selecting on them picks all eight or none. This template selects on pcieRoot.

file: m4/sim-device-on-root-80.yaml (the request)

      - name: sim-device
        exactly:
          deviceClassName: sim-accelerator-class
          selectors:
          - cel:
              expression: "device.attributes['resource.kubernetes.io'].pcieRoot == 'pci0000:80'"

The second template uses prioritized alternatives. It tries the subrequest sim-preferred first, which asks for a device with at least 100Gi of the driver's memory capacity, and falls back to sim-fallback, which takes any device of the class. Prioritized alternatives (DRAPrioritizedList) are GA from Kubernetes 1.36.

file: m4/sim-device-first-available.yaml (the request)

      - name: sim-device
        firstAvailable:
        - name: sim-preferred
          deviceClassName: sim-accelerator-class
          selectors:
          - cel:
              expression: "device.capacity['sim-accelerator.example.com'].memory.compareTo(quantity('100Gi')) >= 0"
        - name: sim-fallback
          deviceClassName: sim-accelerator-class

The extended-resource bridge​

Here is the migration problem every platform team meets. Hundreds of existing manifests say nvidia.com/gpu: 1 in their resource limits, because that is the name the vendor's device plugin advertises. You want to move the fleet to Dynamic Resource Allocation without asking every team to rewrite their manifests.

The bridge is a field on the DeviceClass, extendedResourceName. A DeviceClass that sets it tells the scheduler: when a Pod asks for this extended resource name, satisfy it from my devices. The Pod's manifest does not change, and it carries no claim at all. The scheduler creates the claim for it. An extended resource name on a DeviceClass (DRAExtendedResource) was alpha from 1.34, beta in 1.36, GA in 1.37.

Four ways to share one device, as object state​

On real hardware there are four ways to put more than one workload on one accelerator: hardware partitioning, time-slicing, a multi-process service, and virtual devices. The lesson's decision brief compares them. Here you see how three of them look as Kubernetes objects. Before you start, read this sentence, because it is the most common mistake in this topic:

DRA allocates what the driver exposes; it does not create MIG, time-slicing or MPS semantics, and no isolation is demonstrated here.

Kubernetes records who holds what. The driver decides what "shared" means on the device. In this lab the driver is an example that shares nothing real, so every step below shows the objects and stops there.

Known failures and their fixes​

Each entry below is something that actually happened in one of the course's own runs of this page, or in a learner walk of it, with the step it happened in named so you can compare it with your output.

Two failures on this page are deliberate and are not listed here: the rollout status that runs out of time in the rollback part, and every claim that stays unallocated on purpose. If one of those fails differently from what the page shows, compare your output with the page before you change anything.

The course ran this page twice from a fresh clone. The first run hit the failures below, and the page was fixed so that the second run, whose output this page shows, did not. They are listed because they are what you will see if you leave out one of the waits or reads the page now does, or if your clone is older than the fix.

Right after the driver rolls, the slice still lists the old devices. Seen in the course's first run, at the step that sets GPU_PARTITIONS=4 GPU_ALLOW_MULTIPLE_ALLOCATIONS=true: the next read showed "counterSets": [] and gpu-6 with no counters. After the rollout undo the same thing happened the other way round, and the re-read printed devices=40 instead of devices=8. rollout status returns when the new driver Pod is available, and the driver republishes its devices about two seconds later. The fix is the loop at the end of both blocks, which waits up to two minutes for the device count. If you ran a read without it, run the loop on its own and then the read again.

shared-a and shared-b never become Ready, and kubectl exec says container not found ("workload"). Seen in the course's first run, at the two steps of "One claim shared by two Pods". shared-claim had been allocated gpu-0-partition-0, a partition entry the restored driver had not yet removed, and neither container ever started. It is the same republish delay as the entry above, one step later. Delete shared-a, shared-b and shared-claim, run the devices=8 wait loop from the step before, and apply m4/sharing-shared-claim.yaml again.

allocatable still shows "sim-accelerator.example.com/device":"4" after you removed the resource. Seen in the course's first run, at the clean-up step of the extended-resource part. That run removed the resource from capacity only, and the kubelet drops its allocatable copy on its next status update, about ten seconds later. The page's patch now removes it from both in one step. If your read shows 4, read the node again after a few seconds.

The DaemonSet read prints updated= with nothing after it. Seen in the course's first run, at the step that reads the driver Pods during the broken revision. The DaemonSet's status leaves out a count whose value is zero, and a jsonpath read prints nothing for a field that is not there. The page now reads the counts through jq with // 0, so it prints updated=0.

rollout undo prints a Warning about last-applied-configuration. Seen in both of the course's runs, at both rollout undo steps. It is not a failure, and the undo still completes, as the line after it shows. The reason is under the rollback step.

git status shows clusters/grid-core/addons/dra/rendered-pinned.yaml as modified. Seen in both of the course's runs, after the layer's create.sh. The layer regenerates that file with helm template, and the helm the course ran, v3.22.0, writes it without nine blank lines the committed copy has; the diff is blank lines only. Leave it. The commit step names its paths, so the file is not committed, and nothing on this page reads it.

If a step fails in a way the page does not describe, read the object that step reads, in the form the page reads it, before you re-run anything. Most failures on this page are a claim with no allocation or a Pod whose PodScheduled condition is False, and the object says why.

Where you will use this​

The next time a driver upgrade goes wrong on an accelerator node pool, you will read the DaemonSet's revision and the plugin Pods before you touch the workloads, and you will roll back through the DaemonSet's history knowing the running claims are safe. The next time a team asks for "a device on the fast interconnect", you will write a claim template that selects by attribute instead of adding another node label. The next time someone migrates a fleet from the device plugin to Dynamic Resource Allocation, you will reach for the DeviceClass bridge so no team rewrites a manifest, and you will say out loud that a resource name proves nothing about the hardware behind it. And the next time an XID alert fires, you will correlate before you drain.
