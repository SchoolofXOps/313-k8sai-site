Module 4 — GPU-Enabled Nodes

A Pod that asks for nvidia.com/gpu: 1 gets a device. It does not get the right device, it does not learn whether anyone else is on that device, and nobody tells it when the device starts to fail. This module is about closing those three gaps on the node: how Kubernetes finds an accelerator, what software stack has to be running before it can, how you share one device, how you ask for a device by what it is rather than by how many, and how you read the evidence when one goes bad.

Through this module, an accelerator is the card that does the heavy arithmetic, GPU when we name a specific vendor's product. The lab has no accelerator at all. It runs an upstream example driver that publishes synthetic devices, and the driver's own output calls those devices gpu-0, gpu-1 and so on. They are not GPUs. Every capture on the lab page says so beside it, because the tool itself will not.

How Kubernetes discovers an accelerator​

Imagine a hotel front desk that only counts keys. A guest walks up and asks for a room. The clerk looks at the board, sees four keys on the hook, and hands one over. The clerk does not know which room has the sea view, which one is next to the lift, or whether two guests are about to be given rooms that share a bathroom. The clerk counts keys, and that is all.

That is how Kubernetes has discovered accelerators for most of its life. The pieces are these:

  1. The kubelet's device manager. The kubelet, that is the agent on every node, runs a small registry for devices it does not understand itself.
  2. A device plugin. A vendor ships a program, usually a DaemonSet, that registers with the kubelet over a gRPC socket and says "this node has N of resource X". For NVIDIA cards, X is nvidia.com/gpu.
  3. An extended resource. The kubelet writes that count onto the node's status.capacity and status.allocatable, exactly like CPU and memory, except that it is a whole number and it cannot be overcommitted.
  4. Node labels. Separate tools add labels describing the hardware, so that people can steer Pods with node selectors.

A Pod asks for nvidia.com/gpu: 1 in its limits, the scheduler subtracts one from the node's count, and the kubelet asks the plugin to hand the device to the container. It works. The lab's first part shows it working, and then shows a Pod asking for one more than the node has, and the scheduler refusing it with Insufficient in the PodScheduled condition.

But the key board cannot express six things the platform needs:

  • No attributes. The count says "4". It does not say which one has more memory, which PCIe root each sits on, or which driver version runs it.
  • No sharing semantics. One unit is one Pod. There is no way to say "these two Pods share this device".
  • No topology awareness. The count cannot say "give me two devices on the same interconnect".
  • No claim lifecycle. There is no object that represents "this workload holds this device", with a status you can read.
  • No multi-device coordination. Asking for a device and the network card next to it is two unrelated requests.
  • No way to ask for an alternative. "The big one if you have it, otherwise any" cannot be written.

Dynamic Resource Allocation, later on this page, is the answer to all six. First, the stack that has to be running before any of it works.

The accelerator software stack on a node, component by component​

On a node with a real NVIDIA card, a whole set of components has to be in place before Kubernetes can use it. Most platforms install them through NVIDIA's GPU Operator, which runs each one as a DaemonSet and checks them in order. Here is each component and what it owns.

ComponentWhat it owns
driver DaemonSetbuilds or loads the kernel driver for the card, inside a container
container toolkitconfigures the container runtime so a container can be given the device
device pluginadvertises nvidia.com/gpu to the kubelet as an extended resource
Node Feature Discoverylabels the node with the hardware it finds, such as PCI vendor ids and kernel version
GPU Feature Discoveryadds labels for the card's model, memory and capabilities
DCGM and dcgm-exporterthe vendor's management library, and an exporter that publishes its health and usage readings as metrics
MIG managerapplies partitioning profiles on cards that support hardware partitioning
validatorruns checks after each step and reports when the node is ready for device work

There are two ways to get the driver onto a node. A driver container builds the kernel module on the node at runtime, so one image covers many kernels, but it needs the kernel headers and it can fail when the kernel moves. A cloud-image driver comes baked into the node image by the cloud provider, so it is fast and tested, but you upgrade it by replacing nodes.

The GPU Operator is versioned by the calendar, 26.7, not by semantic versioning, so a jump in the first number is a year, not a breaking change. Read the release notes rather than the number.

These are the failures this stack actually produces, and each one looks like "the GPU is broken" to the team that hits it:

  • Driver, toolkit and kernel skew. The node's kernel was upgraded and the driver container cannot build against it.
  • An unlabelled node. Feature discovery is not running, so a node selector matches nothing.
  • The device plugin in CrashLoopBackOff, usually because the driver underneath it is not loaded.
  • 0 nvidia.com/gpu allocatable on a machine that visibly has four cards, because the plugin never registered.
  • A node that is Kubernetes-Ready but not device-ready. The kubelet is healthy, so the scheduler sends device work there, and the Pods fail at start.

You will not run this stack in this course's core path, because it needs a real card. It arrives in the rented-hardware track as an optional lab, GPU Operator with time-slicing (about $3), which runs it on one rented instance.

Driver and operator lifecycle on a node​

Upgrading a driver on an accelerator node is not like rolling a web Deployment. The order matters, and so does what each step does to the Pods already holding devices.

A driver upgrade usually goes in this order. You cordon the node so nothing new lands there. You drain the workloads that cannot survive the change, if any. You upgrade the driver, and with it the toolkit if the versions are tied, and you reboot if the kernel module demands it. You verify that the device plugin or driver has registered again and the devices are advertised. Then you uncordon. Each step has a scheduling consequence: a cordoned node takes no new Pods, a drained node holds no devices, and a node that has been uncordoned before its driver is ready is the trap from the last section.

That last trap is why you want a readiness gate for devices. The tempting gate is a NoSchedule taint on the node until the driver is ready. On the lab's cluster that is the wrong gate, and the reason is worth remembering: the driver's own DaemonSet carries no tolerations, so a custom node taint also blocks the driver's replacement Pod, and a rollback gets stuck behind the very taint that was meant to protect it. The better gate taints the devices, with a DeviceTaintRule, which blocks new allocations from those devices and leaves the node and the driver alone. DeviceTaintRule is served at resource.k8s.io/v1 in Kubernetes 1.37.

Then the rollback. In the lab you point the driver's DaemonSet at an image that never pulls and watch what happens. Many engineers expect the driver to disappear and every workload to lose its device. It does not happen, because of two numbers in the DaemonSet's update strategy: maxSurge: 1 and maxUnavailable: 0. With those, the controller starts the new driver Pod beside the old one and removes the old one only when the new one is available. A broken new revision never becomes available, so the old driver keeps serving, the published devices do not change, and the claims already allocated are not touched. The lesson for your own platform is simple: run device drivers with maxUnavailable: 0, and you get a failed upgrade that leaves the workload alone, instead of an outage.

The rollback itself goes through the DaemonSet's revision history, kubectl rollout undo. Where a driver is installed by a Helm release you may also have helm rollback, but the lab's driver is rendered with helm template and applied with kubectl apply, so the DaemonSet's history is the only history there is.

Driver mechanics on a real card, such as kernel module builds and reboots, are hardware work and are not shown in the core path.

Four ways to share one accelerator​

An accelerator is expensive and often underused, so every platform team is asked to share it. There are four ways, and they are not four flavours of the same thing. They differ in who does the sharing, what Kubernetes actually hands out, and what protection survives between tenants.

Read the "What isolation survives" column twice. Time-slicing gives no memory isolation and no fault isolation. That sentence is the one to repeat in every design review where someone proposes it to save money.

Now the most common mistake in this topic, stated once so you can recognise it:

DRA allocates what the driver exposes; it does not create MIG, time-slicing or MPS semantics, and no isolation is demonstrated here.

Dynamic Resource Allocation is an allocation and lifecycle API. It describes the devices a driver publishes, the scheduler matches them to claims, and the claim records who holds what. If the driver publishes partitions, the scheduler allocates partitions. It does not make a card partitionable, and it adds no isolation the hardware does not already provide. In the lab, the driver is an example that partitions nothing real, so the lab shows the objects and stops there.

How do you choose by workload class? Training jobs usually want whole devices, because they use all of one and share fate across a gang anyway. Batch inference and development fit time-slicing or a multi-process service, where a slow neighbour costs throughput but breaks no promise. Online inference under a latency target is the class that must never sit on time-slicing: a neighbour's memory spike or crash lands directly on your users. If it has to share, it shares through hardware partitions.

Dynamic Resource Allocation​

Back to the hotel. Dynamic Resource Allocation replaces the key board with a card file. Every room has a card that lists its floor, its view and its size. A guest fills in a request form that says what they need. The front desk matches forms to cards, writes the room number on the form, and only then does the porter go and open the room. The card file is open for anyone to read, and so are the forms.

Here is the mapping, one object at a time:

  • ResourceSlice — the card file. The driver publishes one or more slices per node, listing each device with its attributes (strings, numbers, versions, booleans) and its capacity.
  • DeviceClass — a named category of device, with a selector. A platform team defines these; a tenant asks for a class by name.
  • ResourceClaim — the request form. It asks for one or more devices of a class, optionally with CEL selectors on their attributes. Its status records the allocation.
  • ResourceClaimTemplate — a form the Pod fills in for itself. Each Pod that references the template gets its own claim, which is deleted with the Pod.

Dynamic Resource Allocation is GA in Kubernetes 1.34, API resource.k8s.io/v1.

Allocation versus preparation​

Two different components act on a claim, at two different times, and keeping them apart is the key to debugging this API.

The scheduler allocates: it reads the slices, evaluates the claim's selectors, picks a device and writes the result onto the claim. Then the kubelet on the chosen node asks the driver to prepare that device, and the driver writes a Container Device Interface (CDI) spec that tells the container runtime what to inject. A claim that is allocated but whose container never starts is a preparation problem on the node. A claim that is never allocated is a selection problem in the scheduler. That is why a DRA-capable driver is mandatory: without one, nothing publishes the slices and nothing prepares the devices.

CDI is a vendor-neutral specification for describing devices to container runtimes. It is the reason the same claim machinery works for AMD, Intel and custom silicon as well as NVIDIA: each vendor writes a driver that publishes slices and writes CDI specs, and Kubernetes does not need to know whose device it is. NVIDIA's own DRA driver has been upstreamed to kubernetes-sigs.

Attribute selection and the features around it​

A claim's selector is a CEL expression over the device's attributes and capacity, such as device.attributes['resource.kubernetes.io'].pcieRoot == 'pci0000:80'. The lab writes exactly that, because on the example driver only the index, the UUID and the PCIe root differ between devices.

Around that core sit a set of features at different maturity levels. Each level below is the feature gate's own stage and release:

  • Prioritized alternatives, firstAvailable subrequests: try the big device first, fall back to any. DRAPrioritizedList is GA from Kubernetes 1.36.
  • Admin access, for monitoring tools that need to see a device already allocated to someone else. DRAAdminAccess is GA from Kubernetes 1.36.
  • Device taints, so a device can be marked unusable and new allocations kept off it, or running Pods evicted from it. DRADeviceTaints is GA in Kubernetes 1.37.
  • Claim device status, where the driver writes per-device data back onto the claim. DRAResourceClaimDeviceStatus is GA in Kubernetes 1.37.
  • Consumable capacity, where one device can be allocated several times, each claim taking a slice of its capacity. DRAConsumableCapacity is beta and on by default from Kubernetes 1.36.
  • Partitionable devices, where partitions draw on a shared counter set of their parent. DRAPartitionableDevices is beta and on by default from Kubernetes 1.36.
  • Device binding conditions, where binding waits for a device that must be attached first. DRADeviceBindingConditions is beta and on by default from Kubernetes 1.36.
  • Three alpha gates to know by name and not build on: DRAResourcePoolStatus, DRANodeAllocatableResources and DRADeviceCompatibilityGroups. They are alpha and off by default in Kubernetes 1.37, so this course mentions them and goes no further.

The migration path that matters​

Your fleet has hundreds of manifests that ask for nvidia.com/gpu: 1. Nobody wants to rewrite them. The bridge is a field on the DeviceClass, extendedResourceName. A class that sets it says: when a Pod asks for this extended resource name, satisfy it from my devices. The scheduler then creates a claim for the Pod by itself, and records it in the Pod's status.extendedResourceClaimStatus. The manifest does not change, and it carries no ResourceClaim. An extended resource name on a DeviceClass (DRAExtendedResource) was alpha from 1.34, beta in 1.36, GA in 1.37.

In the lab, an unchanged manifest asking for nvidia.com/gpu: 1 lands on a synthetic device through exactly this field. The lab says beside it what that proves and what it does not: the resource name is a matching key, not a statement about the hardware behind it.

One more API arrives with workload scheduling in Module 5: one ResourceClaim shared by a whole group of Pods, DRAWorkloadResourceClaims. It is beta in 1.37 and disabled by default.

Heterogeneous fleets​

Real clusters mix accelerator generations: last year's cards, this year's cards and a few small inference cards. There are three ways to tell them apart, and each answers a different question.

Node labels and taints answer "which nodes may run this Pod". They work with any device plugin, but they describe the node, not the device, so a node with two different cards cannot be described honestly.

DRA attributes answer "which device does this claim want". They describe each device, so a mixed node is fine, and a claim can say "at least this much memory" or "this driver version or later".

Node pools answer "which group of machines does this team's capacity come from". They are a provisioning and billing boundary, usually per card type.

Most platforms use all three: pools for provisioning, labels and taints to keep general workloads off expensive nodes, and attributes for the precise choice. Then comes the hard question. When the research team gets the newest cards and the data team gets the small ones, who decides, and what happens when research is idle and data is queued? That is a quota and fairness design question, and Module 5 answers it.

Node lifecycle and autoscaling for accelerator nodes​

Accelerator nodes are slow and costly to bring up, so autoscaling them is a different problem from autoscaling web nodes.

The Cluster Autoscaler adds nodes from fixed node groups when Pods are Pending. For accelerators it has limits: it has to guess which group can satisfy a device request, it works in whole node groups, and a cold accelerator node can take many minutes to reach the point where a model is serving. Karpenter provisions nodes directly from the Pending Pods' requirements and is the common choice for accelerator pools on clouds that support it. Compare the two across the axes that matter, which are provisioning delay, how capacity is acquired, Spot with on-demand fallback, consolidation, interruption handling and who operates it. Compare them in one declared environment, never as a portable speed claim. Both need a cloud account, so both are BRIEF in this course.

Follow one request through the whole chain, because every link is a delay: the Pod is Pending, a node is provisioned, the driver and plugin become ready, the model is loaded, and the server starts serving. On a cold node that chain takes minutes, and that is why platforms keep warm pools of ready accelerator nodes even though an idle accelerator costs money every hour.

Kubernetes 1.37 also adds node lifecycle conditions, such as MaintenancePlanned, DrainInProgress and Drained. They are alpha and off by default behind NodeLifecycleConditions, so no learner's cluster has them on. Treat them as the direction Kubernetes is moving, and do not build a runbook that depends on them.

Accelerator health evidence​

An accelerator fails in ways a CPU does not, and the first sign is usually a number in the kernel log.

That number is an XID, the error code the NVIDIA kernel driver writes when something goes wrong on the card. dcgm-exporter publishes the last one it saw as the metric DCGM_FI_DEV_XID_ERRORS. Three are worth knowing by heart, as NVIDIA's XID catalogue describes them:

XIDWhat it reports
48an uncorrectable double-bit memory error (ECC)
63a memory page retired or a row remapped, to be applied at the next reset
79the device has fallen off the PCIe bus

An XID is diagnostic evidence, not an automatic action. Before you retry a job, drain a node, reset a device or replace it, correlate: does the error recur, what is the device's memory-error state, do the application's own errors line up, and does a reset clear it? An automation that drains a node on every XID 48 will drain nodes that a single reset would have fixed. The lab classifies a course-authored fixture for exactly these three, because there is no real card to produce them.

The vendor's management library also runs diagnostics, dcgmi diag -r 1 up to -r 4. Level 1 is a quick system validation that takes seconds, and level 2 an extended one of about two minutes. Levels 3 and 4 are hardware diagnostics that run for about fifteen minutes or longer. Plan the long levels for a drain window, not for a device that is serving traffic.

Then there are failures that raise no error at all: a card throttling because it is too hot, one slow device in a training gang that holds back the other seven, and a card that is slowly running out of rows it can remap. You find those by comparing devices against each other, not by waiting for an alert.

Here is the real gap: Kubernetes has no complete, vendor-neutral remediation loop for accelerator health. Device plugins can mark a device unhealthy, vendor monitoring publishes metrics, node-problem-detector plugins can set node conditions, vendor agents and cloud providers each run their own diagnosis, and none of them owns the whole loop. What Kubernetes does provide now is a common place to read device health from: the Pod's own status, at status.containerStatuses[].allocatedResourcesStatus[].resources[].health, from KEP-4680. ResourceHealthStatus is beta and on by default from Kubernetes 1.36, and the lab's example driver reports health through it since v0.5.0.

Why does the lab classify a fixture instead of running dcgm-exporter? Because the exporter needs the vendor's driver and management library on the host. Its --fake-gpus flag accepts fake devices that the library itself creates, on a host that already has that software; it is not a mode for a machine with no GPU stack. The remediation loop that acts on this evidence comes in Module 12, once quota and checkpointing exist to make draining safe.

Cloud and bare-metal accelerator node pools​

Both of these are BRIEF in this course: concepts and objects, nothing executed.

Cloud accelerator node pools. Every major cloud offers node pools of accelerator instances, and the portable concepts are the same everywhere: a pool per card type, a node image that already carries the driver or an operator that installs it, quotas you request from the provider in advance, Spot or preemptible capacity with interruption notices, and an autoscaler that adds whole nodes. Learn those concepts once, then map them onto your provider's names for them.

Bare-metal accelerator clusters. On your own hardware you take on everything the cloud did for you: provisioning nodes, often through Cluster API; managing driver and firmware versions across the fleet; replacing failed cards; and running the health loop yourself. The reward is cost and control. The price is that every link in the chain from the last section is yours to operate.

Where ownership sits​

Every mechanism in this module has exactly one owner. When something goes wrong, the first question is which one.

MechanismOwner
advertises an integer device count on the nodedevice plugin
publishes devices and their attributes as ResourceSlicesdriver
allocates a device to a claimscheduler
prepares the allocated device and injects it into the container, through the driver's CDI speckubelet
rolls the driver to a new revision and backDaemonSet

Read the third and fourth rows together. The scheduler decides which device; the kubelet makes it real on the node. A claim stuck without an allocation is the scheduler's to explain, and a container that will not start with its device is the kubelet's and the driver's.
