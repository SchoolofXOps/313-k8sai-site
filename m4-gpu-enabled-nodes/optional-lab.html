Optional Lab — Device-Memory Quotas and Placement Policy on Mock Devices

Lab Truth Contract — SIMULATED

The cluster, the webhook, the scheduler extender and its bookkeeping are real software on a real kind cluster. The four devices are mock devices served by NVIDIA's mock NVML library, and nothing here runs CUDA, so the memory and core shares you will read are accounting only: no cap is enforced anywhere in this lab.

This is an optional lab. It sits outside M4's main path on purpose, because it adds a second scheduler path to your cluster, and the course keeps a second scheduler out of the core path. Do it if your platform will hand out slices of one accelerator to many small workloads. It takes about 30 minutes on a laptop, most of it waiting for images.

In the main lab you counted whole devices. Here you ask for a share of a device: some of its memory and some of its cores. HAMi, a CNCF project, does that with three parts: a mutating webhook that sends your Pod to its own scheduler, a scheduler extender that keeps a ledger of how much memory and how many cores each device has left, and a device plugin that finds the devices. You will read that ledger, watch it place Pods two different ways, and then fill it until a Pod waits for memory while the device count still says there is room.

Think of the extender as the booking clerk of a restaurant. Every table seats a fixed number of people, and the clerk writes each booking into the book: table 3, four seats. When the book says table 3 is full, the clerk turns the next party away, even if you can see an empty chair. That is all the extender does. The clerk does not stand at the table and stop a fifth person sitting down. In HAMi that job belongs to a library inside the workload, HAMi-core, and this lab never loads it. So hold on to this: you are reading the booking book, never the table.

The resource names are NVIDIA's and HAMi's; the devices behind them are mocks, and no HAMi cap is enforced here, because nothing here runs CUDA.

Run every command from the root of your clone of the labs repository, as in the main lab. If you open a second terminal, export KUBECONFIG there again.

Where the platform stands​

After the main M4 lab your platform record holds the node layer: a device class, two claim templates, the driver's values file, a rollback record and an XID classification. The cluster is torn down. Your platform can count devices, address them by attribute and read their health, but it can only hand a device out whole.

When you finish this lab you will know how a memory-quota scheduler books a share of one device, how its placement policy moves where a Pod lands, and the one thing such a scheduler cannot do on its own. Nothing is committed to your repository: this lab is a reading exercise on a cluster you delete at the end.

What is still broken stays broken, on purpose. Nothing stops one tenant from booking every share of every device. M5 adds the quota and queueing that fix that.

Install the scheduler extender, its webhook and its device plugin​

HAMi installs from one script. It fetches the v2.11.0 chart from HAMi's release page and refuses it if its checksum differs from the one the course registered. It renders the chart with the course's values, compares that render byte for byte with the committed m4/optional/hami-rendered-pinned.yaml, and applies the committed file. Every image in it is pinned by digest. Then it waits for three things: the webhook's certificate, the device plugin's registration, and the webhook actually answering.

file: m4/optional/values.yaml (the part that points HAMi at the mock)

devicePlugin:
  nvidiaDriverRoot: /var/lib/nvml-mock/driver
  extraEnvs:
    - name: DEVICE_DISCOVERY_STRATEGY
      value: nvml
devices:
  nvidia:
    deviceSplitCount: 10

deviceSplitCount: 10 lets HAMi book up to ten Pods onto each device. The devices.nvidia layout is new in v2.11.0. Values files written for older HAMi releases put this under devicePlugin, and the v2.11.0 chart refuses them at install, so an older tutorial fails loudly rather than quietly.

bash m4/optional/install-hami.sh

Now the webhook. HAMi's webhook is what sends a Pod to HAMi's scheduler, and it is configured to fail open: if it cannot answer, the API server lets the Pod through unchanged, and the default scheduler takes it. The default scheduler does not understand device memory, so that Pod waits forever. The safe habit is to ask the API server for a dry run first and confirm the Pod comes back routed to HAMi.

kubectl --context kind-grid-core get mutatingwebhookconfiguration hami-webhook \
  -o jsonpath='failurePolicy={.webhooks[0].failurePolicy}{"\n"}'
kubectl --context kind-grid-core create namespace m4-hami
kubectl --context kind-grid-core create --dry-run=server -f m4/optional/share-one.yaml \
  -o jsonpath='schedulerName={.spec.schedulerName}{"\n"}'

[ Expected output ]

failurePolicy=Ignore
namespace/m4-hami created
schedulerName=hami-scheduler

failurePolicy reads Ignore, which is what fail-open means. The dry run reached the webhook and came back with schedulerName=hami-scheduler, so a real Pod created now will reach HAMi's scheduler. The install script did the same check before it printed OK:.

Ask for a share of one device​

share-one asks for one device, but only part of it.

file: m4/optional/share-one.yaml (the request)

      env:
        - name: CUDA_DISABLE_CONTROL
          value: "true"
      resources:
        limits:
          nvidia.com/gpu: 1
          nvidia.com/gpumem: "4096"
          nvidia.com/gpucores: "30"

where,

  • nvidia.com/gpu: 1 is one slot on one device;
  • nvidia.com/gpumem is the device memory to book, in MiB;
  • nvidia.com/gpucores is the share of the device's cores to book, in percent;
  • CUDA_DISABLE_CONTROL is HAMi's switch for a machine with no CUDA. Hold on to it; you will see what it does in a moment.

Create it, wait for it, and read the booking.

kubectl --context kind-grid-core apply -f m4/optional/share-one.yaml
kubectl --context kind-grid-core -n m4-hami wait --for=condition=Ready pod/share-one --timeout=180s
kubectl --context kind-grid-core -n m4-hami get pod share-one \
  -o jsonpath='schedulerName={.spec.schedulerName} node={.spec.nodeName}{"\n"}hami.io/vgpu-devices-allocated={.metadata.annotations.hami\.io/vgpu-devices-allocated}{"\n"}'

Synthetic device — the booking HAMi wrote

The GPU-… id is a mock device's id from the t4 profile, and NVIDIA in the annotation is the vendor field HAMi copied from the mock NVML library. The memory and core figures are the Pod's own request, booked against numbers the mock reported.

The annotation reads <device>,<vendor>,<memory MiB>,<core percent>, and it records exactly what you asked for. One detail matters for the rest of the lab: HAMi writes this annotation when its extender chooses the device, before the Pod is bound to the node. So an annotation on its own does not prove the Pod was placed. This step waits for the Pod to be Ready first, and every later step does the same.

The extender also leaves its decisions on the Pod as events. Read them.

Synthetic device — the cap HAMi wrote into the container

CUDA_DEVICE_MEMORY_LIMIT_0 and CUDA_DEVICE_SM_LIMIT are values HAMi handed the container from your request. No library in this container reads them, and no device stands behind them.

This is the most important read in the lab. The cap reached the container as environment variables, a memory limit and a core limit, plus the path of a usage file the library would keep, and that is all. HAMi-core, the library that would read them and refuse an over-quota memory allocation, is loaded through /etc/ld.so.preload, and that file is not there. With CUDA_DISABLE_CONTROL=true, HAMi's device plugin leaves it out. In restaurant terms, the booking is in the book, and nobody is standing at the table.

Placement policy, chosen per Pod​

When more than one device fits, HAMi has to pick one. Two policies decide it:

  • binpack puts the Pod on the most-used device that still fits, so devices fill one at a time;
  • spread puts it on the least-used device that fits, so load spreads across devices.

The cluster-wide default comes from the chart, and changing it restarts HAMi's scheduler. A Pod can also choose for itself with the annotation hami.io/gpu-scheduler-policy, with no restart. The two policy manifests differ only in that annotation and in their name prefix.

file: m4/optional/policy-binpack.yaml (what makes it binpack)

metadata:
  generateName: binpack-
  annotations:
    hami.io/gpu-scheduler-policy: binpack

Create three binpack Pods one at a time, each a small share, and print which device each one got. One at a time matters, and so does waiting for Ready. While HAMi binds a Pod it locks the node, and it lifts the lock only when its device plugin has handed the Pod its device, which happens as the container starts. A Pod that tries to bind inside that window is turned away with node lock contention and retried later. Waiting for Ready keeps each Pod out of the previous one's lock.

for i in 1 2 3; do
  POD=$(kubectl --context kind-grid-core create -f m4/optional/policy-binpack.yaml -o name)
  kubectl --context kind-grid-core -n m4-hami wait --for=condition=Ready "${POD}" --timeout=180s > /dev/null
  ALLOC=$(kubectl --context kind-grid-core -n m4-hami get "${POD}" \
    -o jsonpath='{.metadata.annotations.hami\.io/vgpu-devices-allocated}')
  echo "${POD} ${ALLOC%%,*}"
done

Observe the two lists. Which device did the binpack Pods pick, and why that one? Where did the spread Pods go?

In the course's run, all three binpack Pods went to the device share-one already held, because it was the most-used device that still had room. The three spread Pods went to the other three devices, one each, because each was the least used at the moment it was placed. Your device ids may differ, since share-one can land on any of the four, but the pattern is the same: binpack piles onto one device, spread fans out. The scheduler did not restart between the two lists; only the annotation on each Pod changed.

Fill the devices until memory runs out​

Now the deliberate failure. Each fill Pod books one slot and a large share of memory. You will create them one at a time until one is not scheduled. The loop waits for each Pod to become Ready, or for the scheduler to give the reason Unschedulable, which is its final word. It does not stop on the passing node lock contention you met above: that one carries the reason SchedulerError, and the scheduler retries it.

file: m4/optional/fill.yaml (the request)

      resources:
        limits:
          nvidia.com/gpu: 1
          nvidia.com/gpumem: "6144"
          nvidia.com/gpucores: "10"
for i in $(seq 1 12); do
  POD=$(kubectl --context kind-grid-core create -f m4/optional/fill.yaml -o name)
  for t in $(seq 1 90); do
    READY=$(kubectl --context kind-grid-core -n m4-hami get "${POD}" \
      -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}')
    REASON=$(kubectl --context kind-grid-core -n m4-hami get "${POD}" \
      -o jsonpath='{.status.conditions[?(@.type=="PodScheduled")].reason}')
    if [ "${READY}" = "True" ] || [ "${REASON}" = "Unschedulable" ]; then break; fi
    sleep 2
  done
  echo "${POD} Ready=${READY:-False} PodScheduled.reason=${REASON:-none}"
  [ "${READY}" = "True" ] || break
done
PENDING="${POD}"

Let's analyze what happened:

  • The node still advertises free slots. In the course's run it advertised 40 and 14 were in use, so 26 were free. If the scheduler only counted devices, as it did in the main lab, the last Pod would have been placed.
  • The extender refused it on memory: no single device had enough memory left for one more fill Pod. 4/4 CardInsufficientMemory reads as "all four devices failed on memory". What this lab cannot show​

HAMi-core's caps are enforced only when CUDA runs, and nothing here runs CUDA. So this lab cannot show a Pod being held to its memory share, cannot show one Pod's work slowing another, and cannot show what happens when a workload tries to use more than it booked. It showed admission and placement, which is the scheduler's half of the job.

Even with a real accelerator and CUDA, HAMi-core is a library inside the workload's own process. It is a quota on cooperative CUDA use, not a hardware or kernel boundary, and it gives none of MIG's memory or fault isolation. The lesson's sharing table covers that difference.

The mock's devices are also identical and idle. Every placement difference you saw comes from HAMi's bookkeeping alone. Topology, NUMA and multi-node placement were not exercised, and the node-level policy decides nothing on a cluster with one worker.

Known failures and their fixes​

Each entry below is something that actually happened in one of the course's own runs of this page or of its configuration, with the step it happened in named so you can compare it with your output.

One failure on this page is deliberate and is not listed here: the last fill Pod that stays Pending. If it fails differently from what the page shows, compare your output with the page before you change anything.

A Pod sits at PodScheduled=False with the reason SchedulerError and the message node lock contention. Seen in the course's first run of this page, at the fill step and in the binpack step. The earlier version of the page created each Pod as soon as the previous one had its allocation annotation. HAMi writes that annotation before the bind, and it locks the node until the previous Pod's device is handed over, so the next Pod's bind landed inside the lock and was turned away. That is not the memory failure this page is about: it is a busy signal, and the scheduler retries it. The page now waits for each Pod to be Ready before it creates the next. If you see it anyway, wait a few seconds and read the condition again before you change anything.

A Pod created right after the install goes to default-scheduler and stays Pending for good. Seen in the course's spike of this exact HAMi release on mock devices, when its first Pod was created two seconds before HAMi's scheduler held leadership. The webhook's Service had no endpoint yet, the webhook failed open, and the Pod went to the default scheduler unmutated. The default scheduler does not understand device memory, so the Pod's condition read Insufficient for both the memory and the core resources and never changed. Delete that Pod, run the dry-run step again until it prints schedulerName=hami-scheduler, and create the Pod again. The install script now waits for that answer before it prints OK:, which is why the page reads it once more before creating anything.

Where you will use this​

The next time a team asks to put many small inference or notebook workloads on one expensive accelerator, you will know what a memory-quota scheduler gives you: a booking per Pod, a placement policy, and a clear refusal when memory runs out. You will also know what to ask next, which is who enforces the booking. On HAMi that is HAMi-core inside each workload. On KAI Scheduler it is only there if someone picked its HamiCore sharing mode, because its default mode lets a container use more memory than it asked for. And the next time a Pod sits Pending on a cluster with a scheduler extender, you will read its condition and the extender's events before you blame the device count, and you will check that the webhook is answering before you create anything.

Summary​

You put mock devices on a real cluster, installed a scheduler extender with its webhook and device plugin from a pinned release, booked a share of one device and read the booking, saw that the cap reached the container only as environment variables, placed Pods with binpack and with spread, and filled the devices until a Pod waited for memory while slots were still free. Module 5 decides who gets to book these shares in the first place.

Teardown​

Delete the cluster. A layer teardown is not enough here: the worker still carries the mock's change to its container runtime and the library HAMi's device plugin copied onto it, and only a recreated grid-core gives you a worker that never had them.

Deleting the cluster also removes HAMi's second scheduler path, its webhook and every Pod you created. Nothing from this lab was committed to your repository. One thing stays on your own disk, outside the clone: the HAMi chart the install fetched, kept in ~/.cache/313-k8sai/m4-optional-hami/ so that the next run of this page reuses it instead of downloading it again. Delete that folder if you want the space back. Module 5 starts from a fresh grid-core.

bash grid-platform/clusters/grid-core/teardown.sh
