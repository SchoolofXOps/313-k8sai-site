Lab Machine Setup

Every lab in this course runs on one laptop. There is no accelerator, no cloud account and no registry login anywhere on the core path, and nothing here costs money. This page takes a machine with none of the course's pinned tools installed through to a verified cluster. Work through it once, before Module 1.

What you need​

The figures below are read from the course configuration rather than typed into this page, so the page and the configuration cannot drift apart.

ResourceDeclared minimumRecommended
Memory8 GB16 GB
CPU4 cores8 cores
Free disk50 GB50 GB

Stated as a sentence, because the threshold is the thing people check and then forget: the declared minimum is 8 GB of memory, 4 cores and 50 GB of free disk, and the recommended machine is 16 GB of memory with 8 cores. The same 50 GB of disk serves both.

Check the disk figure before you start, because it is the one nobody checks. You already know how much memory and how many cores your laptop has. Free disk is different — it changes under you, and it is the figure a machine is most likely to be quietly short of. Two commands read it: the first asks the filesystem the container runtime keeps its data on, and the second asks the runtime what it is already holding.

# macOS — the data volume, which is what the runtime's disk image grows into
df -h /System/Volumes/Data

# Linux, and Windows through WSL2
df -h /var/lib/docker 2>/dev/null || df -h /

# Either platform: what the runtime holds already, and how much of it it can give back
docker system df

On macOS, ask about /System/Volumes/Data and not about /. Both volumes sit in one APFS container, so both report the same amount available — but / is the sealed, read-only system volume, and its used and capacity columns describe macOS rather than your data. Reading / makes a nearly full disk look like a disk with room to spare, and the two answers side by side are the clearest way to see it.

On the machine this page was last checked against, the data volume answered below the declared floor, and the runtime explained where it went:

$ df -h /
Filesystem        Size    Used   Avail Capacity  Mounted on
/dev/disk3s1s1   926Gi    12Gi    30Gi    28%    /

$ df -h /System/Volumes/Data
Filesystem      Size    Used   Avail Capacity  Mounted on
/dev/disk3s5   926Gi   856Gi    30Gi    97%     /System/Volumes/Data

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          126       2         46.94GB   30.85GB (65%)
Containers      4         4         8.249MB   0B (0%)
Local Volumes   125       4         21.91GB   17.82GB (81%)
Build Cache     266       0         12.41GB   5.692GB

What to do when you are short. Installing the pinned tools is not what consumes the figure — that is three binaries and their archives, and the archives are deleted again before the block ends. The 50 GB is for node images, the layers every addon pulls, and a cluster image store that grows as you work through the modules. So the two levers are the ones the second command just named: docker system prune returns the reclaimable bytes it reported, and deleting the cluster returns its image store — which is also what the layer-teardown note further down this page is about. Neither is a step you perform on a clean machine. Both are a great deal cheaper than discovering the shortfall halfway through a layer install.

Two platforms are supported: Apple Silicon macOS, and x86-64 Linux — including Windows through WSL2. Both are covered below, and the course's own continuous-integration matrix runs the lab profiles on x86-64 and ARM Linux on every change.

Use the same platform as your host

The cluster's node images are published for both architectures, and kind is explicit about the constraint:

NOTE: These node images support amd64 and arm64, both of our supported platforms. You must use the same platform as your host

So on Apple Silicon you install the ARM binaries and run ARM node images, and on an x86-64 machine you install the x86-64 ones. Mixing them does not produce a slower cluster; it produces containers that will not start.

One step either side of the floor​

The declared minimum is the machine the labs were measured against, so it is worth saying what each side of it actually means rather than quoting only the threshold.

At the declared minimum. The base cluster runs, and so do the synthetic-device layer, the queueing-and-simulated-fleet layer, the storage data-path layer and the operations layer — each one with headroom that was measured rather than estimated. Read that as it is meant: each layer was measured on top of the base, one layer at a time, which is how the modules use them. It is not a promise that all four fit at once, and no module asks you to try. One layer does not fit at all: the inference-serving layer was measured over the lab memory budget for this size, so at the minimum it prints a skip token, applies nothing and exits successfully. That is a deliberate fence rather than a failure, and the serving module is a read-along at this size instead of a run.

Under the declared minimum. Nothing degrades gracefully here, and it is better to know that in advance than to discover it. kind has one create subcommand and no node-add path, so the number of nodes is fixed when the cluster is created and cannot be changed afterwards — a smaller machine does not get a smaller cluster. It gets exactly the same cluster and then runs out of memory inside the container runtime's virtual machine. Nothing below the declared minimum has been measured, so the course makes no claim about it in either direction. Free disk is the one figure that does not behave like this, because it is not fixed when the cluster is created: a machine that is short of it can reclaim it, and the paragraph above says how.

At the recommended size. The inference-serving layer installs and runs, and the simulated node fleet is created at the larger target. Export SIZE=16 and the base profile builds a second worker. SIZE is an environment variable you export before you run a lab script; it accepts exactly 8 or 16, and the section that creates the cluster introduces it properly.

Per-layer memory and disk figures live in the course's measurement records rather than on this page, because a figure on a published page loses the conditions it was measured under. If you want your own number on your own machine, tools/measure.sh is the instrument that produced those records. It ships inside the lab repository you clone further down this page — as does every other tools/… and clusters/… path you will read here, all of them relative to that clone's root.

The container runtime​

Rancher Desktop, with the Moby (dockerd) container engine, is the one supported runtime. Install it, and in its Container Engine settings choose dockerd (moby) rather than containerd: kind's documented path and every script in the lab tree assume a Docker-compatible socket. Then give its virtual machine as much memory as your host can spare. The course's figures were measured with that virtual machine holding close to the whole declared minimum, and the one-profile-at-a-time rule below is what keeps a lab inside it.

Rancher Desktop installs two command-line tools that this page uses. One is the docker CLI, which every lab script asserts by name. The other is rdctl, Rancher Desktop's own control CLI, and rdctl shell <command> runs a command inside that virtual machine rather than on your laptop. The distinction matters more than it sounds: the node containers run on the virtual machine's Linux kernel, not on your host's, so anything you set on a kernel has to be set on the right one. One section further down depends on exactly that, and says which form to use on which platform.

Docker Desktop is not supported. Its licence terms make it the wrong default for a course anyone should be able to take, and the course deliberately documents and supports exactly one runtime — a second one doubles the surface every lab script has to work against and halves the chance that a failure you hit is one the course has already seen. The reason is written down here rather than left as a bare prohibition, because an unexplained prohibition is the one a reader works around.

Install the pinned tools​

Three tools are pinned, and two of them are pinned to an exact version for a reason worth reading before you reach for your package manager.

ToolPinned atWhy this exact version
kindexactly v0.33.0It is the only kind release carrying Kubernetes 1.37 node images. An older kind does not build a slightly different cluster — it cannot build this cluster at all, because the node image it needs does not exist in it.
kubectlthe v1.37 lineAsserted against the supported client/server skew window rather than against one exact build: a v1.37 server supports a client one minor either side, so 1.36, 1.37 and 1.38 are all accepted. This is subtler than an exact pin — a client inside the window is supported, which is not the same as identical, and a command that depends on a 1.37-only field will still fail on a 1.36 client. The window is what the lab helper enforces; the installs below fetch v1.37.0.
helmv3.8.0 or newer — either majorEvery addon layer renders a chart, and all four of them are pulled from OCI registries, so OCI support is required rather than optional. v3.8.0 is the release where it stopped being optional in Helm too: Helm's own v3.8.0 notes say OCI registry support "is now generally available. It has graduated out of being an experiment." Below that, the chart cannot be fetched at all. Above it, Helm 3 and Helm 4 are both fine — see the measurement below.

All three assertions live in one place — tools/pinned-bin.sh — and every script that touches a cluster sources it. No script re-implements a version check, so there is exactly one copy of each pin.

The three pins have three different shapes, and that is deliberate rather than untidy. kind is exact because exactly one release carries the node image. kubectl is a window because the supported skew window is the real property, and an exact pin would fail a correctly-configured machine. helm is a floor because what the layers need from Helm is a capability — OCI support — and a capability has a first version rather than a single correct one.

Helm 4 is fine, and that is measured rather than assumed. It matters because Helm 4 is now what most package managers and Rancher Desktop itself will give you. Both majors were run against every chart this course installs — the queueing chart, the three operations charts, and the device driver's chart at its pinned tag. They produced the same chart digest in every case, and a rendered object set that is identical once blank lines are stripped. Helm 4's only difference is one extra blank line per document, which nothing reads. So you do not need to hunt for a Helm 3.

On the machine this page was last checked against, all of these were installed at once:

$ ~/.rd/bin/helm version --short
v4.2.1+gd591a19
$ /usr/local/bin/helm version --short
v3.22.0+g144ca65
$ /opt/homebrew/bin/helm version --short
v4.2.3+g43e8b7f

All three clear the floor, so on this machine any of them would work. That was not true of the page you may have read before: this pin used to name one exact version, v3.19.0, and none of the three was it. The exact pin was wrong twice over — it rejected two Helm 4 copies that in fact render every chart here identically, and it named a version no layer in this course was ever run under. The layers were built and measured on Helm 4.2.3. The floor above is what was actually established, so it is what the lab scripts now assert.

The install block below fetches v3.22.0, and that is one of the two versions the measurement was taken on. The layers themselves were built on Helm 4.2.3; v3.22.0 is the Helm 3 that was run beside it, chart for chart, and found to resolve the same digests and render the same objects. Either would be defensible, and v3.22.0 is the one handed to you here because Helm 3 is still the major most clusters and most employers are on, and because a version you can compare against a colleague's is worth more than the newest one. Note that it is not the newest Helm 3 — v3.22.1 shipped on 2026-10-15 and has not been run against this course's charts, so it is accepted by the floor and not recommended by this page. If you already have a Helm above the floor, keep it; the block is for a machine that has none.

tools/pinned-bin.sh asserts this floor, and every layer that pulls a chart calls it before it fetches anything — so a Helm below the floor stops the layer with a FAIL: line naming the cause, rather than failing somewhere in the middle of an install.

Alongside those three, the lab scripts assert a handful of ordinary command-line tools by name and refuse to run without them: docker (which Rancher Desktop provides), git, jq, curl, tar, shasum or sha256sum, nc, python3, awk, sed and node. Most machines already carry all of them except jq, which is the one worth installing now rather than discovering is missing halfway through a layer install.

Where the binaries go, and whether you need administrator rights​

One variable names that directory. You set it here, the install block below writes into it, and every lab script further down this page reads the same variable — so there is one copy of the answer and nothing to keep in step by hand:

export LAB_BIN_PREFIX="${HOME}/.local/bin"
mkdir -p "${LAB_BIN_PREFIX}"

A directory you own is the default for one reason: nothing in the install has to elevate. The lab scripts genuinely do not care which directory the binaries are in — they read LAB_BIN_PREFIX — so a prefix that needs no administrator rights costs you nothing and removes a whole class of problem.

/usr/local/bin is the supported alternative. It is already on your path, which is convenient when you type kind yourself, and it is owned by root, which means every move below becomes sudo mv. Two things change with that choice, and both are worth reading before you make it:

If you install into a system directory, authenticate before you paste

You need administrator rights on this machine. Check before you start rather than halfway through:

sudo -v

That prompts for your password and exits successfully if you have them. If it answers sudo: a password is required and you do not have one — a managed laptop, a shared machine — use the prefix you own instead. Nothing later on this page is lost by it.

Run it on its own, and answer the prompt, before you paste anything. It does two jobs. It answers the question above, and — quoting sudo's own manual — it "extends the sudo timeout for another 5 minutes by default", caching your credentials for that terminal, so the sudo mv lines in the block that follows do not prompt at all. The second job is the one that matters, and this is why.

A password prompt that arrives partway through a paste can be handed the next pasted line as the password. That line is then consumed rather than run. In the block below, the next command after the first sudo mv is the curl that fetches kubectl — so losing it means kubectl is never downloaded, the three commands after it fail against a file that does not exist, and you are left with the pinned kind installed and kubectl silently absent. That half-installed state is the real harm here, because it is exactly the state the next section punishes: a LAB_BIN_PREFIX pointing at a directory that holds some of the pinned tools and not others.

Whether it fires at all depends on your terminal, which is the reason to prevent it rather than to watch for it. A terminal that implements bracketed-paste protection holds the remaining input instead of feeding it to the prompt; one that does not, does not. You cannot tell which you have from inside the block, and this page will not guess on your behalf.

So: run sudo -v on its own and the prompt never arrives mid-paste. Two cases where it can anyway — the five minutes run out while a download is slow, or your machine's policy does not cache credentials at all, which sudo's manual is explicit is possible. If a prompt appears while the block is running, stop sending input, answer it, and run the remaining lines one at a time.

The ( set -e ) subshell the block runs inside is the backstop for all of this. It stops at the first failure, so a swallowed line becomes a block that visibly stops rather than an install that quietly finished early — and the default prefix above means none of it arises.

Work out your architecture first​

Both install blocks build their download URLs out of one variable, so this step runs on its own and you read its output before going any further. It works your architecture out from the machine rather than asking you to choose, which is the same-platform-as-host rule above enforced instead of advised:

ARCH="$(uname -m)"
case "${ARCH}" in
  x86_64)        ARCH=amd64 ;;   # Intel or AMD — Linux, WSL2, or an Intel Mac
  aarch64|arm64) ARCH=arm64 ;;   # Apple Silicon, or ARM Linux
  *) echo "unsupported architecture: ${ARCH}" >&2; unset ARCH ;;
esac
export ARCH
echo "installing for ${ARCH:-<unsupported — stop here>}"

If that last line prints <unsupported — stop here>, stop. This course supports x86-64 and ARM64 and nothing else. Every URL in the blocks below is built out of ARCH, so with ARCH unset each one resolves to an address that does not exist and curl reports a missing file — which sends you looking for a broken link on someone else's server instead of at an unsupported CPU. The echo is there to be read, not skipped.

Linux, and Windows through WSL2​

This one runs as a block. It fetches each asset, checks it against the checksum its publisher ships beside it, and only then moves it into your prefix.

It runs inside ( … ) with set -e, and that is load-bearing rather than decorative. A subshell that exits on its first failure cannot carry on past a checksum that did not match — and because it is a subshell rather than your shell, exiting it does not close the terminal you pasted it into:

(
  set -euo pipefail
  : "${ARCH:?stop — architecture not detected, see the step above}"
  : "${LAB_BIN_PREFIX:?stop — install prefix not set, see the step above}"

  curl -fsSLo ./kind "https://kind.sigs.k8s.io/dl/v0.33.0/kind-linux-${ARCH}"
  curl -fsSLo ./kind.sha256sum "https://github.com/kubernetes-sigs/kind/releases/download/v0.33.0/kind-linux-${ARCH}.sha256sum"
  echo "$(awk '{print $1}' ./kind.sha256sum)  ./kind" | sha256sum -c -
  chmod +x ./kind
  mv ./kind "${LAB_BIN_PREFIX}/kind"

  curl -fsSLO "https://dl.k8s.io/release/v1.37.0/bin/linux/${ARCH}/kubectl"
  curl -fsSLo ./kubectl.sha256 "https://dl.k8s.io/release/v1.37.0/bin/linux/${ARCH}/kubectl.sha256"
  echo "$(cat ./kubectl.sha256)  ./kubectl" | sha256sum -c -
  chmod +x ./kubectl
  mv ./kubectl "${LAB_BIN_PREFIX}/kubectl"

  curl -fsSLo ./helm.tar.gz "https://get.helm.sh/helm-v3.22.0-linux-${ARCH}.tar.gz"
  curl -fsSLo ./helm.tar.gz.sha256sum "https://get.helm.sh/helm-v3.22.0-linux-${ARCH}.tar.gz.sha256sum"
  echo "$(awk '{print $1}' ./helm.tar.gz.sha256sum)  ./helm.tar.gz" | sha256sum -c -
  tar -xzf ./helm.tar.gz
  mv "./linux-${ARCH}/helm" "${LAB_BIN_PREFIX}/helm"

  rm -f ./kind.sha256sum ./kubectl.sha256 ./helm.tar.gz ./helm.tar.gz.sha256sum
  rm -rf "./linux-${ARCH}"
)

Those last two lines are not tidiness. The archive and the three checksum files stay in your working directory otherwise, nothing removes them for you, and they are not small.

Each sha256sum -c - line prints OK and the block carries on, or prints FAILED and the subshell stops there. That stop is what set -e buys you: without it the next two lines would go on to chmod a binary that did not match its published sum and move it into your prefix, and nothing afterwards would tell you. If one fails, delete the download and fetch it again.

If you chose /usr/local/bin, change each of the three mv lines to sudo mv, and run sudo -v on its own first so that no password prompt can arrive in the middle of the paste — the warning above is why that ordering matters.

macOS​

macOS ships shasum rather than sha256sum, which is the only difference between this block and the one above:

(
  set -euo pipefail
  : "${ARCH:?stop — architecture not detected, see the step above}"
  : "${LAB_BIN_PREFIX:?stop — install prefix not set, see the step above}"

  curl -fsSLo ./kind "https://kind.sigs.k8s.io/dl/v0.33.0/kind-darwin-${ARCH}"
  curl -fsSLo ./kind.sha256sum "https://github.com/kubernetes-sigs/kind/releases/download/v0.33.0/kind-darwin-${ARCH}.sha256sum"
  echo "$(awk '{print $1}' ./kind.sha256sum)  ./kind" | shasum -a 256 -c -
  chmod +x ./kind
  mv ./kind "${LAB_BIN_PREFIX}/kind"

  curl -fsSLO "https://dl.k8s.io/release/v1.37.0/bin/darwin/${ARCH}/kubectl"
  curl -fsSLo ./kubectl.sha256 "https://dl.k8s.io/release/v1.37.0/bin/darwin/${ARCH}/kubectl.sha256"
  echo "$(cat ./kubectl.sha256)  ./kubectl" | shasum -a 256 -c -
  chmod +x ./kubectl
  mv ./kubectl "${LAB_BIN_PREFIX}/kubectl"

  curl -fsSLo ./helm.tar.gz "https://get.helm.sh/helm-v3.22.0-darwin-${ARCH}.tar.gz"
  curl -fsSLo ./helm.tar.gz.sha256sum "https://get.helm.sh/helm-v3.22.0-darwin-${ARCH}.tar.gz.sha256sum"
  echo "$(awk '{print $1}' ./helm.tar.gz.sha256sum)  ./helm.tar.gz" | shasum -a 256 -c -
  tar -xzf ./helm.tar.gz
  mv "./darwin-${ARCH}/helm" "${LAB_BIN_PREFIX}/helm"

  rm -f ./kind.sha256sum ./kubectl.sha256 ./helm.tar.gz ./helm.tar.gz.sha256sum
  rm -rf "./darwin-${ARCH}"
)

A checksum fetched over the same connection as the thing it describes does not defend you against a compromised publisher. It does defend you against a truncated download, a corrupted one and a silently reissued asset, which is strictly more than no check at all. The course's own continuous-integration jobs gate every one of these assets the same way.

Check what you actually installed​

type -a answers which copies exist, which is a different question from which version each one is. The pins are versions, so check versions — and check them at the prefix the lab scripts will read, because that is the copy that will run:

"${LAB_BIN_PREFIX}/kind" --version
"${LAB_BIN_PREFIX}/kubectl" version --client
"${LAB_BIN_PREFIX}/helm" version --short

Expect kind version 0.33.0, a Client Version: on the v1.37 line, and a helm version of 3.8.0 or newer in either major — v3.22.0+g144ca65 is what the block above installs, and a v4.2.3+g43e8b7f you already had is equally fine. Helm appends its own build hash, so the +g… suffix is never a mismatch. Unlike the other two, this one is also asserted by the lab scripts themselves, so a Helm below the floor stops a layer rather than passing quietly here. A no such file or directory names the one tool that did not land, which is a great deal more useful than a cluster failing an hour later for a reason that looks unrelated to an install you thought had finished.

A tool that is installed is not always the tool that runs​

This is the first failure most readers hit, and it is not an install problem. Installing the pinned kind is not the same as the pinned kind being the one that runs: on a machine that already does other work, whichever copy resolves first on your path wins, and a stale copy answers for a different cluster entirely.

Ask the machine which copies it can see, and in what order:

type -a kind
type -a kubectl
type -a helm

On a machine that does nothing but this course, that prints two lines or three. On a machine that does other work it prints many more, and the many are not a problem to fix. The machine this page was last checked against answers with eight entries for kind, eleven for kubectl and seven for helm — a PATH that lists the same directories several times over, which is ordinary on a laptop that has had a few package managers and a container runtime installed on it. Neither the count nor the duplicates matter. Only the first line matters, because that is the copy that answers when you type the name yourself:

type -a kind | head -1

And there is no "good" answer to look for here, which is worth saying because a command with no pass condition is a command a reader stares at. This step is diagnostic, not a gate: it tells you which directories hold a copy, so that a version mismatch later has an address rather than a mystery. The gate was the version check in the previous section.

For the lab scripts, not even the first line matters. They do not consult your PATH at all: each one prepends LAB_BIN_PREFIX to PATH before it does anything else, so the copy in that directory is the one they run, whatever else is installed and in whatever order. That is the whole reason the variable exists. You set it during the install above; set it again in every new terminal, because an export does not outlive its shell.

So the two questions come apart, and it is worth keeping them apart: your PATH decides what you get at the prompt, and LAB_BIN_PREFIX decides what the scripts get.

When a pin does not match, tools/pinned-bin.sh fails by name and prints the resolution order it measured on your machine — which is the diagnosis, not just an error. This is the real output, captured from a machine whose LAB_BIN_PREFIX pointed at a directory holding a stale kind:

FAIL: kind resolves to '0.32.0' but this course pins v0.33.0,
      the only kind release carrying Kubernetes 1.37 node images.
      Install it and make sure it resolves first:
        brew install kind     # then: LAB_BIN_PREFIX=$(brew --prefix)/bin bash <script>
      Resolution order on this host: kind is /usr/local/bin/kind kind is /Users/you/.local/bin/kind kind is /usr/local/bin/kind kind is /Users/you/.local/bin/kind kind is /Users/you/.local/bin/kind kind is /Users/you/.local/bin/kind kind is /opt/homebrew/bin/kind kind is /usr/local/bin/kind kind is /opt/homebrew/bin/kind

That resolution-order line is long and repetitive, and both of those are expected — it is type -a on a real machine, printed on one line. Read it for the set of directories it names, not for its length: here there is a kind in three of them, and the one the script actually ran is the first.

The remedy is the line above it: point LAB_BIN_PREFIX at the directory holding the pinned copy. Removing or reordering the other copies would also work and is more effort for the same result. Installing a fourth copy is the one response that makes things worse.

Get the lab tree​

The labs live in their own public repository. Clone it and work from its root — every command on this page and in every lab is relative to that root:

git clone https://github.com/SchoolofXOps/313-k8sai-labs.git
cd 313-k8sai-labs

Create the base cluster, verify it, tear it down​

These environment variables carry across every lab. Export them rather than passing them per command, and export them again in every new terminal — an export lives exactly as long as the shell that ran it, so a reader who opens a second window, or comes back the next day, has none of them:

export LAB_BIN_PREFIX="${HOME}/.local/bin"    # the prefix you installed into above
export SIZE=8                                 # 8 or 16; defaults to 8
export KUBECONFIG=/tmp/grid-core.kubeconfig   # isolated, so the labs never touch another cluster

SIZE accepts exactly 8 or 16 and nothing else. It decides the worker count, the lab memory budget and the simulated fleet size, and all three are read from the course configuration rather than from a literal in a script. The base profile is three scripts, and all three must be run at the same SIZE — that is the whole reason it is an exported variable and not an argument.

What each size builds, so that you can count the nodes yourself. At SIZE=8 the cluster is one control-plane node and 1 worker, so kubectl get nodes must list 2. At SIZE=16 it is one control-plane node and 2 workers, so it must list 3. Both counts are read from the course configuration, the same place the create script reads them from, so they cannot drift away from the cluster you actually get. Learn the one for your size: a section further down is about a cluster that comes up short while every tool reports success, and the count is what you check it against.

KUBECONFIG deliberately points into /tmp, which is what keeps the labs away from whatever your ~/.kube/config already holds. The side effect is that the file and the cluster have different lifetimes: the cluster lives in containers and survives a reboot, and a file in /tmp is not guaranteed to. So if kubectl starts saying it cannot reach the cluster while kind get clusters still lists it, the kubeconfig is what went missing, and one command writes it back from the live cluster:

kind export kubeconfig --name grid-core --kubeconfig /tmp/grid-core.kubeconfig

It reads the cluster and regenerates the file. It creates nothing and deletes nothing, so it is safe to run at any point you are unsure.

bash clusters/grid-core/create.sh      # creates it, or reuses an existing one and exits
bash clusters/grid-core/verify.sh      # read-only; asserts nodes, version, health and feature gates
bash clusters/grid-core/teardown.sh    # deletes the cluster and everything on it

Every script in the lab tree reports the same way: on success exactly one line beginning OK:, and on failure a line beginning FAIL: naming both what went wrong and the remedy. If you see neither, the script did not finish.

When a cluster from this course is already running

create.sh is idempotent. If the cluster already exists it says so, reuses it and exits successfully:

kind cluster 'grid-core' already exists — reusing it.

That is what you want when you come back to a lab the next day, and it is a trap in exactly one case. Node count is fixed at the moment a cluster is created — kind has one create subcommand and no node-add path — so a cluster created at the other SIZE is reused at its own node count, and the create still exits successfully. Nothing in that output is wrong; it simply is not telling you about a size you changed since.

verify.sh is what catches it, because it counts the real nodes on the cluster against the SIZE you asked for. This is its output, measured on a cluster created at SIZE=8 and verified at SIZE=16:

FAIL: SIZE=16 expects 3 real nodes (1 control-plane + 2 worker(s)), found 2 on the cluster.
      The count was READ from the cluster, not taken from SIZE, so this is a real disagreement.
      Simulated nodes are excluded from it and are not the cause: 0 carry the type=kwok label.
      Either verify at the size this cluster was CREATED at, or recreate at this one:
        SIZE=16 bash .../clusters/grid-core/teardown.sh && SIZE=16 bash .../clusters/grid-core/create.sh
      Node count is create-time-immutable — kind has no node-add path, so it cannot be adjusted in place.

Run the teardown and the create again at the size you want. The three Kubernetes feature gates this profile carries behave the same way and for the same reason — they cannot be enabled on a cluster that already exists — so a reuse prints a note naming them and the one-time recreate command rather than pretending they are on.

One cluster profile at a time

The declared minimum has no room for two clusters. The base profile's create path refuses rather than racing a conflicting lab profile, and it prints the command that resolves the conflict. If you have a cluster of your own running from other work, it is left alone — but you will get a note saying it competes for the same memory, with the command to delete it. Take that note seriously; the next section is what happens when you do not.

When the cluster comes up with fewer nodes than you asked for​

This failure is worth reading before you meet it, because the one thing it does not do is report itself. kind can print that it joined every node and exit successfully, and kubectl wait --for=condition=Ready node --all can pass, while the cluster has fewer nodes than you asked for — because the nodes that are present really are ready. The symptom you see is "my cluster came up with one node and nothing reported an error", which is close to unsearchable.

The profile's own verify.sh catches it, because it counts the nodes against the size you asked for. You can also catch it by hand, which is worth knowing because it takes one command and no scripts:

kubectl get nodes

Count the lines. At SIZE=8 that must be 2, and at SIZE=16 it must be 3, exactly as the previous section said. Every node it lists will say Ready, which is the whole difficulty: the signal is the number of lines and not the state of any one of them.

The cause is in the missing node's kubelet journal:

$ docker exec grid-core-worker journalctl -u kubelet --no-pager -n 12
... Registration of the raw container factory failed: inotify_init: too many open files
... "Failed to start cAdvisor" err="inotify_init: too many open files"
... kubelet.service: Main process exited, code=exited, status=1/FAILURE

Not memory — inotify instance exhaustion. Every kubelet needs a share of the host kernel's inotify instances, and because kind runs its nodes without user namespaces, every kubelet on the machine counts against the same limit. The limit is therefore a property of the machine and not of your cluster.

The fix is the rule this page already gave you: one cluster profile at a time. This was measured on a clean machine, and the result is not the obvious one. Neither lab size needs any kernel tuning when it is the only cluster running — the larger size fits under the kernel's default limit with room to spare. The failure appears when a second, unrelated cluster is resident at the same time and the two together ask for more instances than the default allows. So delete the other cluster, or tear down the other profile, and the nodes join.

If you genuinely need something else running alongside, raising the limit is the escape hatch rather than a step everyone performs. These are the values kind's own documentation recommends.

The setting belongs to the kernel the node containers actually run on, which is not always your laptop's kernel, so there are two forms of the same command and the one you need depends on where that kernel is. On macOS, and on Windows through WSL2, the container engine runs inside Rancher Desktop's virtual machine, and rdctl shell is how you reach into it:

rdctl shell sudo sysctl -w fs.inotify.max_user_instances=512
rdctl shell sudo sysctl -w fs.inotify.max_user_watches=524288

On a Linux host where the container engine runs against the host kernel directly, there is no virtual machine to reach into and the same two settings go to the host:

sudo sysctl -w fs.inotify.max_user_instances=512
sudo sysctl -w fs.inotify.max_user_watches=524288

If you are not sure which case you are in, ask both kernels their version and compare:

uname -r              # your host
rdctl shell uname -r  # the virtual machine, if there is one

Two different answers means the engine is in a virtual machine and the rdctl shell form is yours. On the machine this page was last checked against, the host answered 25.5.0 and the virtual machine answered 6.18.36-0-virt — a Darwin kernel and a Linux one, which is as clear as that distinction gets.

That raise does not survive a restart of the kernel you set it on. Making it permanent is a provisioning question this course does not answer, which is another reason the one-profile-at-a-time rule is the recommendation and this is the exception.

The layers you apply onto the base cluster​

Almost everything a later module needs is a layer applied onto the running base cluster, not a cluster of its own. Each layer is the same three scripts in its own directory, and each module's lab page tells you which layers it needs.

LayerApply withCheck it withWhat it adds
Synthetic devicesclusters/grid-core/addons/dra/create.shclusters/grid-core/addons/dra/verify.shA device driver publishing synthetic devices, a device class, and the claim lifecycle end to end. These are simulated devices, never accelerators — the driver's own output calls them otherwise, and the lab pages caption that where it appears.
Queueing and a simulated fleetclusters/grid-core/addons/kueue-kwok/create.shclusters/grid-core/addons/kueue-kwok/verify.shQuota, queues, gang admission and topology-aware scheduling, plus a fleet of simulated nodes to admit against.
Storage data pathsclusters/grid-core/addons/dataplane/create.shclusters/grid-core/addons/dataplane/verify.shFour storage paths side by side, and the harness that measures them.

Operationsclusters/grid-core/addons/ops/create.shclusters/grid-core/addons/ops/verify.shA metrics collector, a dashboard surface and a cost tool.

Every layer ships the same three scripts the base profile does — create.sh, verify.sh and teardown.sh — so the OK: line you learned to look for above is available for a layer too. Run the layer's verify.sh after you apply it; it is read-only and changes nothing.

One ordering constraint is not free. Apply the synthetic-device layer before the queueing layer. The queueing layer's configuration maps device classes by name, and a configuration naming a device class that does not exist fails in complete silence — no log line, no status condition, nothing. The queueing layer checks for the device class up front and refuses rather than installing into that state, which is why the order is stated here instead of being left to be discovered.

Two scripts share the name teardown.sh and do very different amounts of damage

Read which one you are about to run.

ScriptWhat it removes
clusters/grid-core/addons/<layer>/teardown.shThe layer only. The base cluster keeps running and everything else on it survives.
clusters/grid-core/teardown.shThe whole base cluster, and every layer and workload on it.
clusters/grid-sandbox/teardown.shThe sandbox cluster — and then it recreates and verifies the base cluster, so you are never left with no cluster. It is the only teardown in the course that creates anything.

A layer teardown does not give you your disk back. Removing a layer removes its objects; the container images it pulled stay in the cluster's image store, and they accumulate as you work through modules. That matters against a 50 GB declared minimum. Deleting the cluster is what reclaims those bytes, so if disk is tight, tear the cluster down between modules rather than only tearing down layers.

The sandboxed-runtime cluster​

One module needs a cluster the base profile cannot become: its container runtime has to know about a sandboxing runtime handler, and that is written into the node image when the image is built, not configured afterwards. So it is the one dedicated profile in the course, with the same three scripts:

Change KUBECONFIG first. Each profile keeps its own, and the scripts take whatever you have already exported rather than overriding you — so if you leave the base profile's value in place the sandbox cluster's context is written into the base profile's file and the two stop being separate:

export KUBECONFIG=/tmp/grid-sandbox.kubeconfig

bash clusters/grid-sandbox/create.sh
bash clusters/grid-sandbox/verify.sh
bash clusters/grid-sandbox/teardown.sh     # deletes it, then rebuilds and verifies the base

When you go back to the base profile, set KUBECONFIG back to /tmp/grid-core.kubeconfig.

Because only one profile runs at a time, creating this one tears the base cluster down first. Its teardown brings the base back and checks it, so the loan is repaid without a second command from you.

Where your work lives between labs​

Your work accumulates in a Git repository, never in a running cluster. The lab tree carries it at grid-platform/, it grows in place as you work through the modules, and that is deliberate: a cluster is something you will delete and recreate many times, and anything that only exists inside one is lost the first time you do.

Three steps take a synced working tree to a reference point you can come back to or share. They are written here rather than hidden inside a script, because the last one writes to a public repository and the course's own sync tool stops short of it for exactly that reason — it produces a tree and does not commit, publish or tag:

git add -A grid-platform
git commit -m "m4: devices requestable by attribute"
git push --follow-tags

Tag a reference point when a module tells you to, and push the tag with the commit — --follow-tags is what sends both, and a tag left behind on your machine is not a reference point anyone else can reach.

What you do not need​

  • No accelerator. Nothing on the core path needs one. Where a claim genuinely requires real hardware, the lab says so and is tagged for it.
  • No cloud account. Every core-path lab runs on your laptop.
  • No registry login. Every image the labs pull is public and pinned by digest.
  • No second scheduler, no bundled monitoring distribution and no serverless layer. The course installs none of them, and each lab page says what it installs and what it leaves out.
