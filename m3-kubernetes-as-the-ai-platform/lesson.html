Module 3 — Kubernetes as the AI Platform

Every platform team that takes on AI work gets asked the same three questions in its first month. Why Kubernetes, when the research team already has a Slurm cluster? Which of the forty projects on the vendor slides should we actually run? And is our cluster "AI-ready"? This module gives you an honest answer to each one, and a way to keep answering them after the course ends, because the answers change every few months.

You will not install anything in this module. You will read: how Kubernetes came to carry AI workloads, where the upstream work happens, what the alternatives are good at, and how to grade a project by the evidence for it rather than by the confidence of its announcement. Then you will audit a real cluster against the published AI conformance requirements, write down every gap you find, and write the design document the rest of the course builds against.

  • Core path: ~1.5 h
  • Advanced brief: 0.5 h (labelled, optional)

How Kubernetes became the substrate for AI workloads​

Kubernetes was built for a particular kind of tenant: stateless web services that start in seconds, grow by adding identical copies through a Deployment, and do not care which machine they land on. Think of a hotel built for business travellers. Every room is the same, guests check in and out all day, and the front desk can hand any guest any room. AI workloads arrived like a touring orchestra. They need specific rooms next to each other, they bring equipment that only fits in some of them, and the whole group either checks in together or not at all.

The project did not get rebuilt for the orchestra. It grew the missing pieces one at a time, and you can read its history as a list of what AI workloads broke:

  1. Extended resources and device plugins. A node could advertise a count of something, such as nvidia.com/gpu: 8, through a vendor's device plugin, and a Pod could ask for one. This made accelerators schedulable at all, as opaque integers: the scheduler could count devices but knew nothing about them.
  2. Operators and Kubeflow. Training jobs needed more than a Job, so projects wrote their own controllers with their own CRDs, one per framework, each with its own idea of a worker group.
  3. Batch scheduling and queueing. Volcano brought a second scheduler built for batch work. Kueue took the other road: it decides when a workload may start, against quota, and leaves the default scheduler to place its Pods.
  4. Dynamic Resource Allocation. Devices stopped being integers. A driver publishes what each device is, in ResourceSlice objects, and a Pod's ResourceClaim asks for a device by its attributes.
  5. Workload-aware scheduling in the core. The scheduler itself is learning to treat a group of Pods as one unit, through the core Workload and PodGroup objects.

Dynamic Resource Allocation is GA in Kubernetes 1.34, API resource.k8s.io/v1. That is the release where asking for a device by what it is, rather than by how many, became part of the core API that every conformant cluster serves.

The group-scheduling step is the one still in motion. In Kubernetes 1.37 the core Workload and PodGroup objects are served at scheduling.k8s.io/v1beta1, behind one feature gate, GenericWorkload, which is beta and off by default. Off by default means it is off in almost every cluster you will meet at work. The course's base cluster turns it on, so you can read the API in the lab, and Module 5 shows what it does. Module 4 makes devices requestable by attribute, which is the first gap your audit will find.

Where the upstream work happens, and how to track it​

Nothing in this module will stay true by itself. The useful skill is knowing where to look when a release lands, so you can check a claim in ten minutes rather than trust a blog post for a year. It helps to think of Kubernetes as a city with a planning office. Proposals are filed at one desk, decisions are recorded at another, and what actually got built is a third thing again. You learn to read all three.

Who does the work. Kubernetes is organised into Special Interest Groups, the SIGs, which own code, and Working Groups, which run for a fixed purpose across several SIGs and then close. Three of them matter most for this course:

  • WG Serving concluded in February 2026. Among the projects it sponsored is the Gateway API Inference Extension, and one of its workstreams was Dynamic Resource Allocation. This course teaches both.
  • WG Batch is active and is where Job, JobSet and Kueue work is coordinated.
  • The AI Gateway Working Group was added to the Kubernetes community repository, with its charter, in September 2025, and announced on the Kubernetes blog in March 2026. It works on how gateways in front of model servers should behave.

Where the decisions are written down. Three artifacts, in the order they appear in a feature's life:

ArtifactWhere it livesWhat it tells you
A KEP (Kubernetes Enhancement Proposal)kubernetes/enhancements, one folder per proposal, with a kep.yamlwhat a SIG intends: the target stage and the release it is aiming at
A feature gate's pagekubernetes/website, one file per gate, with stage, defaultValue, fromVersion and toVersion in its frontmatterwhat each release shipped, and whether it is on unless you switch it on
The release changelogkubernetes/kubernetes, CHANGELOG/CHANGELOG-1.NN.md, with a pull request number per changethe exact change, and the code that made it

The deep dive reads one of each, at a pinned commit, and turns the readings into evidence.

Three things people confuse. Participating in a SIG means you show up and contribute. Maintaining a project means you have merge rights in its repository. Owning an API means your SIG decides how that API group changes. A vendor can do the first for years without the second or third, and a slide that says a vendor "drives" a Kubernetes feature usually means the first. When it matters, read the OWNERS file in the repository and the owning-sig line in the KEP.

The alternatives to Kubernetes, compared fairly​

Kubernetes is not the only way to run AI workloads, and pretending it is costs you credibility with the people who run the alternatives. Think of the choice the way a city chooses between a bus network, a metro and a taxi fleet. Each one is the right answer for some trips. You want the one that fits the journeys you actually have, and a city with a working metro does not tear it up because buses exist.

HPC estates hybridise rather than convert. A site with years of Slurm job scripts, accounting and trained users does not move to Kubernetes in one step, and usually should not. What happens instead is a bridge: Slinky runs Slurm's own components as Kubernetes workloads, and its scheduler lets Slurm decide placement for Pods that opt in. The batch users keep their tool, and the platform team gets one fleet to operate.

A decision framework. Ask four questions about the estate in front of you, in this order:

  1. How many teams share the accelerators? One team on a fixed set of machines gets little from a multi-tenant control plane. Several teams competing for scarce devices is the problem Kubernetes with a queueing layer such as Kueue is built for.
  2. Does the same fleet serve models as well as train them? Pure batch on a fixed estate is what Slurm has done well for decades. A fleet that must also run long-lived inference services, with readiness probes, rollouts and request routing through a Gateway API implementation, is where Kubernetes earns its cost.
  3. How many models, behind how many endpoints? One model behind one endpoint, with steady traffic, is a job for a managed endpoint or a single server. Dozens of models with different owners, rollouts and traffic is a platform problem.
  4. Who will operate it? A Kubernetes AI platform needs people who can run it. A team without them may be better served by a managed platform, paying in money and lock-in instead of in staff.

When Kubernetes is the wrong answer. A single team on a static cluster. Pure HPC batch, where nothing needs to be served. One model behind one endpoint. In each of those cases the control plane you would run costs more than it saves, and saying so is part of the job.

The landscape, graded by evidence​

Before the grading, one sentence, because it is the claim this part of the course is most often misread as making:

CNCF's Certified Kubernetes AI Conformance certifies platforms, not people. It is not a Kubernetes certification for you, and no AI-specific Kubernetes certification for engineers exists.

That last part is a statement about CNCF's own catalogue of certifications for individuals, read on a dated page: it lists none that is AI-specific for Kubernetes engineers.

Here is what the programme is. It certifies a vendor's platform, per product and per configuration, and a platform must already be Kubernetes-conformant before it can be certified AI-conformant. The requirements are a checklist, one file per Kubernetes version, in CNCF's cncf/k8s-ai-conformance repository. The checklist for 1.37, read at commit c64e5bc8085da207715df96e458f2c6585c9f53e, lists 15 requirements, 8 MUST and 7 SHOULD, across accelerators, networking, scheduling and orchestration, observability, security and an operator category.

The list moves between versions, and one item shows how. The DRA-support item was SHOULD in the 1.33 checklist, MUST in the 1.34 and 1.35 checklists, and is absent from 1.36 on, because DRA is core Kubernetes.

The programme was launched at KubeCon North America in November 2025, as reported by the trade press at the time. Its repository held 19 certified submission directories at its last commit on or before 2025-11-30, and 31 at its last commit on or before 2026-03-31. Those are submission directories, not products: a product certified at two Kubernetes versions has two directories, so the numbers count certifications, never vendors. From the 1.37 checklist, the programme recommends automated tests as evidence for the requirements that have them, beside the documentation-backed self-assessment that covers the rest.

What the published requirements say​

Each requirement is a sentence of intent with a level. A MUST requirement says the platform has to offer a capability: a way to schedule a group of Pods all at once, such as a PodGroup and a scheduler that honours it, or a way to expose accelerator metrics. A SHOULD requirement says it is recommended. Some MUST requirements are conditional, such as cluster autoscaling, which a platform without node groups can mark as not applicable with a written justification. The requirements say what a platform offers. They do not say how well it works, on how large a fleet, or on which hardware.

What is independently verifiable today​

Some items can be checked by anyone with access to a cluster, using read-only commands: whether an API group is served, whether a ResourceSlice exists, whether a RuntimeClass is defined, whether a metrics API is registered. You have just done exactly that in the lab, and your gap report is the result. Other items cannot be checked from outside: that a vendor's driver manages accelerators correctly, or that its networking is fast, needs the hardware and a test you design. From 1.37, automated tests exist for some items and are recommended, not required, so a submission may or may not carry them.

What is vendor marketing​

A certified platform's submission is the vendor's own self-assessment, reviewed by the programme against the checklist. Read it the way you read any vendor document: as a claim with links. When a press release says a product is "certified for AI", what it means is that one product, in one configuration, at one Kubernetes version, filed a checklist that was accepted. It does not mean the product is faster, cheaper or easier than an uncertified one, and the programme makes no such claim.

What it does not guarantee​

It does not guarantee that a workload which runs on one certified platform runs unchanged on another, because the requirements name capabilities, not the APIs that deliver them. It does not guarantee performance, isolation between tenants, or support. It does not certify the version or configuration you run unless that exact one was submitted. And it certifies nothing about you: no course, lab or document in this course confers a certification, a conformance status or a credential of any kind.

The graded landscape​

The table below grades every tool and API this course names, so you can tell a settled API from an announcement before you build on it. Each entry gets three marks: maturity, read from a release artifact; a recommendation, which says what this course's evidence supports you doing with it; and the evidence grade of the fact behind the marks. The criteria for every mark are printed first, so you can check each grade yourself, and in the lab you do exactly that for six of the entries. The decision briefs that follow compare the projects in each category on the same columns as the alternatives table above, and each one names the module that goes deeper.

Maturity. What has shipped, read from a release artifact and never from an adjective — resource.k8s.io/v1 served by Kubernetes 1.34, say, or jobset.x-k8s.io/v1alpha2 at JobSet v0.12.0.

  • shipped-and-stable — a GA or v1 API served at a named release tag, or a project at 1.0 or later with a stable API.
  • shipped-and-immature — an alpha or beta API group, a beta feature gate that is off by default, or a release of a project before 1.0.
  • announced-or-roadmap — no release artifact exists.

Recommendation. What this course's evidence supports you doing with it.

  • bet-on-it — shipped-and-stable, AND governed upstream (a Kubernetes SIG or the CNCF), AND taught as a lab in this course.
  • pilot-it — shipped but immature, or governed by a vendor with a released artifact.
  • read-it-fluently — announced, taught only as a BRIEF here, or outside this course's install path.

Evidence grade. The confidence of the claims-ledger entry the row names, with the date it was read.

  • verified — the fact was read from the artifact the ledger entry names.
  • cited — the fact rests on a published source that was read but not independently reproduced, such as a product page or a press release.
  • unverified — this course pins no version for the entry, so its release cell sends you to the project's own releases page.

How the definitions are applied.

  • Where an entry meets both maturity definitions, the API it serves decides. A v1 API in a project still numbered 0.x is shipped-and-stable (LeaderWorkerSet serves leaderworkerset.x-k8s.io/v1 at v0.11.1), and a 1.0 project serving an alpha or beta API is shipped-and-immature (kagent v1.0.0 serves api.kagent.dev/v1alpha3). An entry with several APIs is graded by the least settled one a workload has to use.
  • The project's release number decides only for an entry that serves no Kubernetes API of its own.
  • An entry with no public release artifact you can open at a version, such as a commercial product, a managed cloud service or a certification programme, is graded announced-or-roadmap. This axis grades what you can read at a version, not whether a vendor sells the product today.
  • Where an entry meets both the pilot-it and the read-it-fluently definitions, read-it-fluently applies, because this course gives you no lab to pilot it from.

The platform design document​

A design document is the drawing the builders work from. Without one, every module of this course would make its own decisions about who the tenants are and which team owns which layer, and the decisions would contradict each other by Module 8. With one, every later module has an address to build at and a list of decisions it is expected to make.

The platform in this course has three tenants, each with its own way of using accelerators:

  • research runs training and fine-tuning experiments. It needs groups of Pods placed all at once and can wait in a queue.
  • data prepares datasets in batch. It mostly needs CPU and fast storage, and its work can be interrupted.
  • product serves models to users. It needs capacity that is there when traffic arrives, and it cannot wait in a queue.

They map onto the four workload classes from Module 2: data preparation, training and fine-tuning, inference and agents. The document records that mapping, the capabilities the platform offers today and the module that delivers each missing one, the platform's layers with an owner for each, the boundaries between the platform team and the teams it serves, and the decisions this module deliberately does not make. How much quota each tenant gets is one of those deferred decisions: it belongs to Module 5, where the objects that enforce quota arrive.

You write the document yourself, in the lab's platform design section, and commit it to your repository beside the gap report and your grading of the landscape. From this module on, when a later module adds a layer, it is filling in a row of this document.

Confidential and sovereign AI workloads​

Advanced brief, optional. No lab and nothing written to your repository.

Some workloads carry data the platform's own operators must not see: medical records, a customer's proprietary model, data that may not leave a country. Think of it as renting a safe-deposit box inside a bank. The bank runs the building, the guards and the vault, but the box is designed so the bank's staff cannot open it. The question is always how far that design actually goes.

GPU confidential-computing modes can reduce host visibility into protected workload data, subject to accelerator mode, firmware, attestation flow, driver stack, data path and declared threat model. They do not make the Kubernetes platform confidential.

That sentence carries every condition because each one can undo the protection on its own. The accelerator has to run in its confidential mode, on firmware that supports it. The workload has to prove what it is running to the party that releases the keys, which is attestation. The driver stack has to support the mode end to end. And data that travels unprotected on its way to the accelerator was never protected. Even when all of that holds, the Kubernetes control plane still sees the Pod's metadata, its scheduling and its logs.

What a platform team decides. Five things, and none of them is a product choice:

  1. Host trusted execution. Whether the CPU side of the node also runs in a trusted execution environment, because protecting the accelerator while the host's memory is readable leaves the data path open.
  2. Attestation. Whether keys are released per session after the workload proves its state, and who runs the service that checks the proof.
  3. Cost. Confidential modes cost throughput and operational effort, and neither is free. Measure both on your own workload before you promise a tenant a number.
  4. Data residency. Where the data and the model may physically sit, which decides which regions and providers are in scope at all.
  5. Air gap. Whether the platform must run with no outside network, which changes how images, models and updates reach it.

Write the threat model down first: which party you are protecting the data from, and which of them you still have to trust. Without that, no mode on any accelerator can be said to protect anything.
