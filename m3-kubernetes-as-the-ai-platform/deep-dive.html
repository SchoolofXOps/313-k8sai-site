Deep Dive — Feature-Gate Frontmatter, KEP Metadata and CRD Served Versions as Evidence

The lab graded six landscape entries from release pages and from your own cluster's API. This page goes one layer down, to the three artifacts every grade in this course rests on, and reads each one raw, at a pinned commit or release: a feature gate's frontmatter, a KEP's kep.yaml, and a CRD's served and storage versions in a release manifest. Each says something different, and the most common grading mistake in this field is reading one of them as if it said what another does. You will use this the first time a release note, a vendor slide and a KEP disagree about which stage a feature has reached, and when you have to decide whether a manifest written for one version of a project will still be accepted by the next.

Where this picks up

This page needs no cluster. It needs curl, awk, grep, sed and shasum, and it writes into one folder, evidence/, at the root of your clone. That folder is outside your platform repository and is never committed: it grades claims this course makes, and it is not a record of your platform. Your clone's git status lists evidence/ as untracked, and that is expected; leave it out of every commit. Running the block again is safe.

mkdir -p evidence
ls -d evidence

[ Expected output ]

evidence

Every read below names a full commit SHA or a release asset, never a branch. A branch moves, so a reading taken from main today and one taken next month can disagree with neither of them wrong. A pinned read gives the same bytes every time, which is what makes it evidence.

1 — Feature-gate frontmatter: what each release shipped​

Think of a feature gate's page as the label on a medicine bottle. The label does not tell you what the lab hopes to make next year. It tells you what is in this bottle, from which batch, and whether you take it unless told otherwise. In Kubernetes, the bottle is a release, and the label is the frontmatter at the top of the gate's page in the kubernetes/website repository: one entry per stage, each with the release it started in, the release it ended in, and whether the gate is on by default.

Read the frontmatter of GenericWorkload, the gate behind the core Workload and PodGroup objects. The awk prints only the stages list.

curl -fsSL https://raw.githubusercontent.com/kubernetes/website/72786d43a07fafa626843a6f8a56a6ee5f0db7af/content/en/docs/reference/command-line-tools-reference/feature-gates/GenericWorkload.md | awk '/^stages:/{p=1} /^---$/{p=0} p'

[ Expected output ]

stages:
  - stage: alpha
    defaultValue: false
    fromVersion: "1.35"
    toVersion: "1.36"
  - stage: beta
    defaultValue: false
    fromVersion: "1.37"

Read it entry by entry. The gate was alpha from 1.35 through 1.36, and it is beta from 1.37, with defaultValue: false in both entries. So in Kubernetes 1.37 the API is served at scheduling.k8s.io/v1beta1 only on a cluster whose operator turned the gate on, as the course's base profile does. A slide that says "gang scheduling is beta in 1.37" is true and leaves out the half that matters: it is off unless someone switched it on. Two fields carry the grade, stage and defaultValue, and you need both.

2 — A KEP's kep.yaml: what a SIG intends​

A KEP is a building permit application, not a building. It says what the applicant plans to build, when they hope to finish each floor, and who signed off on the plan. Nobody moves into a permit. The kep.yaml file in each KEP's folder in kubernetes/enhancements is the form's cover sheet: a status, a target stage, the release the work is aimed at, and the milestone each stage was or is aimed at.

Read the cover sheet of KEP 4671, the gang-scheduling proposal behind the same gate.

curl -fsSL https://raw.githubusercontent.com/kubernetes/enhancements/91ac5bf521ebe74a27f75bf274467b192932d618/keps/sig-scheduling/4671-gang-scheduling/kep.yaml | grep -E '^(owning-sig|status|stage|latest-milestone):|^  (alpha|beta|stable):|^  - name:'

[ Expected output ]

owning-sig: sig-scheduling
status: implementable
stage: stable
latest-milestone: "v1.38"
  alpha: "v1.35"
  beta: "v1.37"
  stable: "v1.38"
  - name: GenericWorkload

The line that misleads people is stage: stable. The comment above it in the file says what it means: the target stage in the current development cycle. Read it with latest-milestone, which names the release that work is aimed at, v1.38. At the time of this reading Kubernetes 1.38 had not been released, and this course pins 1.37.x. So the KEP's stable line is a plan for a release that does not exist yet. It is not evidence that anything shipped, and a grade that rests on it is resting on an intention. The feature-gate frontmatter in section 1 is what tells you what 1.37 actually shipped: beta, and off by default. The feature-gates entry in the KEP is worth reading for a different reason: it names GenericWorkload as the one gate for this work, which is how you find the frontmatter to read.

3 — A CRD's served and storage versions: what a cluster answers​

For a project that adds its own API, neither a feature gate nor a KEP applies. The evidence is the CustomResourceDefinition the release installs. Think of a CRD's versions list as a post office's list of accepted address formats. served: true means the API server accepts a request written in that version's format. storage: true marks the one version the API server writes to etcd, whatever format the request came in. A version that is no longer served is a format the post office refuses, and a manifest written in it is rejected at the counter, however correct it once was.

Download Agent Sandbox's v1.0.5 release manifest, and check that its bytes are the ones this course pinned before you read anything from it. The course pinned sha256 e89fd95c0aa57609fa24be4112bd52ce67fe8939ecf6f3c17edf2f1e8f1eb860.

curl -fsSL -o evidence/sandbox-v1.0.5.yaml https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.5/sandbox.yaml
shasum -a 256 evidence/sandbox-v1.0.5.yaml

[ Expected output ]

e89fd95c0aa57609fa24be4112bd52ce67fe8939ecf6f3c17edf2f1e8f1eb860  evidence/sandbox-v1.0.5.yaml

If the hash differs, stop: the asset was replaced after this page was written, and the reading below would describe bytes nobody pinned. Now read each CRD in the manifest, its group, and every version with its served and storage flags.

awk '/^kind: /{k=$2} k=="CustomResourceDefinition" && /^  name: /{print "crd: " $2} k=="CustomResourceDefinition" && /^  group: /{print "group: " $2} k=="CustomResourceDefinition" && /^    name: v[0-9]/{v=$2} k=="CustomResourceDefinition" && /^    served: /{s=$2} k=="CustomResourceDefinition" && /^    storage: /{print "version: " v "  served: " s "  storage: " $2}' evidence/sandbox-v1.0.5.yaml

[ Expected output ]

crd: sandboxes.agents.x-k8s.io
group: agents.x-k8s.io
version: v1beta1  served: true  storage: true

The manifest holds one CRD, sandboxes.agents.x-k8s.io, and one version, v1beta1, served and stored. That single line is the whole maturity grade: a beta API group, agents.x-k8s.io/v1beta1, so shipped-and-immature under the course's criteria, whatever the project's own release number says. It also tells you something no release note does as directly. No older version is listed as served, so a manifest written for an earlier API version of this project is refused by a cluster running this release, not converted. When you plan an upgrade of any CRD-based project, this is the read that tells you which of your stored manifests will still be accepted.

4 — Recording the three readings as evidence​

Write the three readings into one table, one row per evidence type. Each row says which claim the artifact bears on, the stage word you read, and the pinned address you read it from, so anyone can repeat the read and get the same bytes.

cat > evidence/m3-claim-grades.md <<'EOF'
# Claim grades, read from pinned artifacts

| Evidence type | Claim | Stage read | Source URL |
| --- | --- | --- | --- |
| Feature-gate frontmatter | GenericWorkload in Kubernetes 1.37 | beta, defaultValue false | https://raw.githubusercontent.com/kubernetes/website/72786d43a07fafa626843a6f8a56a6ee5f0db7af/content/en/docs/reference/command-line-tools-reference/feature-gates/GenericWorkload.md |
| KEP kep.yaml | KEP 4671, gang scheduling | stable, as the target for latest-milestone v1.38; a plan, not a release | https://raw.githubusercontent.com/kubernetes/enhancements/91ac5bf521ebe74a27f75bf274467b192932d618/keps/sig-scheduling/4671-gang-scheduling/kep.yaml |
| CRD served and storage versions | sandboxes.agents.x-k8s.io at Agent Sandbox v1.0.5 | served, v1beta1 only, also the storage version | https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.5/sandbox.yaml |
EOF
cat evidence/m3-claim-grades.md

[ Expected output ]

# Claim grades, read from pinned artifacts

| Evidence type | Claim | Stage read | Source URL |
| --- | --- | --- | --- |
| Feature-gate frontmatter | GenericWorkload in Kubernetes 1.37 | beta, defaultValue false | https://raw.githubusercontent.com/kubernetes/website/72786d43a07fafa626843a6f8a56a6ee5f0db7af/content/en/docs/reference/command-line-tools-reference/feature-gates/GenericWorkload.md |
| KEP kep.yaml | KEP 4671, gang scheduling | stable, as the target for latest-milestone v1.38; a plan, not a release | https://raw.githubusercontent.com/kubernetes/enhancements/91ac5bf521ebe74a27f75bf274467b192932d618/keps/sig-scheduling/4671-gang-scheduling/kep.yaml |
| CRD served and storage versions | sandboxes.agents.x-k8s.io at Agent Sandbox v1.0.5 | served, v1beta1 only, also the storage version | https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.5/sandbox.yaml |

Compare each row with what you read above. If a row disagrees with your own reading, your reading wins: change the row. The second row is the one to read twice. Its stage word is stable, and the rest of the cell is there so that nobody, including you in six months, reads it as a fact about a release.

Keep evidence/ for as long as it is useful to you. It is not in your platform repository, and nothing later in the course reads it. Delete the folder when you are done with it.

Where you will use this​

Where you will use this
  • A feature gate's stage and defaultValue together are what a release shipped. Use it when: a team asks to depend on a feature that "is beta in 1.37". Read the gate's frontmatter for your exact release, check defaultValue, and if it is false, ask who turns it on in every cluster you run, and what happens to the workload in a cluster where nobody did.
  • A KEP's stage is the target for its latest-milestone, a plan and never a shipment. Use it when: a roadmap, a vendor slide or a conference talk says something reaches its next stage in a coming release, such as 1.38. Read the kep.yaml, note the milestone, and record the claim as a plan with that milestone beside it until the release ships and the gate's frontmatter says so.
  • A CRD's served and storage versions are the API a cluster with that release answers. Use it when: you plan an upgrade of a CRD-based project, or a manifest copied from an older example is rejected. Read the versions list in the new release's manifest, and find every stored object and manifest written in a version that is no longer served before you upgrade.
  • A pinned read is evidence, and a read from a branch is a snapshot. Use it when: you write a design review, an incident report or a grading of your own. Cite a commit SHA or a release asset, with the date you read it, so the next reader gets the same bytes you did.
