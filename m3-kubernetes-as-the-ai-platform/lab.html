Lab — Audit a Base Cluster Against the AI Conformance Requirements and Write the Platform Design

Lab Truth Contract — REAL

Nothing is installed. The audit reads a real cluster's API: every probe is a read-only kubectl command against the grid-core cluster you create, and the design documents are files you write yourself. The gap report is your own reading of one cluster against a published checklist. It is not a conformance result, and nothing in this lab certifies the cluster, the platform or you.

In this lab you take a fresh base cluster and check it, item by item, against the requirements CNCF publishes for AI-conformant platforms. You will find that most of them are not met. That is the honest starting point, and writing it down is what makes the rest of the course measurable: every later module closes one or more of the gaps you record here. Then you write the design document the course builds against, and you grade six entries of the landscape yourself.

Think of it as a building inspection before a renovation. The inspector does not fix anything. They walk the building with the regulations in hand, write down what is there and what is missing, and note which items they could not check without opening a wall. The renovation plan is written from that report, not from the brochure.

Run every command from the root of your clone of the labs repository, as in the earlier modules. If you open a second terminal, export KUBECONFIG there again. You need curl and jq on your machine; the setup page installed both.

Where the platform stands​

Module 1 left you a base cluster profile you can create, verify and tear down from your own repository, and a record of three failures it cannot handle yet. Module 2 added two documents and no cluster: a capacity model and a cost model. There is no cluster running now. Module 1 tore it down, and this lab starts by creating a new one.

What the platform cannot do yet is almost everything an AI platform is asked for. When you finish, your repository holds a gap report that says so item by item, a design document that says what the platform will become and which module delivers each part, and your own grading of six entries in the landscape.

The headline gap is the one the next module closes. The cluster serves the Dynamic Resource Allocation API, resource.k8s.io/v1, but no driver publishes a single ResourceSlice, so no device can be requested by attribute yet. Module 4 closes it.

Read the published conformance requirements​

The requirements are a YAML file in CNCF's cncf/k8s-ai-conformance repository, one file per Kubernetes version. A vendor copies it, fills in how its platform meets each item, and submits it. You read it at a fixed commit, so the list you audit against is exactly the list this page was written against.

m3/kar-list.sh downloads the 1.37 file at that commit and prints one line per requirement: its category, its level and a short label this course uses for it. It prints no upstream description and no upstream id. The descriptions are the vendor checklist's own prose, which you can read in full at the pinned file on GitHub, and one of the upstream ids contains an adjective this course does not print. The script reads nothing from your cluster, and it stops with an error if the file ever holds an item it has no label for, or a count other than 15.

bash m3/kar-list.sh

Audit the cluster against each requirement​

Now walk the building. For each item you run a read-only command and decide one of three verdicts:

  • verifiable here means this cluster's API can answer the question. It often answers it with a gap: "the API this needs is not served" is a real finding, read from the cluster.
  • not verifiable on this cluster means the question needs something a laptop cluster cannot have, such as an accelerator, a driver or a fast network. You cannot say yes or no.
  • not applicable means the item does not apply to this kind of cluster at all, and the checklist allows that with a written reason.

A kubectl get that finds nothing prints No resources found. That line is the evidence, so read it rather than skip it. A kubectl api-resources for an API group the cluster does not serve prints only its header line, NAME SHORTNAMES APIVERSION NAMESPACED KIND, with nothing under it, and no error: that empty table is the finding too. Every command below is read-only.

Write the gap report​

The gap report is the inspection report. KAR stands for the Kubernetes AI Requirements, the items the checklist lists. The report lives in your repository as grid-platform/docs/kar-gap-report.md, beside Module 2's two models, and it has three parts: where the list came from and which cluster you read, the one headline gap, and one row per requirement.

The first block writes the source and the cluster, read from your cluster rather than typed, and the headline. The headline is this sentence, on one line:

resource.k8s.io/v1 is served, but no driver publishes a ResourceSlice: no device can be requested by attribute yet. Module 4 closes this.

K8S=$(kubectl --context kind-grid-core version -o json | jq -r '.serverVersion.gitVersion')
{
  echo '# KAR gap report'
  echo
  printf 'Source: the Kubernetes AI Conformance checklist for 1.37, `docs/AIConformance-1.37.yaml` at commit `c64e5bc8085da207715df96e458f2c6585c9f53e` of `cncf/k8s-ai-conformance`. Cluster: `grid-core` at SIZE=%s with no addons, Kubernetes %s. Audited on %s.\n' "${SIZE:-8}" "$K8S" "$(date +%F)"
  echo
  echo '## Headline'
  echo
  echo 'resource.k8s.io/v1 is served, but no driver publishes a ResourceSlice: no device can be requested by attribute yet. Module 4 closes this.'
  echo
} > grid-platform/docs/kar-gap-report.md
cat grid-platform/docs/kar-gap-report.md

Write the platform design document​

The design document is the drawing the rest of the course builds from. It names the three tenants, maps them onto the four workload classes from Module 2, lists what the platform can and cannot do today, gives every layer of the platform an owner, draws the boundaries between your team and the teams you serve, and lists the decisions this module leaves to later ones.

Its ## Capabilities section links the two models Module 2 wrote, capacity-model.md and cost-model.md, because the capacity and cost numbers behind the design live there. If you skipped Module 2, do its lab now: it needs no cluster.

cat > grid-platform/docs/platform-design.md <<'EOF'
# Platform design

The platform runs AI workloads for three internal tenants on one shared fleet of accelerators. This document records who the tenants are, what they run, what the platform offers today, who owns each layer, and the decisions that later modules make.

## Tenants

| Tenant | What it runs | Priority |
| --- | --- | --- |
| `research` | distributed training and fine-tuning experiments | waits in a queue; may be preempted by `product` |
| `data` | batch dataset preparation | lowest; may be interrupted and resumed |
| `product` | models served to users, and the agents built on them | highest; capacity must be there when traffic arrives |

## Workload classes

| Class | Tenants | What it needs from the platform |
| --- | --- | --- |
| Data preparation | `data` | CPU-heavy batch jobs, fast reads from object storage, tolerance of interruption |
| Training and fine-tuning | `research` | a group of Pods placed all at once or not at all, devices requested by attribute, checkpoints that survive a lost worker |
| Inference | `product` | a readiness gate for a slow model load, autoscaling on a queue signal, routing by load and cache locality |
| Agents | `product`, `research` | a sandboxed runtime, a narrow identity per tool server, an audit trail of every change |

## Capabilities

Capacity and cost inputs: the [capacity model](capacity-model.md) and the [cost model](cost-model.md), from Module 2. Status today comes from [the gap report](kar-gap-report.md).

| Capability | Status today | Delivered by |
| --- | --- | --- |
| Devices requested by attribute | not available: resource.k8s.io/v1 served, no driver | M4 |
| Quota, queues and gang admission | not available: no queueing layer installed | M5 |
| Storage and network paths that keep accelerators busy | not available | M6 |
| Training that resumes from a checkpoint | not available: no training operator installed | M7 |
| Model serving with autoscaling on a queue signal | not available: no metrics API registered | M8 |
| Routing by load and cache locality | not available: no Gateway API served | M9 |
| A data layer, verified artifacts and promotion through Git | not available | M10 |
| Sandboxed agents with a narrow identity | not available: no RuntimeClass defined | M11 |
| Metrics, cost per tenant and recovery | not available: no monitoring stack | M12 |

## Architecture by layer

| Layer | Components | Owner |
| --- | --- | --- |
| `nodes` | device driver, DeviceClasses, ResourceClaimTemplates | `DRA` driver, run by `platform` |
| `capacity` | ResourceFlavors, ClusterQueues, LocalQueues, PriorityClasses | `Kueue`, configured by `platform` |
| `dataplane-storage` | StorageClasses, cache tiers, secondary networks | `platform` |
| `training` | training runtimes, job templates, checkpoint policy | training operator, run by `platform`; jobs owned by `research` |
| `serving` | model-server Deployments, probes, autoscalers | `platform` runtime; models owned by `product` |

| `observability` | Prometheus rules, dashboards, chargeback queries | `platform` |

## Ownership boundaries

| Boundary | Owner |
| --- | --- |

Grade the landscape yourself​

The lesson printed the course's grading of the landscape. Now you grade six of its entries yourself, from the artifacts, so the grading in your repository is yours. The file is grid-platform/docs/landscape-grading.md. This block writes its frame: a place for the criteria, and the six rows with the entry and a source to read already filled in. The grade cells and the date are empty, because they are your part.

Known failures and their fixes​

Each entry below is something that actually happened in one of the course's own runs of this page, or in a learner walk of it, with the step it happened in named so you can compare it with your output.

The course ran this page once from a fresh clone, every block in order from the cluster's creation to its teardown, and no step failed: every command printed what this page shows, and the course's checks for this lab passed against the cluster and the three documents before the teardown. So there is no failure to list yet. Two readings in that run look like failures and are not.

The scheduling step prints Error from server (NotFound) and exits non-zero. Seen in the course's run, at the scheduling and orchestration step. The cluster has no metrics API registered, and that error is how kubectl get apiservice v1beta1.metrics.k8s.io says so. It is the pod-autoscaling finding, and the gap report records it. The No resources found lines and the header-only tables elsewhere in the audit are findings in the same way.

One CoreDNS Pod reads 0/1 in the networking step. Seen in the course's run, at the networking step: get pods -A listed one of the two CoreDNS replicas as Running but not yet ready, 0/1, 21 seconds after the cluster was created. It does not change the audit. The disaggregated-inference item reads only whether an inference server is running, and none is. If you run the audit later than the course did, you may see 1/1 on both.

If a step fails in a way the page does not describe, run the step's command again on its own and read its error before you change anything. Every command on this page is read-only, except the file writes and the commit, so running one again is safe.

Where you will use this​

The next time a vendor tells you their platform is certified for AI, you will ask which product, in which configuration, at which Kubernetes version, and then read that submission yourself. When a team asks whether your cluster is "AI-ready", you will hand them a gap report like this one, item by item, with the command behind each answer, instead of a yes. When someone proposes adopting a project because of its announcement, you will grade it against printed criteria and an artifact you can open at a version. And when the platform's direction is argued about, the design document is the thing the argument is about: who the tenants are, who owns each layer, and which decision belongs to which stage of the build.
